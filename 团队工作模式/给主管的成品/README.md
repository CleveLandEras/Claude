# 给主管的成品：每周一重跑说明

只读：只用 Jira 查询类工具（`searchJiraIssuesUsingJql`、`getJiraIssue`），不评论、不改字段、不转状态。cloudId 写 `xsg-game.atlassian.net`。

## 1. 两份成品各是什么、给谁

- **版本清单**（`<日期>_版本清单.html`，附 `<日期>_版本清单_Teams摘要.txt`）：给崔峰龙排期、开周会前看——本周和下周两个版本还差哪些需求、哪些单有逾期风险、哪些需求已转成长篇故事还没挂版本。由 Dk 转发，摘要贴进 Teams。
- **需求单预读**（`<日期>_需求单预读.html`，附 `<日期>_需求单预读_Teams摘要.txt`）：给崔峰龙立项、派单前看——上一周新进的营运需求单逐张一个建议（要他定、建议立项、重复或已有单在做、营运已说不用），已被他转走或派了人的照实标出；另附 3 张建议关的老单。由 Dk 转发，摘要贴进 Teams。

## 2. 每周一的参数怎么定

- **数据日期 `<日期>`**：跑查询的当天，格式 `YYYY-MM-DD`。文件名、数据文件夹都用它。
- **两个版本**：本周版本是发版日落在本周四的那个，下周版本是下一个。版本名格式「08_V序号_M.D」（M.D 是发版日）。例：11/2 那周是 `08_V50_11.5`、`08_V51_11.12`；11/9 那周是 `08_V51_11.12`、`08_V52_11.19`。发版日脚本直接从单子的 `fixVersions[].releaseDate` 取，不用手填。
- **需求单预读的时间窗 `<起>`、`<止>`**：上周一到上周日。例：11/2 跑的是 `2026-10-26`—`2026-11-01`；11/9 跑的是 `2026-11-02`—`2026-11-08`。JQL 里写 `created >= "<起>" AND created < "<止的下一天>"`。没到周日就跑时（例如 10/29 的初稿），标题的止日自动写成数据日期。
- **两份共用一个查询时间** `数据/<日期>/查询时间.txt`，两份 HTML 的「数据截至」一样。（10/29 初稿两份是分开查的，所以 `数据/2026-10-29/` 里另有一份 `查询时间_需求单.txt`；需求单预读.py 有这个文件时读它，没有就读 `查询时间.txt`。以后不用再建。）

## 3. 步骤和 JQL（版本清单 Q1—Q4，需求单预读 Q5—Q7）

先建文件夹、记查询时间（HTML 里的「数据截至」从这里读）：

```
cd ~/claude/团队工作模式/给主管的成品
mkdir -p 数据/<日期>/原始/变更记录
date "+%Y-%m-%d %H:%M" > 数据/<日期>/查询时间.txt
```

**查询顺序：记完查询时间，先查需求单预读的 Q5—Q7（连同 Q5 里长篇故事的变更记录），紧接着查版本清单的 Q1—Q4，中间不停。** 两份要一起转给主管，同一张单在两份里的说法必须一致。10/29 初稿版本清单 16:45 截数、需求单 16:54 截数，中间 16:48 RICH-25929 被转成长篇故事，结果需求单写「已转」，版本清单的「已转、没挂版本」里却没有它。先查需求单是为了让版本清单的 Q4 取到最新的转单结果；万一中间还有人转单，以 Q4 为准，需求单那张会显示「还停在待受理」，重跑一次 Q5 就对上了。

每条 JQL 前面都加 `project = RICH AND`。`maxResults` 填 100，没写的不限状态。

| 编号 | 存成 | JQL（`project = RICH AND` 之后） | fields |
|---|---|---|---|
| Q1 | `q1_版本长篇故事.json` | `fixVersion in ("<版本1>", "<版本2>") AND issuetype in (Epic, Legend) AND statusCategory != Done ORDER BY key` | `summary,status,issuetype,assignee,fixVersions,duedate,created,labels` |
| Q2 | `q2_子单_p1.json`、`_p2`… | `parent in (<Q1 的长篇故事单号>) ORDER BY key` | `summary,status,issuetype,assignee,fixVersions,duedate,parent` |
| Q3 | `q3_版本内其他单.json` | `fixVersion in ("<版本1>", "<版本2>") AND issuetype not in (Epic, Legend) AND statusCategory != Done AND (parent is EMPTY OR parent not in (<Q1 的长篇故事单号>)) ORDER BY key` | 同 Q2 |
| Q4 | `q4_已转未挂版本.json` | `issuetype = Epic AND labels = form-37 AND fixVersion is EMPTY AND statusCategory != Done ORDER BY created DESC` | `summary,status,assignee,reporter,created,labels,issuelinks` |

`<Q1 的长篇故事单号>`（不含 Legend）用这行取，逗号分隔贴进 Q2、Q3：

```
python3 -I -c "import json,glob;print(','.join(sorted({x['key'] for p in glob.glob('数据/<日期>/原始/q1*.json') for x in json.load(open(p))['issues']['nodes'] if x['fields']['issuetype']['name']!='Legend'})))"
```

**Q4 的长篇故事要查变更记录**（form-37 标签会被克隆单带过来，只有变更记录能证明是由需求单改来的）：

1. 先看 `数据/来源核对*.json` 里已有哪些单号，已有的不再查。
2. 其余每张调 `getJiraIssue`：`issueIdOrKey=<单号>`，`expand=changelog`，`fields=["summary"]`。原始结果存成 `原始/变更记录/<单号>.json`（存法见第 4 节）。一张约 30KB，张数多时交给子任务并行查。
3. 跑版本清单命令时加 `--补来源核对`，脚本读这些文件，把结果写进 `数据/来源核对_版本清单.json`。

`来源核对_版本清单.json` 的格式（每张一条）：

```
{"RICH-25461": {"由需求单转来": true, "改类型时间": "2026-10-19 12:05", "改类型人": "Fury Cui(崔峰龙)", "克隆自": null}}
```

判据：变更记录里有一条 `field == "issuetype"`、`fromString == "Requirement"`、`toString == "Epic"`，就是「由需求单转来」；`克隆自` 看 Q4 的 `issuelinks` 里有没有 `Cloners` 类型的链接。为 false 的单不进「已转、没挂版本」表，只在终端打印。

### 需求单预读：Q5—Q7

| 编号 | 存成 | JQL（`project = RICH AND` 之后） | fields |
|---|---|---|---|
| Q5 | `q5_新需求单.json` | `created >= "<起>" AND created < "<止的下一天>" AND (issuetype in (Requirement, ACC) OR (issuetype = Epic AND labels = form-37)) ORDER BY created` | `summary,status,issuetype,assignee,reporter,created,labels,fixVersions,issuelinks,description,comment` |
| Q6 | `q6_老单.json` | `key in (RICH-12940, RICH-18256, RICH-13234, RICH-18097) ORDER BY key` | `summary,status,issuetype,created,resolutiondate,comment` |
| Q7 | `q7_查重_<单号>.json`（每张一个） | `issuetype in (Epic, Requirement) AND summary ~ "<关键词>" AND created >= -365d ORDER BY created DESC`；多个关键词用 `(summary ~ "a" OR summary ~ "b")` | `summary,status,issuetype,created,fixVersions,assignee` |

- Q5 查正文和评论时，`responseContentFormat` 填 `markdown`。
- **Q5 里的长篇故事要查变更记录**：和 Q4 的做法一样（先看 `数据/来源核对*.json` 里已有的不再查，其余每张 `getJiraIssue`，`expand=changelog`，`fields=["summary"]`，存成 `原始/变更记录/<单号>.json`）。跑需求单预读命令时加 `--补来源核对`，结果写进 `数据/来源核对_需求单.json`，格式和判据同上。克隆单（例：RICH-25951 克隆自 RICH-25358）记为 false，不算新进，只在终端打印。
- **Q7 只查还停在待受理的单**：Q5 里仍是 Requirement 或 ACC、负责人还是崔峰龙的单。每张取 1—3 个标题关键词（取业务名词，例「刮刮樂」「信用卡」「卡號」），用繁体原文。已转长篇故事或负责人已不是崔峰龙的单不用查。

## 4. 原始 JSON 怎么存

- **结果超长**：工具会提示 `Output has been saved to …/tool-results/<文件名>.txt`，用 `cp` 把那个文件拷成 `原始/<编号>_<名字>.json`，不改内容。
- **直接返回在对话里的小结果**：用 Write 原样存成 JSON（从 `{"issues"` 开始的整段）。
- **翻页**：返回里 `pageInfo.hasNextPage` 为 true 时，把 `endCursor` 填进 `nextPageToken`、其余参数不变再查一次；每页一个文件 `q2_子单_p1.json`、`q2_子单_p2.json`…。脚本用 glob 合并同一前缀的所有文件、按单号去重。
- **变更记录**：每张一个文件 `原始/变更记录/<单号>.json`。
- 直接返回在对话里、又长得不便原样抄的结果，可以只去掉头像（`avatarUrls`）、`self`、`iconUrl`、邮箱、`accountId`、类型和版本的说明，以及正文里的图片链接，其余字段照抄；在文件顶上加一个 `"_存法"` 字段写明去掉了什么（10/29 的 Q5—Q7 和 4 张变更记录就是这样存的）。脚本只读 `issues.nodes`，不受影响。

## 5. `建议.json` 的格式和四类判断

放在 `数据/<日期>/建议.json`，由 AI 逐张读 Q5 的正文和评论、Q7 的查重结果后写，脚本只负责校验和合成。每周从上一周的拷过来再改：已被转走或派了人的单脚本会自动挪到「已转或已派」，旧条目不用删；新进的单补写；已有的看有没有新评论推翻原来的证据。

```
{
 "新单": {
  "<还停在待受理的单号>": {
   "一句话需求": "转述营运要什么，一句",
   "建议": "要他定 | 建议立项 | 重复或已有单在做 | 营运已说不用",
   "要他定的问题": "只给「要他定」写：要他定的是什么，一句问句",
   "建议做法": "只给「要他定」写：我们的建议，一句",
   "理由": "一句",
   "对应单号": ["RICH-…"],
   "评论原话": {"原文": "照抄评论里的一段"},
   "外部资料": {"名称": "表格名", "分页": "页名", "链接": "单子正文里的原链接", "摘录": "原始/表格摘录_<单号>.txt", "原话": ["摘录里的原文片段"]},
   "要点草稿": "1. …\n2. …"
  },
  "<已转长篇故事或已派人的单号>": {"一句话需求": "从单子正文转述，一句"}
 },
 "老单": {
  "RICH-12940": {"原话": ["現況已經有了"]},
  "RICH-18256": {"原话": ["已經有單子優化", "那這單請關閉"]},
  "RICH-13234": {"做掉它的单": "RICH-18097"}
 }
}
```

- **每张新进单都要有 `一句话需求`**，包括已转长篇故事或已派人的（只转述单子正文，不给建议）；缺了脚本报错。
- **需求写在外部表格里的**（单子正文只有一个链接）：先用 Google Drive 只读打开表格（`get_file_metadata` 加 `snippetVerbosity: MAX_ALLOWED` 能拿到整页文字），把和这张单有关的部分照抄进 `原始/表格摘录_<单号>.txt`（开头写表格名、分页、链接、打开时间），再按表格内容写一句话需求和建议；理由里引用的表格原文放进 `外部资料.原话`，脚本会逐字到摘录里核对，链接也要出自单子正文。**打不开**就在理由里写「表格没有查看权限」，判「要他定」，问题写成「要不要先请营运把范围写进单子」。

四类怎么判：

- **重复或已有单在做**：Q7 里有范围相同、未关或已完成的单。`对应单号` 必填，而且要出现在 Q5 或 Q7 的结果里。
- **营运已说不用**：营运在评论里说过不需要、已经有了。`评论原话.原文` 必须是该单评论原文的一段（脚本逐字比对，作者和日期从评论里取）。
- **建议立项**：需求写清楚了、没有重复。`要点草稿` 必填。
- **要他定**：有相近的单但范围不同；范围太大或还有未定项，单子本身看不出这次要做哪些；或者牵涉插单、急单、和在做的单冲突。相近的单写进 `对应单号`；`要他定的问题`、`建议做法` 必填（脚本拦），页面上会写成「要你定：…建议：…」。

`要点草稿`（只给「建议立项」写）：3—5 条编号要点、≤200 字，只转述营运原文——现况、要改什么、范围或平台、营运给的参数或参考；原文有待定项时最后加一行「营运待确认：…」。不写目标版本、负责人，也不写自己的方案。脚本会拦：超过 200 字、出现 `V` 加两位数字、出现原始 JSON 里任何人的中文名。

`老单` 里的原话要能在 Q6 的评论原文里找到；`做掉它的单` 要在 Q6 里而且已完成。老单如果已经关了，脚本会把它从表里去掉，写一句「已关」，不补别的单。

## 6. 命令

```
cd ~/claude/团队工作模式/给主管的成品
python3 -I 版本清单.py 数据/<日期> --版本 <版本1> <版本2> --补来源核对 --自检
```

- 输出 `<日期>_版本清单.html`、`<日期>_版本清单_Teams摘要.txt`，终端打印各版本未完成长篇故事数、风险数、未填截止日数、已转未挂版本数。
- `--自检`：HTML 里每个单号都要在原始 JSON 里；「先看这里」的计数要等于对应表格的行数；风险原因只能是三种；「先看这里」要排在第一个表格前面。不过就返回非 0。Q4 里有长篇故事还没核对来源时返回 2，先补变更记录。
- 用同一份原始数据再跑一次，HTML 和摘要应当和上次完全一样（`diff` 无差异）。

```
python3 -I 需求单预读.py 数据/<日期> --起 <起> --止 <止> --补来源核对 --自检
```

- 输出 `<日期>_需求单预读.html`、`<日期>_需求单预读_Teams摘要.txt`，终端打印各类张数、被剔掉的克隆单、`建议.json` 里已不用的条目、老单是否已关。
- Q5 里有长篇故事还没核对来源时返回 2；还停在待受理的单在 `建议.json` 里缺条目、或证据校验不过（见第 5 节）时返回 1，不出文件。
- `--自检`：HTML 和摘要里每个单号都要在原始 JSON 里；「先看这里」的各个计数要等于对应表格的行数；「先看这里」要排在第一个表格前面；HTML 和摘要里没有第 7 节第 2 条那些词，状态名后面没跟括号；摘要 3—5 行、用了第 05 节的开场句。不过就返回非 0。

**抽查计数**（用 `searchResultMode: count`，和 HTML 对数）：

| 哪份 | 对哪个数 | JQL（`project = RICH AND` 之后） |
|---|---|---|
| 版本清单 | 本周版本未完成需求数（等于本周版本表行数） | `fixVersion = "<版本1>" AND issuetype = Epic AND statusCategory != Done` |
| 版本清单 | 已转、没挂版本（减去来源核对为 false 的，等于第 2 节行数） | Q4 去掉 `ORDER BY` |
| 版本清单 | 已过截止日 | `(parent in (<Q1 的长篇故事单号>) OR (fixVersion in ("<版本1>", "<版本2>") AND issuetype not in (Epic, Legend))) AND statusCategory != Done AND duedate < "<日期>"` |
| 版本清单 | Blocked | 同上，把后半段换成 `AND status = Blocked` |
| 需求单预读 | 新进张数（减去来源核对为 false 的，等于第 1、2 节行数之和） | Q5 去掉 `ORDER BY` |
| 需求单预读 | 还停在待受理的（等于第 1 节行数） | `created >= "<起>" AND created < "<止的下一天>" AND issuetype in (Requirement, ACC) AND assignee = "712020:fd4c2aca-03b3-4cad-8de8-fc1e0c53ef27"` |
| 需求单预读 | 老单还开着（等于第 3 节行数） | `key in (RICH-12940, RICH-18256, RICH-13234) AND statusCategory != Done` |

查询和抽查之间如果有人改了单，数字会差几张；差的单要能逐张说清楚（用 `key not in (<快照里的单号>)` 找出来）。

**口径**（脚本已按这些算，不用手判）：

- 长篇故事只取 Epic；Legend 只计数，写在页脚。两版都挂的长篇故事归到较早的版本，后一版那节写「另 N 张同时挂…，见上表」。
- 逾期风险只认三条：截止日早于数据日期；截止日晚于这张单所挂版本里最晚的发版日（单子没挂版本时用它所属长篇故事的版本）；状态是 Blocked。一张单挂两个版本不算风险。长篇故事本身填了截止日的，也按这三条判。
- 子单取本版长篇故事下的全部子单（不限是否挂本版）；挂了本版、但不在这些长篇故事下的单只在命中风险时列出，页脚计数。

## 7. 发送前自查

两个脚本的 `--自检` 都返回 0 以后，再手动过这三条（在本文件夹下跑）：

1. **只给建议、不拍板**：
   `grep -nE "已决定|请关闭|应挂|挂到 ?V|派给.{0,6}(吧|即可)|直接关" <日期>_*.html <日期>_*_Teams摘要.txt` 没有命中（需求单预读.py 也会拦 `建议.json` 的「建议」「理由」「要点草稿」）；「已转、已派」那节写的是 Jira 上的事实，不算。要点草稿里没有版本号、没有人名。
2. **写给上级的口吻**：
   `grep -nE "待验收|替你定|验收官|子代理|自评|制作过程|对照表|轮次" <日期>_*.html <日期>_*_Teams摘要.txt` 没有命中；`grep -nE "(To Check|Checking|Blocked) ?[（(]" <日期>_*.html` 没有命中（状态名后面不加括号解释）。
3. **Teams 摘要**：`wc -l <日期>_*_Teams摘要.txt` 每份 3—5 行；两份第 1 行分别是第 05 节的原句：
   - `grep -F "我用 AI 把这周和下周两个版本的未完成和逾期风险整理了一份，你看看有没有用；有用我每周一给你。" <日期>_版本清单_Teams摘要.txt`
   - `grep -F "上周新进的需求单我先过了一遍、标了建议，你立项时可以直接看；另外这 3 张营运已经说不用了或已被别的单做掉，你看能不能关。" <日期>_需求单预读_Teams摘要.txt`

再看一眼：两份 HTML 的「数据截至」是不是当天；3 张老单是不是还开着（关了的脚本会自动写「已关」）。

## 8. 只读

只用查询类工具，不评论、不改字段、不转状态，不加载任何写入类工具。
