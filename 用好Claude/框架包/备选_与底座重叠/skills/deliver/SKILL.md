# 交付闸门

目的只有一个：Dk 不该是第一个发现问题的人。闸门三道：程序判（确定性，必跑）、读者走查（无上下文子任务，只看作品）、整体过目（版面与一致性，看全部页面）。三道都过才交；过不了最多修 3 轮，仍过不了就交 Dk 并写明卡在哪、我的判断。

## 0. 先有目标卡
交付物旁要有一张目标卡（模板在文末）。没有就先写。验收标准写不出「怎么验」的，说明还没想清楚，回去想，不要先做再补。目标卡是 Dk 和我之间唯一要对齐的东西：他改卡，我改产出。

## 1. 程序判（必跑，✘ 全改完再往下）
项目里有检查脚本就全跑（弹窗项目：`_scripts/judge_程序.py`、`_scripts/an_可读字数.py`、`_scripts/pl_逗号句清单.py`）。没有脚本的项目至少查：
- 链接、图片路径都能打开；渲染结果（PowerPoint 导出的 PDF、HTML 截图）能打开、无截断、底色一致。
- 禁用词：待确认、待核实、资料没写、主管要求、请主管定、请评审定、评审判断、到此结束，以及对话里长出来的内部叫法（如 核心五件、必需档、尽量档、合并版）。
- 数字有主语和分母；相对时间（今天、本周）带日期；正式文件用简体。
这一道已做成 hook（`框架包/hooks/`），Write/Edit 交付物时自动跑；用 Bash 改文件时它看不到，所以这里仍要手动跑一次。

## 2. 读者走查（无上下文子任务）
派一个子任务（机械核对用 sonnet；结构与设计判断用 opus）。**只给**：作品本身（文件或截图）＋目标卡的「读者」「读完要做什么」「验收标准」三项。**不给**：任务说明、规则全文、研究建议、我的判断、Dk 原话。
提示词骨架：

> 你是〈读者〉，没有这个项目的任何背景，只读给你的材料。你要用它完成这几件事：〈目标卡·读完要做什么〉。逐件回答：做得到／做不到（卡在哪，引原文）。然后：① 只看首屏，说出这份材料一共几部分、各讲什么、要你做什么；② 列出你看不懂、要猜、或前后矛盾的词、句、数字；③ 对照验收标准逐条判过／不过，每条给原文证据。只说你确定的，不给改进建议。

读者说「做不到」「要猜」的地方是不过项。读者复述出来的内容如果本不该出现（被否决的选项、过程说明、评审引导语），同样是不过项：走查是找漏洞，不是找表扬。

## 3. 整体过目（有页面的交付物）
另派一个没改过稿的子任务，逐页看真实渲染结果（不只看改动页），查两样：
- 三条通行做法：一页一个观点（Duarte 三秒测试）、层级不超过三层、同一组内容在同一个模块里；
- 跨页一致：同一件事的名称、数字、叫法、状态、底色全稿一致，只有一个「今天」。
先改会被当场追问的（矛盾、数字、事实不符），再改版式。

## 4. 汇总与交付
一张过／不过表（每条带证据）；不过项改完只重跑该项。全部过了才交 Dk：一句结论、文件、「要你定」「替你定、可推翻」两张短表。不写验收过程、轮次、分了几路。
把三道结果记进目标卡末尾「闸门记录」（日期、过／不过）。Dk 若仍退回，/retro 要用它判断「是闸门没跑，还是闸门拦不住」。

## 目标卡模板
```
# 目标卡：<交付物名>
- 读者：<谁，职级，对项目了解多少>
- 读完要做什么：<判断什么／拍什么板／动手做什么>
- 可用时间与篇幅预算：<分钟；页数或字数，作参照不是硬线>
- 验收标准（3–5 条，每条带怎么验）：
  1. <效果> —— 验法：<无上下文读者只看首屏能复述出……>
  2. <效果> —— 验法：<读者按任务走一遍能做成……>
  3. <效果> —— 验法：<程序判：……>
- 不做什么：<排期、开发阶段事项、被否决的选项……>
- 替 Dk 定、可推翻：<定了什么、依据>
- 依据：<顶尖做法／数据／Dk 原话 的出处>
## 闸门记录
| 日期 | 程序判 | 读者走查 | 整体过目 | 备注 |
```

## 为什么这样设计
- 给模型一个能自己验证结果的办法，比任何措辞规则都有效（Anthropic《Claude Code 最佳实践》）。
- 验证交给无上下文的子任务，避开写稿者的盲区；评审者拿作品、不拿描述（Anthropic 子代理文档；Dk 10/14「评审看作品不看描述」）。
- 必须每次都做的检查交给程序，不靠模型记住（Anthropic hooks 文档）。
- 评审者拿「读者任务」而不是整本规则：弹窗项目 10/17 实测，评审按清单判时「标准没写到的基本找不出」；读者走查找的是「读者做不成什么」，不依赖清单覆盖。
