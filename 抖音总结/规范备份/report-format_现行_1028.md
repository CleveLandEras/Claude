# 汇报格式规范

Dk 看汇报是为了做判断、做动作。所以一份汇报好不好，只看一件事：Dk 读完第一屏，能不能知道结论、看到他要的内容本身、知道要他定什么。

Dk 的写作标准以 `/Users/decheng.huang/claude/弹窗标签推送系统/规则与交接/写作标准_合并版.md` 为参考（只维护这份 .md；Dk 10/9：「这个文件作为标准参考」，10/10 定稿）；本规范与它不一致时，以它的「现行说法」为准。

反面例子（2026-10-08）：Dk 说「带我过一遍 02 和 03 的验收」，Claude 交了一份「验收看哪几处」的清单，写着「开头全景」「第 17 件」「序号 1′」「K5 退路」。Dk 的反应是：「我没看到我要看的内容，你不知道怎么汇报吗？」他要的是 02、03 本身改了什么、为什么、结果怎样、要他定什么，不是一张去哪看的地图。

## 一、动笔前先想三件事

1. **Dk 看完要做什么？** 验收、拍板、回答问题，还是只是了解进度。结论就围着这件事写。
2. **他要的「内容」是什么？** 「带我过一遍 X」「讲讲 X」里，内容就是 X 讲了什么：改了什么、为什么、结果。不是 X 在哪、该看哪几处。
3. **哪些跟他的决定无关？** 删掉。Dk 说过「别太关心无关紧要的内容」。每段都要能回答：这段会改变他的哪个判断？

## 一点五、骨架：金字塔原理

整份汇报按金字塔原理搭，下面第二节的结构就是在这个骨架上展开的。动笔前先在心里（或草稿里）把金字塔搭出来，再写成文字。

**四条规则**

1. **结论先行**：最上面一句是整份汇报的中心结论，Dk 只读这一句也知道要点。先说结论再说理由，不按「背景 → 过程 → 发现 → 结论」的时间顺序讲。
2. **以上统下**：每一层都是下一层的概括。每个小节的标题，是这一节下面所有内容合起来能推出的那句话；下面的每一条都在支撑它。说不出概括句，就说明这一组还没想清楚。
3. **归类分组**：同一组里的论点属于同一类、彼此不重叠、合起来不遗漏（MECE）。首层和各节标题层的并列项不超过 5 条（写作标准）；更下层超过 7 条就再分一层。
4. **逻辑递进**：同一组按一种顺序排，并且选定了就不混用：
   - 时间顺序：第一步、第二步……
   - 结构顺序：按人群、按模块、按位置……
   - 重要性顺序：影响最大的排最前。

**怎么搭**

- **自上而下**（结论已经清楚时）：先写中心结论 → 问自己「Dk 读到这句会问什么」（为什么？怎么做？有什么依据？）→ 下一层就回答这个问题 → 一层层往下，直到数据。
- **自下而上**（手里是一堆材料时）：先列出所有要说的点 → 按同类分组 → 给每组写一句概括 → 再从这几句概括里提炼出中心结论。

**开头**：第一句就是中心结论；需要背景时，紧跟一两句交代 Dk 已知的情况和出了什么变化，不写成长段背景。

例：「第一批可以验收，第二批等你查两样东西，约 20 分钟。02、03 已过审查，第二批卡在标签和价格上。」

**自查**：遮住正文只看各级标题，能不能读出一条完整、连贯的论证？读不出，就回去改标题或分组。

## 二、结构（按这个顺序）

1. **标题就是结论**。写「02、03 可以验收：弹窗按人群拆开，没有人多弹」，不写「02、03 验收说明」。
2. **核心结论**：标题下一行副标题，再放几张要点卡（一般不超过 3 张），分别回答是什么、结果、要 Dk 做什么；有能直接说明结论的数字就放数字，没有就不硬凑。不写成多段文字的结论框。
3. **主体：观点 → 数据 → 观察**。
   - 每节小标题是一句观点，下面放支撑它的数据，最后是观察。观察里的推断要标明是推断。
   - 讲方案或改动时：
     - 先给**全景**，也就是改完以后整体长什么样，再讲每一项。只讲改动不讲全貌，Dk 会问「最终结构什么样、完整方案在哪」。
     - 每一项写四样：改什么、为什么（附数据）、结果、卡在哪。
     - **按读者的视角组织**。比如「选一类玩家，看他改前、改后看到什么」，不要逼人一格一格去对规则表。改前、改后并排放，变了的地方标出来。
   - 讲进度时：讲改了什么内容、发现了什么，不报轮数、次数、改了几处。每份结果写清给谁、做到哪、还差什么。
4. **要 Dk 定的事**（只有三类：业务方向取舍、验收、只有他能对外安排的事；我方流程、我自己的内容取舍、材料怎么准备，自己定，不挂给 Dk。Dk 10/14：「这些问题根本就不需要我回答，根本是可以自行解决的」。拿不准的可以另列「待 Dk 补」，每条写明我方判断和暂按的做法，推进不等他回复。Dk 10/15：「拿不准的让我补是没问题的，只是你自己也要有个判断，我如果补充了就多一些参考信息，如果我没补充也不影响推进才对」。弹窗标签推送系统项目以标准体系第〇节「什么事交给 Dk」为准），每件先给关键信息，再写四样。
   - **关键信息**（Dk 10/16：「现在最大的问题是，我信息不全无法做出决策，你也没给我提供相关的关键信息」）：现状怎么运作，用一个真实例子走一遍；原话证据（例如评审的原话放在 Dk 的判断旁边）；已经替 Dk 定了什么；每个选项落地后实际会改变什么。缺这些时 Dk 的回答只能算暂定。
   - 背景：为什么现在要定，不定会怎样；
   - 选项：写成封闭选项，每个写清具体做法；不单列利弊，代价只在影响决策时写（Dk 10/9 确认）；
   - 推荐：必须有，先自己想清楚答案，不平铺问题；
   - 理由。
5. **要 Dk 做的事或回答的问题**，每项写四样：卡在方案哪一处；答案不同，方案怎么变；不答会怎样；大概要花多久。
6. **我发现的问题**（有就写）：说清是什么问题、影响什么、建议怎么改。
7. **原文链接放最后**。汇报放精炼版，完整内容链接过去。完整文件也要尽量好读。

## 三、写法

- **专业、简洁、直接，不出现内部代号**（Dk 2026-10-08：「用词能不能专业点，看着像在给小学生解释，简洁直接就行了」）。用产品和运营通用术语，不刻意口语化、不做多余解释。简洁不等于缺信息：标题、定义、结论要能被直接转述（主语、动作、对象齐全，一句话说完整），不用名词罗列代替句子。任务号、退回号、约束号、工作表列号、「第 N 件」这类，Dk 不记，每出现一个就逼他去查一次。要提，就直接写出它说的那件事：
  - 不写「见 K5 退路」，写「群组不能用排除时，要先写一个『非新增、非回流』标签」；
  - 不写「第 17 件」，写「第一批留不留对照组」。
- **数字带分母和口径**。例如「6,366 人，占近一月活跃 62,292 人的 10.22%」。
- **事实和推断分开写**：事实只写已证实的；推断写明依据和边界，不写成事实；上界不当下界说。暂时确认不了的集中放一处，写成待求证的问题，不逐条贴「已证实／推断／待确认」标签。
- **说明消息来源可靠到哪一级**：子任务自称、判卷通过、我已核实。转述 agent 的自评之前先核实；没核实的就写「子任务自称」。
- **不写内部记录**：轮数、更正史、内部讨论。Dk 问到过程时另当别论：讲每一步实际做了什么、依据是什么（Dk 9/29：「我先看过程，每一步到底都做了什么，给我看实际推进的过程」）。
- **交付状态最多写到「待 Dk 验收」**。不写「可以直接交」「可原样转发」「可以上线」：Dk 验收是唯一出口，给不给别人由他决定。
- **呈现格式自己定，不问 Dk**。表格、对比、图，哪个好读就用哪个。
- **Dk 的话按它针对的情况理解**，不照字面、不外推、不收紧；回复先用一句话复述理解，再往下写（工作原则甲·0）。

## 三点五、版面：汇报不是文章

Dk 2026-10-10：「简报的文字几乎堆在一起，毫无结构性，很难阅读，每次汇报我都像在读一篇长文，这不能叫汇报。」

要解决的问题：文字堆在一起、看不出结构，读起来像文章。
- **不写成段落**。每一块先放一句结论，再放数字或短条目；条目尽量短（一两行为宜，是参考，不是上限）。
- **用版面表达结构**，形式按内容选。常用的：时间线用并排卡片，原因用并排卡片（标题＋一行说明＋一行例子），清单用标签，选项并排成卡片、推荐项加标记。
- **要 Dk 判断界面、页面或表格时，把截图或表本身放在页面上**，链接只用来给全文（10/16：判断页只有文字和链接，Dk：「没图吗？全是纯文字？这符合写作标准吗？」）。整页截图裁到要问的部分，或用框标出位置。
- **表格格子写短**，一格一件事；成句时主语、动作、对象写全（写作标准「句子成分完整」）；长说明放表外。
- 每节小标题是结论；节与节之间留大间距；全页没有大段文字。
- 对话里的摘要同样短：结论一句，其余分条。Dk 要求直接介绍、或内容本身是解释时，用平实的对话式文字（写作标准「协作与交付」）。

## 三点七、写到决策层，按场景套句式

来源：2026-10-28 Dk 让我从两份汇报主题的抖音内容里学汇报，他定的是把学到的做法写进本规范。这一节来自外部材料，**不是 Dk 的写作标准**，不得当作 Dk 的要求引用；和写作标准冲突时以写作标准为准。对照文件：`/Users/decheng.huang/claude/抖音总结/2026-10-28_我能学的汇报做法.html`。

**1. 每条发现都写到决策层，让 Dk 读完只需说好或不好。**

| 层级 | 写到什么 | Dk 读完还要做什么 |
|---|---|---|
| 事实层 | 做了什么、结果是什么 | 自己判断、自己想办法 |
| 分析层 | 再加上原因和关键因素 | 还得自己拿主意 |
| 决策层 | 再加上我的判断（不做会怎样，能估数就估）和建议，或我已经做了什么 | 说「好」或「不好」 |

- 我能定的直接定，写明「已替你定，可推翻」，不挂给 Dk（反例：10/14「这些问题根本就不需要我回答」）。
- 要 Dk 定的事照第二节第 4 条写全：关键信息、背景（不定会怎样）、选项、推荐、理由（反例：10/16「我信息不全无法做出决策」）。
- 交付时只写确定的话：查了什么、结论是什么；不写「有问题你指出来」，不把检查推回给 Dk。
- 例：字幕自动截取漏了 10:35–11:35（事实）；这一段换成横屏幻灯片，字幕位置变了（原因）；不补就少掉整章（判断）；已单独截取并补进总结（已做）。

**2. 按场景套句式。**

| 场景 | 句式 |
|---|---|
| 小事、小改动完成 | 结果 ＋ 做到哪 ＋ 在哪看 ＋ 要你做什么；对话里不超过 3 行 |
| 要 Dk 拍板 | 按第二节第 4 条写（关键信息、背景、选项、推荐、理由；代价只在影响决策时写），结尾加一句「你选了我马上做」 |
| 阶段或项目总结 | 结果 ＋ 数据 ＋ 不足与已做的补救 ＋ 亮点 ＋ 想听你意见的点 |
| 坏消息 | 出了什么问题 ＋ 原因 ＋ 我怎么补 ＋ 需要你什么；第一时间说，不等 Dk 自己发现 |

「3 行」只管小事、小改动的对话回复；附了简报文件的实质汇报，对话里的摘要按第四节写 3–5 行。

**3. 第一句先定基调**，让 Dk 一开头就知道这件事处在什么状态：
- 成果型：做完了，带来的价值是什么；
- 改进型：落地了，发现了什么问题，已经改了；
- 攻坚型：卡在哪里，已经做了什么，下一步做什么；
- 规划型：准备做什么，为了什么。

**4. 说什么、什么时候说。**
- **用 Dk 关心的语言**：先说对目标、进度、风险、要他投入什么的影响，再说具体做法。不写「改了版式」「删了 N 页」，写这件事给他的判断或会议带来什么变化。
- **少用「大概、可能、应该」**：查得清的查清，写查到的数；查不清的写成「如果…就…」，附上我暂按的做法。和第三节「事实和推断分开写」一起用。
- **按节点开口，不按时间播报**。只在四种时候主动汇报：出了结果；发现会改方向的风险；需要 Dk 的决定或资源；之前答不上的问题查清了。其余时间不播报进度。
- **讲工作只讲三件事**：替 Dk 做了哪些关键取舍；解决了什么难题；留下了什么能复用的东西。不列「做了 A、B、C、D」。

**5. 禁止项**（这些在外部材料里是为了说服上级争资源；Dk 要靠我给的信息做判断，Dk 9/29：「给的不准确还不如不给」）：
- 不因为结论不合适就换数据、换统计口径。口径固定、带分母；确实要换口径，写明为什么换。
- 不弱化、不省略已知短板。已知问题放在第一屏、写在亮点之前，并附上补救。
- 分析时不先定结论再找证据。先看证据再下结论；结论先行只用在表达上。

## 四、载体

- **一两句能答完的**：直接在对话里答，第一句就是结论。
- **只是向 Dk 要信息**：在对话里用 md 发（写作标准「协作与交付」）。
- **数据分析报告**：按写作标准「数据分析报告」交两份：对话里给全部结论句，不含数据表和推导；完整内容存成 markdown 文件，便于带到别的对话继续用（文档类型规则优先于通用标准）。
- **实质汇报**（验收、进度、方案）：
  - 写成 HTML 简报，样式照 `assets/brief_template.html`。
  - 放在项目约定的汇报目录。弹窗标签推送系统项目是 `简报/`，文件名 `YYYY-MM-DD_主题.html`。项目没有约定时，问一句放哪。
  - 写完在对话里给 3–5 行摘要和文件链接。摘要同样结论先行，不要把简报全文贴进对话。
- **你如果是子任务**：只把第二、三节的写法用在你本来就要写的文件上。不要新建简报文件，简报目录归主对话管。

## 五、交出去之前自查

逐条过一遍，有一条答「否」就改：

- 标题是一句结论吗？
- 只看各级标题，能读出完整的论证吗？每组论点同类、不重不漏、按一种顺序排了吗？
- 只读第一屏，能知道结论和要 Dk 做什么吗？
- Dk 要看的内容本身在页面上吗？还是只告诉了他去哪看？
- 页面上还有读起来像段落、看不出结构的大块文字吗？有就拆成卡片、短条目或短表。
- 正文里还有内部代号吗？
- 每个数字都有分母吗？推断都标了吗？
- 每个要定的事都有推荐吗？每个问题都写了「答案不同，方案怎么变」吗？
- 有没有混进内部记录（轮数、更正史、「已改 N 处」）？
- 有没有写「可以直接交 / 可以上线」？
- 每条发现都写到决策层了吗（有我的判断，以及建议或已做的）？有没有把我能定的事、该我做的检查推回给 Dk？
- 坏消息有没有写原因和补救？已知短板有没有写在前面？
- 有没有为了好看换数据或换口径？换了口径的，写明原因了吗？
- 对话回复用简体中文了吗？小事、小改动的回复在 3 行以内吗？附简报的摘要在 3–5 行以内吗？
