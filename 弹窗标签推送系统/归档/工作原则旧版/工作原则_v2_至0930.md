# 工作原则（v2，2026-09-29 Dk 确认生效）

所有角色（规划者、设计者、执行者、审查者）每轮开始前先读本文件。本文件由 Dk 确认，agent 不得修改。上一版（11 节）存档在 `归档/工作原则_v1_至0929.md`。

> 为什么改：上一版的目标有三把尺子（主管的交付、平台业绩、方案完成度），冲突时听谁的没写，结果是用最远的目标（业绩）把主管要的交付一件件论证掉了。本版把目标分成三层，写死冲突时的判断顺序。

## 一、目标分三层

| 层 | 是什么 | 用来做什么 |
|---|---|---|
| **近** | 这一步要交出去的东西。当前：① 02 弹窗方案稿通过 Dk 验收；② 03 配置单第一批通过 Dk 验收。**不设日期**（Dk 9/29：正常推进就行，给得快但不准还不如不给） | 定当下做什么。完成与否一眼能判断 |
| **中** | 主管这一期的三份交付（任务清单第一节、目标脑图）：弹窗方案与分人群配置单；标签需求；推送需求。每份都先经 Dk 验收，由 Dk 决定交给主管、运营、研发的时机 | 定范围。每项工作都要能说出推进了哪一份交付 |
| **远** | 平台业绩：活跃人数 × 付费率 × 客单价；活跃取决于新增、留存、回流 | 在范围内排优先级、在选项之间做取舍；发现范围外的更大机会，写成提案交主管 |

近目标由规划者写在推进计划第一行，完成后由 Dk 更新。**准确优先于速度**：交付内容没有做准之前不交，不为赶进度降低准确度。

## 一点五、Dk 验收是唯一出口

- **任何交付物、消息、取数请求，都只交给 Dk。** 只有 Dk 验收通过后，由 Dk 决定是否、何时交给主管、运营、研发或数据组。
- 所有文件里不写「可以直接交」「可原样转发」「可以上线」「可以发给数据组」这类绕过验收的话；状态只写到「待 Dk 验收」为止。
- 近目标的「完成」= Dk 验收通过。

## 二、冲突时的判断顺序

1. **先看近**：这项工作推进本期要交的东西吗？不推进的排在后面。
2. **再看中**：它在主管要的范围里吗？不在的不做，除非写成提案。
3. **最后看远**：同在范围内的几个做法，选对业绩贡献大的。
4. **远目标认为中目标有问题时**（例如数据显示主线应转向高卡）：写成「提案」，在交付物里单列一节，附依据、代价和选项，交主管定。**主管定之前，主管要的交付照常做完**，不得以提案为由删减、降级或推迟主管要的内容。

## 三、每项工作开工前回答三句

- 推进的是哪一份近交付？
- 属于中目标的哪一项？
- 对业绩有什么影响（能量化就量化，估不出就写估不出）？

前两句答不出，就不做、不问。数据考证（账号性质、字段含义、口径细节）只在会改变交付内容时才做，做到够用为止。

## 四、产出

- **交付物**（02–09，给主管、运营、研发、数据组）是决定之后要执行的东西；近目标的完成以交付物为准。
- **决策汇报**（`决策汇报.html`）用来让 Dk 直接判断：Dk 读完能直接定；Dk 需要向上汇报的部分写成可以直接用的文字，由 Dk 决定用不用、怎么用。
- 逻辑链每一环都有完整文件（`环节1_现状盘点.html`、`环节2_问题诊断.html`、`环节3_方案.html`），汇报放精炼版并链接完整文件；两边结论必须同步。完整文件开头一屏写完关键发现，标题写结论，数字带分母，事实标来源，口径说明放最后，样式一致（含深色模式）。
- 汇报讲内容不讲次数：说清改了什么、发现了什么、让哪份交付更近了。

## 五、推进方式

- 逻辑链：现状 → 问题诊断（含证据）→ 方案 → 决策点。弹窗、标签、推送三条线一起走。
- **每一环开工先做「问题空间扫描」**：沿中目标的三份交付和业绩驱动树，列出所有可能的问题或原因，不管原有文件里有没有；逐列扫一遍数据，写明没用的字段为什么不用。审查者检查「清单有没有漏」，不只检查「清单里的项做对了没有」。
- 各环完成标准：

| 环节 | 做透的标准 |
|---|---|
| 现状 | 配置、用户结构、实际表现（曝光、转化、留存、付费）都有描述；数字写明分母、口径和出处；拿不到的列为缺口，写清影响哪条结论、由谁来补 |
| 问题诊断 | 每个问题或机会写清：现象、根因、证据强度、已排除的其他解释、对业绩的影响量级（落到业绩驱动树哪一项）；问题和机会一起找；在范围内按对业绩的影响排序 |
| 证据 | 每条结论标明已证实、推断或待确认；关键结论有数据支撑、做过反例检查；推断不写成事实 |
| 方案 | **在主管要的范围内**按业绩贡献选方案；每个方案写清：作用于驱动树哪一项、预期影响量级及推算过程（估不出写原因）、至少一个备选及取舍理由、实现方式与成本（受「短期 = 现有功能迭代」约束）、风险、上线后怎么评估（主指标用业绩类，体验类作护栏）。范围外的更大机会按第二节第 4 条写成提案 |
| 决策点 | 列出需要判断的点，分 Dk 能定、主管定；每点写背景、选项、利弊、推荐及理由；按「近交付要用到的先定」排序 |

- 按环节推进：推进计划第一行写当前环节；只做当前环节的工作，后面环节冻结。当前环节每条标准都满足时，规划者申请过闸并逐条给证据，审查者自己去文件里核，写「闸门审核：通过」或「不通过，缺什么」。**核心标准所需的数据缺失时，不能只凭「已写成缺口」放行**，见第六节。
- 发现前面某环不扎实或不成立，就回头：规划者在推进计划「回溯记录」写明矛盾、退回哪一环、重做什么；方向要变的写进「方向变更」并在决策汇报如实体现。不为维持已有文件的样子回避回头。
- 分工：规划者定做什么（队列项标「需设计」或「直接做」）；设计者定怎么证明（设计卡：要回答的问题、为什么重要、假设与其他解释、方法、判读规则、结论边界、已知陷阱、交付位置）；执行者照卡做，结论不越过边界；审查者对照检查。申请过闸前先把当前环节的完整文件整合成一篇完整的论证。

## 六、数据与证据

- 事实来源：盘点、任务清单第四节答复登记、`数据/` 原始数据，以及基于它们的分析。能用数据回答的先分析，脚本放 `_scripts/`，结果写进 `分析/`，写明方法、口径、分母、局限。
- **核心数据缺失时，先把取数请求和问句准备好交 Dk 发出；答复到之前，不用代理指标去做依赖该数据的精细分析**，只做不依赖它的部分。
- 拿不到的信息不假装有：写明缺口、影响哪条结论、由谁来补。
- 用户的答复按字面、按它针对的对象理解；会推翻方向的答复，先向 Dk 复述确认再登记。

## 七、防止偏离

- 每处改动分类：实质推进（新发现，或让结论更站得住）、纠错、口径细化、同步或表述。审查者每次统计占比；「实质 + 纠错」低于一半，或出现不属于当前环节的改动，就写「⚠ 偏离警报」及原因，规划者下一轮必须先回应。
- **范围检查**：出现以远目标为由删减、降级、推迟主管要的交付的改动，审查者按第二节第 4 条退回。
- 没有实质工作时往深处挖（换切分维度、做反例检查、拆根因）；确实都卡在外部输入上，就停下，在进展日志写明在等什么。不设「不能停」，深度优先于速度。不拿形式打磨冒充推进。
- 每一轮在「进展日志.md」追加一行大白话：时间｜谁｜环节｜做了什么｜为什么（推进哪份交付、哪条标准）｜结果或发现。

## 八、约束

- 短期 = 现有功能迭代：优先用配置解决，需要开发的单列并说明理由。
- 不使用、不传播任何个人身份或联系方式信息。
- agent 不对外发送任何消息；要发的消息写好原话交 Dk。
- 文件存放按根目录「先看这里.md」：根目录只放 Dk 直接打开的文件；链接用相对路径；过时文件移到 `归档/`，不删。
