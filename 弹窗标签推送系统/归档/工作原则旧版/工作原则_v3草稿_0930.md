# 工作原则 v3（草稿，待 Dk 确认后替换现行 v2）

> 改动说明（相对 v2）：① 中目标拆成**方案线**和**能力线**，各有各的逻辑链和衡量尺子（Dk 9/30：定方案是短期的、要数据验证迭代；改能力是长期有效的）；② 每条约束写明适用范围，「短期 = 现有功能迭代」只约束方案线；③ 事实要准、方案是待验证的假设，两者分开；④ 原则或前提改动后，先清点旧结论再排队列。标【新】的是本版新增或改变的规则。

所有角色每轮开始前先读本文件。本文件由 Dk 确认，agent 不得修改。旧版存档在 `归档/`。

## 一、目标分三层

| 层 | 是什么 | 用来做什么 |
|---|---|---|
| **近** | 这一步要交给 Dk 验收的东西。当前：① 02 弹窗方案稿；② 03 配置单第一批。不设日期，准确优先于速度 | 定当下做什么 |
| **中** | 主管这一期的交付，分两条线【新】：<br>**方案线**（短期，上线后靠数据验证、迭代）：02 弹窗分人群方案、03 配置单，以及验证它们用的 08 效果评估、09 上线前基线取数。<br>**能力线**（长期有效）：04 弹窗功能缺口需求、05 标签需求、07 推送需求，以及数据能力（弹窗曝光与点击、分组实验、月储值等取数） | 定范围 |
| **远** | 平台业绩：活跃人数 × 付费率 × 客单价；活跃取决于新增、留存、回流 | 方案线内排优先级、在选项间取舍；发现范围外的更大机会，写成提案。**不用来衡量能力线**【新】 |

## 一点五、Dk 验收是唯一出口

- 任何交付物、消息、取数请求，都只交给 Dk。Dk 验收通过后，由 Dk 决定是否、何时交给主管、运营、研发或数据组。
- 文件里不写「可以直接交」「可原样转发」「可以上线」「可以发给数据组」；状态最多写到「待 Dk 验收」，并写清验收时要看哪几处。
- 近目标完成 = Dk 验收通过。

## 二、冲突时的判断顺序

1. 先看近：推进本期要验收的东西吗？
2. 再看中：在主管要的范围里吗？属于方案线还是能力线？
3. 最后看远：只在方案线内、同在范围内的几个做法之间取舍。
4. 远目标认为中目标有问题时，写成「提案」单列一节，附依据、代价、选项；主管定之前照常做完主管要的交付，不得以提案为由删减、降级或推迟。

## 三、每项工作开工前回答三句

- 推进哪一份近交付？
- 属于中目标的哪条线、哪一项？
- 方案线：对业绩的影响是什么、上线后怎么验证？能力线：它解开哪些方案、哪些运营动作、哪些验证？【新】

前两句答不出就不做、不问。

## 四、按事情的性质选尺子【新】

| 事情 | 什么叫做对 | 不能用的尺子 |
|---|---|---|
| **事实与分析**（数字、口径、现状） | 准：有出处、有分母、复算一致，推断标成推断 | — |
| **方案**（02、03 这类配置） | 是一个可上线的第一版，并且写清验证计划：看什么指标、结果怎么判读、下一版怎么改。方案是待验证的假设，它准不准由上线后的数据决定 | 不要求上线前一次论证到位；不用代理指标反复打磨细节 |
| **能力**（04、05、07、数据能力） | 说清它卡住了哪些方案、运营动作和验证，需求写到研发能直接评估 | 不用短期业绩量级衡量；「现在测不出效果」是需要数据和实验能力的理由，不是推后它的理由 |

## 五、推进方式

- **每条线开工先做「问题空间扫描」**：方案线沿业绩驱动树、能力线沿「运营想做而做不到的事」列全，不管原有文件里有没有；逐列扫一遍数据，写明没用的字段为什么不用。审查者检查清单有没有漏。
- **方案线的逻辑链**：现状 → 问题诊断（含证据）→ 方案第一版 → 验证计划 → 决策点。
- **能力线的逻辑链**【新】：现有能力（有 / 没有 / 未知，附出处）→ 缺口卡住了什么（哪些方案、运营动作、效果验证做不了或做得慢）→ 需求（功能、字段、口径、验收标准）→ 优先级（按解开多少、是不是方案验证的前提、成本）→ 决策点。能用配置绕开的，写明绕法和代价，但「能绕开」不等于「不需要这项能力」。
- 各环完成标准：

| 环节 | 方案线做透的标准 | 能力线做透的标准 |
|---|---|---|
| 现状 | 配置、用户结构、实际表现有描述；数字有分母、口径、出处；缺口写清影响哪条结论、谁来补 | 每项能力写明有、没有还是未知，附出处（截图、盘点、答复） |
| 诊断 / 缺口 | 每个问题或机会写清现象、根因、证据强度、已排除的其他解释、对业绩的影响量级；范围内按业绩排序 | 每个缺口写清卡住了哪些方案、运营动作、效果验证，现在怎么绕、绕的代价 |
| 证据 | 已证实 / 推断 / 待确认；关键结论做过反例检查；推断不写成事实 | 同左 |
| 方案 / 需求 | 在主管范围内给出可上线的第一版：作用于驱动树哪一项、实现方式（配置优先）、风险、备选；写清验证计划（主指标、护栏、判读规则、对照怎么设、下一版怎么改） | 需求写到研发能直接评估：功能、字段、口径、验收标准；优先级和理由；不确定的能力写进前置条件，由研发确认 |
| 决策点 | 分 Dk 定、主管定；每点写背景、选项、利弊、推荐 | 同左 |

- 按环节推进：推进计划第一行写近目标和当前环节。过闸由规划者申请、审查者自己去文件里逐条核。核心标准所需的数据缺失时，不能只凭「已写成缺口」放行。
- 发现前面某环不扎实就回头，写进回溯记录；方向要变的写进「方向变更」。
- 分工：规划者定做什么；设计者定怎么证明（设计卡）；执行者照卡做；审查者对照检查。申请过闸前先整合成完整的论证。
- **原则或前提改动之后，规划者先做「旧结论清点」**【新】：列出在旧原则、旧前提下得出的结论、决策项、分析，逐条标「仍成立 / 要改写 / 作废」，再排队列。

## 六、数据与证据

- 事实来源：盘点、答复登记、`数据/` 原始数据及基于它们的分析。能用数据回答的先分析，写明方法、口径、分母、局限。
- 核心数据缺失时，先把取数请求和问句准备好交 Dk；答复到之前，不用代理指标做依赖该数据的精细分析。
- 拿不到的信息不假装有：写明缺口、影响哪条结论、由谁来补。
- 用户的答复按字面、按它针对的对象理解；会推翻方向的答复，先向 Dk 复述确认。

## 七、防止偏离

- 每处改动分类：实质推进、纠错、口径细化、同步或表述；「实质 + 纠错」低于一半，或出现不属于当前环节的改动，审查者发「⚠ 偏离警报」，规划者下一轮先回应。
- 范围检查：以远目标为由删减、降级、推迟主管要的交付，审查者退回。
- **尺子检查**【新】：用短期业绩或「测不出」否定能力线需求的，用代理指标反复打磨方案细节的，审查者退回。
- 没有实质工作时往深处挖；确实都卡在外部输入上，就停下写明在等什么。深度优先于速度，不拿形式打磨冒充推进。
- 每一轮在进展日志追加一行大白话：时间｜谁｜环节｜做了什么｜为什么（推进哪份交付、哪条标准）｜结果或发现。
