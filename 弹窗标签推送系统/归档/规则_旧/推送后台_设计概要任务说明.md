## 一、这份文件是什么
- 给团队自己人看的设计概要：传达核心内容，也包括重要的设计细节，但不含给研发的冗长要求与说明。需求评审用它。
- Dk 原话：「像推送系统后台集成这样一个大需求，策划案各种内容肯定是很多，但那些是给程序给开发看的，我们现在最需要的是一个给自己人看的东西，传达出去核心的内容，但也包括很多细节上的设计，只是没有那些冗长的细致要求和说明」。
- 参照的做法：游戏业的「一页设计」（Stone Librande，EA／Maxis：一张带标注的图讲清一个系统，长文档没人读）；国内常见的系统策划案「概要设计」（给团队对齐与评审，详细设计给程序）；Basecamp Shape Up 的提案（问题、方案草图、风险点、不做的）；Google 设计文档（背景与范围、目标与非目标、方案总览、关键设计与取舍、备选）。
- 要建、按「统一入口」建，都已定；本文件不论证要不要做；已定的事不写成建议、推荐或待选项；不出现「请评审定」这类对话用语。
- 形式：16:9 pptx，`推送系统后台集成需求/5_设计概要.pptx`，生成脚本 `_scripts/an_推送后台_设计概要.py`。正文约 12–15 页，10 分钟读完；附录单独成节、可折叠。

## 一·五、10/14 补：按现在（2025–2026）的做法调整
主流是「一页纸＋原型＋行为规格」三件配合（Anthropic 官方博客：先写规格、用 Claude Code 做出原型、以原型为准；Uber：问题模糊或需对齐时原型先行；2026 常见：约 500 字一页纸写问题、目标、关键决定与怎样算做好，交互靠原型，书面规格只写行为、边界与验收；游戏业：每个系统一张单页，运营型游戏每个活动一张单页，完整设计文档作生产参考）。因此：第 2–3 页合起来就是一页纸（总图＋背景、目标、范围、关键决定、怎样算做好，文字约 500 字）；模块页以原型为主，关键规则作为编号标注放在截图上（规则＋一句为什么），不另列表格。Dk：「你说的业界那是很多年前了，我想知道现在的情况」。

## 二、粒度：写什么、不写什么
- 写（设计层）：影响运营怎么用、玩家收到什么、数据怎么算的规则与取舍——默认值、边界、关键取舍，每条一句为什么。
- 不写（实现层，留在 `4_需求文档.md`）：字段类型与程序命名、接口、错误码、全部异常分支、完整状态表、权限矩阵细项、每个下拉的全部可选值。
- 判断方法：去掉这条，团队对系统怎么运作的理解会不会变？会变就写，不会变就不写。

## 三、内容大纲
1. 封面：推送统一后台 · 设计概要。
2. 一页总图（最重要的一页）：一张图画出整个后台——左侧侧栏的页面结构（游戏外推送：推播、短信、Facebook、LINE；游戏内推送：弹窗、快显；频率上限、数据看板、玩家查询、操作纪录），中间一条推送从配置到看数据的路径（内容 → 对象 → 时间 → 发送前拦截 → 发送 → 回执、曝光、点击 → 数据），关键规则以短标注挂在图上。只看这一页要能懂八成。
3. 背景、目标与范围（一页）：现状四个问题各一行（带数字）；要做到的四项能力；本期做／不做（不做：会员标签设定的改动、多步自动化流程、A/B 测试、审批、埋点）。
4. 运营要做的事（1–2 页）：5–7 个核心场景，每个一行流程，配原型缩略图（经过哪几页、每步做什么）。
5. 各模块的关键设计（约 7–8 页，每页一个模块）：一张原型图（只截关键区域）＋ 3–6 条关键规则，每条「规则：为什么」。模块：新建推送（内容、对象、时间、确认）；按行为推送；频率上限与勿扰；失败与重试；数据看板与指标统计方法；玩家查询与操作纪录；弹窗；快显与短信、Facebook、LINE 的差异；迁移与切换。
6. 关键决定与为什么（一页）：一行一条，取自方案设计的 11 条决定；被否掉的做法只在理由里一句带过，不列选项。
7. 依赖与未定（一页）：需要营销侧、客户端、数据平台做的事；文档中仍为假设值、待研发评审确认的几项（列名称与当前取值）。
8. 怎么判断做成了（一页）：四项能力的验收标准与观察时间。
9. 附录：链接到原型、需求文档、逐条需求表；术语表。
