- 判卷：`分析/标准判卷/玩家查询与操作纪录_夜间判卷.md`（客服主管兼运营视角，总判「基本够用」）
- 结论先行：
  1. **最大缺口：发送时「不在受众内」的人不留任何记录**。客服最常问的「我为什么没收到 ID 42」，若原因是当时不在群组、被 VIP 名单排除、按行为条件不成立、当时不可触达，现在只看到一片空白；「所属群组」也只是当前名单。补法：每条推送按人留「判定链」30 天（与逐人发送明细合为一张表，不在群组的人按群组进出纪录现算、不存）；玩家查询可按推送名称、日期、推送方式找到推送再看判定，不要求客服知道 ID。
  2. **弹窗只记曝光，不记没弹的项和原因**。「我怎么没看到回流任务」答不了；8 步判断里优先级让出、冷却、次数已满、被截断，以及「已下发但客户端没显示」，原型页 15 都没有字段承载。补法：每次弹窗请求留逐项判定 14 天，结果加「已下发·未回报曝光」；页 14 加按规则汇总的「未弹出原因」与改动前后对比，定位曝光骤降。
  3. **回滚只有弹窗规则有**。页 14 有「恢复此版本设置」，推送、频率上限与勿扰、标签群组都没有；误改后只能凭操作纪录手抄回去。补法：统一「恢复此版本」，恢复即生成新版本并记一条操作纪录。
  4. **迁移期查无记录会被误判**。短信、Facebook、LINE 切换前由营销侧发送，礼包推播切换前由礼包后台发送，这些在本后台没有记录；页面按各推送方式的切换时间提示「当时由哪方发送、到哪里查」。
  5. 其余：可触达加设备、令牌、退订与手机号变更历史；客服可对单个玩家「弹窗减量」或记一笔客诉，直接生效、自动到期、记入操作纪录，不经审批；操作纪录补标签群组、测试发送、导出、查看玩家、客服处置；加客服角色。

## 二、对标：成熟平台都把「按人看判定结果」和「可回退的版本」做成一等功能

| 平台·功能 | 做法 | 本后台对应 | 差距 |
|---|---|---|---|
| Braze · User Profile（[文档](https://www.braze.com/docs/user_guide/audience/manage_audience/user_profiles)） | 按外部 ID、邮箱、手机号、推送令牌查人；Engagement 页签列各渠道订阅状态、每台设备的推送令牌，并有 **push changelog**：令牌失效、注册错误、令牌转移到别的用户；另有 Segments 页签列当前所在分群、Messaging History 列收到的消息 | 页 15 能否收到、所属群组、收到记录 | 缺设备与令牌明细、订阅状态变更历史 |
| Braze · Message Activity Log（[文档](https://www.braze.com/docs/user_guide/administrative/app_settings/message_activity_log_tab/)）、Messaging Observability（[文档](https://www.braze.com/docs/user_guide/analytics/dashboards/dashboard_builder/messaging_observability)） | 记录发送错误与中止（aborted）消息及原因；Observability 给出未发出的压制原因，如「无有效推送令牌」「用户订阅状态不允许」 | 页 15 未送达原因；页 12 拦下与未送达原因 | 本后台把「发送前不可触达」只做汇总、不按人逐条留 |
| Braze · 活动变更日志（Campaign changelog，见 [Banner 报表文档](https://www.braze.com/docs/user_guide/channels/banners/reporting)、[邮件 FAQ](https://www.braze.com/docs/user_guide/message_building_by_channel/email/faq/)） | 记名称、排程、受众、内容、权限的每次修改及修改人、时间；FAQ 建议排查重复或异常发送时先看变更日志 | 页 16 | 相当；Braze 也没有一键回滚，靠复制 |
| OneSignal · Subscriptions（[文档](https://documentation.onesignal.com/docs/en/subscriptions)）、Push message reports（[文档](https://documentation.onesignal.com/docs/notification-delivery)） | 一个用户多个订阅（每台设备、每个渠道一条），各有 Subscribed／Unsubscribed／Never Subscribed 状态及原因码（如 -2＝主动退订）；单条消息的 **Audience Activity** 按订阅列出是否送达、点击，并区分「发送时已不可触达」与「投递错误」；文档明确提示「订阅状态列是当前状态，可能与发送时不同」 | 页 13 导出逐人明细；页 15 能否收到 | 缺「单条消息按人查」；缺发送时状态与当前状态的区分 |
| CleverTap · User Profiles（[文档](https://docs.clevertap.com/docs/user-profiles)）、Debugger（[文档](https://docs.clevertap.com/docs/debugger)） | 档案页有活动时间线；Debugger 的 Reachability 区逐渠道写可达／不可达；「Reachable By」事件记下令牌、手机号变化导致的可达性变化；发送失败区分 User not reachable（设备不可达）与 Profile not reachable（档案不可达，如 iOS 关通知） | 页 15 能否收到 | 缺可达性变化的时间线 |
| Firebase Remote Config · 版本与回滚（[文档](https://firebase.google.com/docs/remote-config/templates)） | 每次发布生成版本，记版本号、时间、修改人、来源；回滚＝把旧版本复制为新版本发布（从 v10 回滚到 v6 生成 v11），版本记 rollbackSource；保留最多 300 个版本 | 页 14「恢复此版本设置（存为新版本）」 | 做法一致，但本后台只有弹窗规则有；推送、上限与勿扰、标签群组没有 |

对标结论：

- **按人判定留痕**是推送平台排查的基础（Braze 的 aborted／压制原因、OneSignal 的 Audience Activity、CleverTap 的 not reachable 两分），本后台只做了「发出后」的一半。
- **设备级可触达与变更历史**三家都有；本后台只有一句当前状态。
- **回滚即「复制旧版本为新版本」**是通行做法，本后台弹窗规则已采用，推广到其他对象成本低。
- 游戏内弹窗的逐项判定没有现成对标（三家的 In-app 都是单条消息）；本后台的大厅弹窗一次取多项、有优先级、互斥和额度，逐项留原因是自身需要，依据弹窗配置 5.4。

### 4.10 存储估算：判卷后约 1,230 万行，压缩后合计约 1 GB

假设沿用判卷：全部玩家 7.4 万；日均 15 条推送，其中 3 条全部玩家、12 条按群组（平均 1.5 万人）；弹窗日活 3 万、每人每天进大厅 5 次。均为估算，研发按实际量复核。

| 数据 | 原设计 | 改后 | 30 天行数 | 体积（列式压缩后） |
|---|---|---|---|---|
| 推送判定链 | 每条推送排除前全部候选人一行，另有逐人发送明细一张 | 合为一张；按群组发的只存群组内的人；按行为每次触发一行（估每天 1 万） | 原约 3,300 万 → 改后约 (3 × 7.4 万＋12 × 1.5 万＋1 万) × 30 ≈ 1,230 万 | 每行约 200 字节，原始约 2.5 GB，压缩后约 0.4–0.8 GB |
| 群组进出纪录 | 已有 | 不变 | 估每天 2–5 万，30 天 ≤ 150 万 | < 0.1 GB |
| 弹窗逐项判定 | 一次请求主表一行＋逐项子表，30 天，约 3,600 万子表行 | 一次请求一行，只存未曝光项数组，14 天 | 每天 15 万 × 14 ≈ 210 万 | 每行约 400 字节，原始约 0.8 GB，压缩后约 0.2 GB |
| 规则未弹出原因计数 | 无 | 规则 × 原因 × 日 × 位置时机 × 平台 × 版本 | 估每天 2,000 行，1 年约 73 万 | 可忽略 |
| 客服处置与客诉 | 无 | 每次一行 | 估每天 < 100 | 可忽略 |

写入峰值仍在全部玩家推送的瞬时 7.4 万行，与原逐人发送明细相同，不新增峰值；查询按会员编号＋时间建索引。

### 5.3 统一「恢复此版本」（Q3）

**适用对象与规则**：

| 对象 | 能否恢复 | 恢复后 |
|---|---|---|
| 弹窗规则 | 能（原型已有） | 生成新版本；不变 |
| 运行中、已暂停的按行为推送 | 能 | 生成新版本，只对之后的触发生效；状态不变 |
| 已排程推送（含重复定时） | 能 | 回到编辑页并带入旧版本设置，须「重新确认排程」 |
| 发送中、已完成、已停止 | 不能 | 可复制旧版本为新草稿 |
| 频率上限与勿扰 | 能 | 按「修改上限与勿扰」的确认框走：列改前改后、每天约多（少）拦下、将被顺延的推送 |
| 标签群组 | 能 | 生成新版本条件；下次刷新（25 分钟内）生效；确认框写人数变化与引用它的规则、推送 |
| 发送方式、触发行为不同的旧版本 | 不能 | 原型规定这两项不可改，所以不会出现 |
| 模板、常用受众、活动（推送配置 5.1、5.3） | 能 | 生成新版本；已从模板创建的推送不受影响（复制关系）；活动改名随版本恢复，已关联的推送随之显示 |
| 消息类别规则、重要推送额外额度、短信费用设置（频控 5.1–5.7） | 能，随「频率上限」页整页恢复 | 同「频率上限与勿扰」一行 |
| 告警规则、报表订阅（数据能力 4.10、4.11） | 不做版本 | 只记操作纪录（改前改后），手动改回 |
| 迁入管理的切换开关 | 不适用 | 用迁入管理页的「切回」，是开关切换，不叫「恢复」，确认框与本表分开 |

**确认框字段**：

| 字段 | 例 |
|---|---|
| 标题 | 恢复「弹窗 13 活动类·回流」到版本 2 的设置？ |
| 差异 | 字段｜当前（版本 3）｜恢复后（版本 4，内容同版本 2）；例：弹窗排序 回流任务 第 1 → 第 7 |
| 影响 | 对之后的请求生效；版本 3 期间的数据仍按版本 3 统计 |
| 原因 | 必填，例「误改排序」 |
| 冲突 | 若打开确认框后有人改过该对象，提示「运营01 于 10/15 21:02 修改过，请重新查看差异」（引用乙1 的版本校验） |

**操作纪录**：记一条操作「恢复版本」，改动内容「版本 2 → 生成版本 4；原因：误改排序」，版本字段加「来源：恢复自版本 2」（同 Firebase 的 rollbackSource）。

### 5.5 弹窗规则「未弹出原因」与改动前后对比（Q19，页 14 新模块，归数据能力文档 4.5）

**归属**：本模块放在页 14 单条弹窗规则数据，与数据能力文档 4.5（页 14 增补：改动竖线、归档提示、客户端版本标红）属同一页；设计只写在本节，数据能力文档 4.5 并入时加一行「未弹出原因与改动前后对比，见玩家查询与操作纪录文档 5.5」，不在两处重复。

**解决什么**：规则曝光骤降时，同期改动常有好几项（群组口径、额度、排序、发版），只看改动清单只能猜；看本规则「没弹出的人次」按原因怎么变，变化最大的原因直接指向是哪类改动。

**区块一：按日分布**（单位：人次＝弹窗请求次数；每天一列，近 14 天，默认显示表格，可切换堆叠柱状图；改动竖线规则同数据能力文档 4.3；统计窗口未满的日期按数据能力文档 4.12 标记）

| 行 | 含义 |
|---|---|
| 大厅请求人次 | 本位置、本规则触发时机内的全部请求；整体进大厅变少时这一行下降 |
| 不在对象 | 不在规则对象群组内 |
| 被排除 | 在排除群组、固定排除或「规则 N 的对象」内 |
| 投放条件不符 | 平台、客户端版本、每日时段、每人总次数、关闭后冷却 |
| 实验对照组 | 按尾数分到对照组 |
| 优先级让出 | 同位置同弹窗类型（或同互斥组）由更高优先级规则弹出；附「让给谁」：规则 12 ×N、规则 14 ×N |
| 项目全部跳过 | 命中但各项都冷却、次数已满、不可购买或时机不符 |
| 额度截断 | 当日额度已满，本规则的项被截掉 |
| 客服减量 | 玩家处于弹窗减量 |
| 已下发·未显示 | 显示失败与未回报曝光合计；可展开按失败原因、客户端版本 |
| 有曝光 | 至少 1 项已曝光 |

各行加总等于「大厅请求人次」。

**区块二：改动前后对比**：选一次改动（点趋势图竖线、上表日期表头的改动标记，或从页 16「看原因变化 ▸」进入），默认比较改动当天之前 1 个完整日与之后 1 个完整日，可选 3 天或 7 天（按日均）；改动当天不计。

示例：规则 13 活动类·回流，选「10/14 18:20 群组 回流 修改」，比较 10/13 与 10/15：

| 原因 | 10/13（改前） | 10/15（改后） | 变化 |
|---|---|---|---|
| 大厅请求人次 | 98,400 | 97,900 | −500（−0.5%） |
| **不在对象** | 81,200 | 87,600 | **＋6,400** |
| 被排除 | 1,100 | 700 | −400 |
| 投放条件不符 | 900 | 600 | −300 |
| 优先级让出 | 3,200 | 2,100 | −1,100 |
| 项目全部跳过 | 2,600 | 1,500 | −1,100 |
| 额度截断 | 1,400 | 900 | −500 |
| 已下发·未显示 | 300 | 200 | −100 |
| 有曝光 | 7,700 | 4,300 | −3,400 |

表下自动写一句：「有曝光减少 3,400 人次；变化最大的是『不在对象』＋6,400，对应同期改动：群组 回流 修改（10/14 18:20）。额度截断、未显示均下降，大厅额度 6 → 5、App 3.8.2 发版不是主因。」

**对照提示**（固定规则，自动语句按此生成）：

| 增加最多的原因 | 指向的改动类型 |
|---|---|
| 大厅请求人次下降 | 整体进大厅减少，非配置问题 |
| 不在对象、被排除 | 群组口径、排除群组、规则对象改动 |
| 投放条件不符 | 本规则投放条件改动；客户端版本分布变化 |
| 优先级让出 | 同位置其他规则上架、优先级或互斥组改动 |
| 项目全部跳过 | 排序项、弹窗次数、冷却改动；活动或项目下架 |
| 额度截断 | 弹窗上限调低；同位置更高优先级规则多弹 |
| 已下发·未显示 | 客户端发版、资源上传问题 |

**数据来源**：服务端在每次判断时按「规则 × 原因 × 日 × 位置时机 × 平台 × 客户端版本」累加计数，不从逐项明细（只存 14 天）汇总；保留 1 年。

**推送是否也要**：游戏外推送已有数据能力文档的「拦下与未送达原因」；判定链存了第 2b 步以后的原因，第 2a 步现算不存，所以推送不做同样的按日分布，留待需要时再评估。

### 5.6 客服处置「弹窗太多」：弹窗减量与记录客诉（Q22）

**设计原则**：客服当场可做、立即生效，不经审批；用固定选项、只减不加、自动到期、全程留痕来控制风险，运营事后可查、可提前解除。

**弹窗减量**（玩家卡「客服处置 ▾」）：

| 选项 | 效果 | 不受影响的 |

| 减量（默认） | 大厅每次进入最多弹 1 个；该玩家当天大厅额度降为 2（全局额度更低时取全局） | 破产弹窗（破产时的救济礼包是功能入口）；勾「本条不受频率上限」的公告类；新手两项 |
| 暂停大厅弹窗 | 大厅活动类、储值类弹窗都不弹 | 同上 |

| 字段 | 规则 |
|---|---|
| 时长 | 7／14／30 天，默认 14 天；到期自动恢复，记「弹窗减量到期」 |
| 原因 | 必选：弹窗太多／内容引起不适／其他；可填客诉单号 |
| 同一玩家 | 同时只有一个处置；再次设置覆盖前一个，纪录保留两条 |
| 解除 | 设置人、运营可提前解除，填原因 |

参数（每次 1 个、当天 2 个、最长 30 天）为建议值，运营确认后可在后台改为固定值；客服不能自定义数值。

**游戏外推送嫌多**：推播、短信、LINE 不做单人减量，客服引导玩家关闭通知、回复退订或封锁；短信可由客服代为退订，可触达变更历史记来源「客服代退」。

**记录客诉**（玩家卡「客服处置 ▾」第二项）：不处置也可只记一笔。

| 字段 | 可选值 |
|---|---|
| 类型 | 弹窗太多／没收到／内容不当／收到不该收的／其他 |
| 关联推送或规则 | 选填，用 4.3 的选择器选 |
| 说明 | 选填，200 字内 |

**汇总给运营**：页 16 加「客服处置」子页签：处置中人数；近 30 天按客诉类型、按关联规则的计数（例「弹窗太多 42 次，其中关联规则 14 有 17 次」）；可筛单条记录。运营据此决定是否调额度或改规则，不需要客服另开工单。
