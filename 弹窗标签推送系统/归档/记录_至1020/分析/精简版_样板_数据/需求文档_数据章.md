## 4.1.9 数据

**为什么做**：产品计划要求推送「增加數據情況（發送量，到達率等）」。Dk 10/15：「后台集成数据是很明确要做的，但目前只有数据看板和操作界面有一些简陋的内容」，并问过「推送系统弹窗的数据在哪里看」，要求游戏版本更新后旧版本的弹窗数据仍然保留。现在推播报表没有到达数，推播点击要到 Firebase 查；短信数据在数据平台上查；Facebook、LINE、弹窗、快显在后台都看不到数据。

**做什么**：在推送统一后台给出六种推送方式的统一数据，共八页（原型页 15–22）：

- 概览：两层推送的关键数字与较上一周期的变化、按日趋势、按推送方式、五类人群对比、表现最好与最差。
- 游戏外推送数据：按人群看点击率，实验组与对照组并排；拦下与未送达原因；推送明细。
- 游戏内推送数据：按位置、按位次、改动前后对比、项目 × 五类人群、按规则、按客户端版本。
- 档期汇总：一个活动在各推送方式上的合计与去重覆盖人数。
- 触达与打扰：可触达人数的变化与原因；每人每天收到几条、多少人碰到上限。
- 告警：6 条告警规则、告警记录、发版登记。
- 单条推送数据：一条推送从受众到点击的漏斗，失败部分在这里重试；立即、定时推送另有预计与实际对照。
- 单条弹窗规则数据：一条弹窗规则的漏斗，七种拆分，各设置版本的数据分开保留、可并排比较。

**涉及端与分工**

| 端 | 做什么 | 依赖谁 |
|---|---|---|
| 客户端（iOS、Android、Web） | 推播收到、显示、点击时上报（iOS 收到由通知服务扩展上报）；弹窗、快显显示、点击、显示失败时上报，带规则 ID、规则版本号与客户端版本；从弹窗点进礼包、活动时带上规则 ID | iOS 上报到达需加通知服务扩展并发版 |
| 服务端（推送服务、弹窗服务） | 写逐人发送明细、逐次显示明细；接收服务商回执与客户端上报；拉取 LINE 与 FCM 的汇总数；每天 00:00 拍可触达快照；立即、定时推送在确认时与开始发送时各存一份人数快照；提供各页的查询与导出；每 15 分钟检测告警 | 各服务商回调；数据平台汇总表 |
| 数据平台 | 每 15 分钟出汇总表；回填发送后登录；把领取、购买记录关联到弹窗点击 | 礼包后台、各活动的记录加「来源弹窗规则」字段 |
| 后台前端 | 原型页 15–22 | 服务端查询接口 |
| 礼包后台、各活动 | 购买、领取记录加「来源弹窗规则」字段 | 客户端传规则 ID |

### 一、指标怎么算

游戏外推送和游戏内推送的数据来源不同，分开统计，两层不相加。

| 层 | 指标 | 怎么算 |
|---|---|---|
| 游戏外推送（推播、短信、Facebook、LINE） | 发送 | 服务商受理的条数。服务商未受理的（超时、当场拒绝）、已提交但服务商没有返回的（结果不明）、测试发送，都不计入 |
| | 到达 | 确认送达的条数，各推送方式的来源见下一节 |
| | 到达率 | 到达 ÷ 可确认发送。可确认发送不含收不到到达回传的发送（推播 iOS 旧版本、LINE 逐人发送），这部分条数在到达率旁单列 |
| | 点击、点击率 | 每条发送最多计 1 次点击；点击率 ＝ 点击 ÷ 发送。不用到达作分母，因为部分发送没有单条到达，各推送方式会不可比 |
| | 到达人数、覆盖人数 | 到达人数为至少一条确认到达的玩家；覆盖人数为至少被发送一条的玩家；都按玩家去重，跨推送方式也去重 |
| | 发送后登录 | 受理后 N 小时内登录游戏的人数 ÷ 发送人数，都按玩家去重。短信按它看效果（玩家多直接打开游戏、不点链接），推播、Facebook、LINE 只作参考 |
| | 发送后付费（只有跳转礼包或商城的推送） | 受理后 24 小时内有储值的人数与金额，不论是否经推送进入；只作参考 |
| 游戏内推送（弹窗、快显） | 曝光、曝光人数 | 客户端显示后上报的次数；服务端已返回、客户端没有上报的不计。曝光人数按玩家去重 |
| | 点击、点击率 | 每次曝光最多计 1 次点击；点击率 ＝ 点击 ÷ 曝光 |
| | 点击后领取、购买（只有弹窗规则） | 点击后 24 小时内、「来源弹窗规则」为该规则的领取、购买记录，写人数与次数，购买另写金额。只作参考，不进漏斗、不算转化率 |
| 触达与打扰 | 可触达人数 | 每天 00:00 快照中该推送方式状态为可发送的玩家数；分母全部玩家不含已注销、机器人、测试账号 |
| | 人均收到条数 | 当天全部已发送条数（含服务通知与不计入上限的）÷ 当天至少收到 1 条的玩家数；弹窗按曝光个数算 |
| | 达上限人数 | 当天计数达到该推送方式每人每天上限的玩家数 |
| 跨推送方式 | 合计 | 五种游戏外推送的到达、点击来源不同，合计行、人群行、活动行只给数量，不出合计到达率、合计点击率；比率只在同一推送方式内比较 |

### 二、各推送方式的到达从哪来

| 推送方式 | 到达从哪来 | 多久有数 | 统计窗口 |
|---|---|---|---|
| 推播 · Android | App 收到推播时回执（实现方式待评审确认，见第 9 章第 1 条） | 1 分钟内 | 发送后 5 天 |
| 推播 · iOS | App 的通知服务扩展在设备收到时上报；只有接入的新版本有，发给旧版本的记「未接入」 | 1 分钟内 | 发送后 5 天 |
| 短信 | 运营商回执经服务商回调；长短信全部分段送达才算到达 | 数分钟到数小时 | 发送后 5 天 |
| Facebook | Messenger 送达回调 | 回调到达即记 | 发送后 5 天 |
| LINE | 群组发送用窄播，次日按每次发送的请求 ID 取 LINE 统计的已送达人数（只有汇总、不逐人）；逐人发送没有单条到达 | 次日 | 发送后 14 天 |
| 弹窗、快显 | 曝光、点击由客户端实时上报 | 实时 | 无窗口 |

推播的点击由客户端上报。短信、Facebook、LINE 的点击取短链服务的跳转记录，过滤链接预览、安全扫描这类自动请求。

客户端上报推播事件时带逐人发送明细 ID、App 版本、事件（到达、显示、点击）和时间；推送服务按「明细 ID ＋ 事件」去重后写入逐人发送明细。

### 三、拿不到的数怎么写

拿不到的数一律写原因，不写 0、不估算，也不用上一步的数代替。

| 格子里写 | 什么时候用 |
|---|---|
| 待回执 N | 已受理，统计窗口未满，还没收到到达回传；窗口满后转「无回执」 |
| 无回执 N | 窗口已满仍没收到；不算失败，也不算到达 |
| 未接入 N | 能回传，但对象的客户端版本没有接入（如推播 iOS 旧版本、不带规则 ID 的旧客户端） |
| 该渠道不回传 | 渠道本身没有这一步的回传（如 LINE 逐人发送的到达） |
| 待汇总（预计 HH:mm） | 按日汇总的数还没出（如 LINE 窄播次日出数前） |
| 未收到上报 | 游戏内有返回，但该客户端版本没有任何上报 |
| 统计中 · 剩 N 小时 | 按时长统计的数还没满（发送后登录、发送后付费、点击后领取与购买） |
| 未发送 | 该格对应的人群、日期或活动没有发送，不写 0% |
| 样本不足 | 比较的一方发送（游戏内为曝光）少于门槛，不下结论 |

### 四、统计规则

| 项 | 规则 |
|---|---|
| 统计窗口 | 游戏外推送的到达、点击统计至发送后 5 天，LINE 14 天；窗口内数字还会增长，含窗口未满日期的数字标「窗口未满」 |
| 与对比期比较 | 对比期可选上一周期、上周同一天、不对比；选单日默认上周同一天，选多日默认上一周期。数量写增减百分比，比率写增减百分点。游戏外两期都只取发送后同样时长的数再比（同龄） |
| 切换前不比较 | 推播、短信、Facebook、LINE 逐种从原工具切换到本后台，切换前的数据不导入。对比期含某推送方式切换前的日期时，该推送方式写「不比较」 |
| 缺数 | 某天某推送方式的回传没到齐（按日汇总未回传、客户端回执明显少于服务商汇总）时标「缺数」，比率不含这一天。推播 Android 以客户端回执到达率比 FCM 汇总送达率低 3 个百分点以上（暂定）为准 |
| 日期归属 | 游戏外按服务商受理时刻所在的台湾自然日，之后几天的点击仍计入受理那一天；游戏内按服务端返回弹窗（快显为下发）时刻所在日 |
| 人群归属 | 五类人群（新增、回流、破产、潜在付费、潜在流失）按发送时（弹窗按请求时、快显按下发时）玩家所在的标签群组归属，写进明细，之后不回算。破产取标签「近 7 天发生过破产」。一人可同属多类，各行不相加 |
| 单位 | 拦下与未送达原因按人次计，按行为推送一人触发几次计几次；另列按玩家去重的人数。导出的名单按玩家去重 |
| 重复的定时 | 每一次按一次性推送统计；单条推送数据可选看第 N 次，各次一行 |
| 更新 | 每 15 分钟内更新一次，页面写「数据更新于 HH:mm」 |
| 保留 | 逐人发送明细、逐次显示明细保留 30 天，汇总、可触达快照、发送快照长期保留。查询范围超过 30 天时，按玩家去重的人数写「—」并注明超过明细保留期 |
| 不计入 | 测试发送、弹窗测试预览不计入任何数字；迁移期营销侧切换前已排程、仍在营销侧发出的推送不计入 |

### 五、看板各页的规则

| 项 | 规则 |
|---|---|
| 表现最好与最差 | 各推送方式内（游戏内按位置）与自身均值比；发送（游戏内为曝光）不少于 1,000 且发送已满 24 小时才参与。短信按发送后 24 小时登录占比排 |
| 任选标签群组并排 | 人群可改选任意标签群组（最多 5 个）并排，如同一实验的实验组、对照组。逐推送方式比点击率并写两组发送条数；另列整组的 1 日、7 日内登录占群组人数（不论是否收到推送，对照组不发时也能比）。差值做 95% 置信的两比例检验，写「差异显著」或「差异不显著」；任一组少于 1,000 写「样本不足」 |
| 按发送小时、按跳转类型、按客户端版本 | 游戏外推送数据里三块默认收起，标题行写一句摘要。按客户端版本：某版本发送不少于 100 条、到达回执为 0 而其他版本正常时，判「疑似该版本回执上报缺失」，不判通道故障 |
| 按位次 | 位次＝玩家这次进入该位置实际第几个显示，跨规则计，不是规则内的排序号 |
| 改动前后对比 | 选一次改动（规则改版、上限改动、发版），取改动前后各 1、3 或 7 个完整日的日均，改动当天不计；列位置整体、本次改动涉及的项目和频率上限拦下的变化。同期另有改动或发版时提示「不能单独归因，要归因用实验组与对照组」 |
| 项目 × 五类人群 | 每个弹窗项目在五类人群的点击率；每个位置默认列曝光最多的 4 项；曝光少于 500 写「样本不足」 |
| 档期汇总 | 一行一个活动：推送、快显、弹窗排序项按「所属活动」归入，没选的归「未归属活动」；各行发送、到达、点击、曝光相加等于概览合计；覆盖人数跨活动、跨两层都不相加。展开先按推送方式小计，再到每条 |
| 可触达人数 | 每天 00:00 快照，按推送方式列人数与较 30 天前；不可触达按原因列（未装 App、通知关闭、令牌失效、无手机号、号码无效、已退订、未绑定、未加好友、已封锁），写怎么知道的；令牌失效、号码无效、已封锁要发送后才知道。快照失败的日子写「未取得快照」，趋势断开 |
| 每人每天收到几条 | 按人、按台湾自然日；列人均收到条数、当天收到条数的分布、各推送方式的达上限人数与占比、上限拦下。短信、Facebook、LINE 上限 1 条、收到即达上限，不列占比 |

### 六、单条推送数据

| 项 | 规则 |
|---|---|
| 漏斗 | 游戏外推送：受众 → 发送 → 到达 → 点击，下面另列发送后登录。快显：受众 → 可触达 → 已下发 → 曝光 → 点击。每一步写比上一步少多少、少在哪 |
| 受众到发送之差 | 固定拆成发送前拦下、服务商未受理、结果不明、待提交四项，合计等于差额。发送前拦下按固定顺序判断，一人次只记第一个命中的原因 |
| 发送到到达之差 | 拆成受理后退回（只有短信和推播 Android 有来源）和未确认到达（待回执、无回执、未接入、该渠道不回传） |
| 重试失败部分 | 只重发超时等可重试的部分：系统先自动重试 3 次，结束后 24 小时内可手动重试。当场拒绝的（令牌失效、内容格式错误）不重试；结果不明的可能已送达，推播只允许手动重试一次。重发时同一人只计入每人每天上限一次，落在勿扰时段的顺延。重试记入操作纪录 |
| 停止的推送 | 发送数停在停止时的条数，回执在窗口内继续累加 |
| 设置版本与版本对比 | 每次修改生成一个版本；数据可按版本筛选。选两个版本并排，只比日均与比率 |
| 预计与实际对照（立即、定时） | 确认发送或确认排程时、开始发送时各存一份快照（群组批次号、各层人数）。逐层两列加差额；差额拆到群组名单变化、排除变化、可触达变化、频率上限、发送失败，相加等于预计与实际之差。拆法：先换群组人数，再依次换各层通过率（本层人数 ÷ 上一层人数），避免群组缩小被记成可触达改善。重复的定时每期对照上一期。按行为推送没有确认时快照，不显示 |
| 导出 | 每类原因的名单、逐人明细可导出（逐人明细保留 30 天）；只读角色只能导出汇总 |

### 七、单条弹窗规则数据

| 项 | 规则 |
|---|---|
| 漏斗 | 目标人数（统计期间内属于对象群组的玩家）→ 进入该弹窗位置 → 符合条件（至少一次请求返回了本规则的项目）→ 曝光 → 点击。人数按玩家去重；次数按请求、返回项目、显示、点击计。每一步写比上一步少在哪 |
| 生成版本 | 新增规则为版本 1，之后每次确认保存加 1；上架、下架、删除不生成版本。现有规则移入本后台时，以当时的设置为版本 1 |
| 数据归属 | 每次弹窗请求记下命中规则当时的版本号，曝光、点击按服务端返回时的版本统计 |
| 旧数据保留 | 改设置、游戏发版都不清除旧数据；每次曝光、点击另记客户端版本号。已下架、已删除（软删除）规则的数据照常可查 |
| 版本对比 | 选两个版本并排，各按自己的生效时段统计，只比日均和比率；另逐项列各版本中该项排第几、日均曝光和点击率，回答排序改了有没有效果 |
| 恢复旧版本 | 带入旧版本的设置，经保存确认后存为新版本，不改写旧版本 |
| 拆分 | 按日、按小时、按平台与设备、按客户端版本、按人群、实验组与对照组、按排序项（每个弹窗项目一行）。实验组与对照组默认对照同一位置、排除了本规则对象群组的那条规则，两组取同一时段，差值写是否显著 |
| 一次请求命中多条规则 | 各规则各自计入自己的漏斗 |
| 移入前的历史 | 移入本后台前的曝光、点击没有版本号和人数，按日只显示有记录的曝光、点击，其余写「—」，不回算 |

「为什么这位玩家没弹出」按人查，在玩家查询（4.2.3）的弹窗逐项结果里看，本模块不重复。

### 八、告警

| 规则 | 什么时候告警 | 样本够了才判断 | 适用 |
|---|---|---|---|
| 到达率低于同龄均值 | 发送后 2 小时、24 小时各查一次，比近 7 天同龄均值低 5 个百分点；LINE 窄播次日出数后判断 | 该批发送 ≥ 1,000；按行为推送每满 1,000 条查一次 | 推播（iOS 只算已接入版本）、短信、Facebook、LINE 窄播 |
| 服务商未受理占比高 | 按推送方式当天累计，未受理占提交超过 5%（不含令牌失效、号码无效） | 提交 ≥ 1,000 | 游戏外四种 |
| 回执中断 | 发送后 2 小时到达回执为 0；短信为无回执占比超过 50% | 发送 ≥ 500 | 推播、短信、Facebook |
| 新客户端版本曝光异常 | 新版本有弹窗请求但曝光为 0，或曝光人数占比低于请求占比的一半 | 该版本请求 ≥ 100 次 | 弹窗、快显 |
| 游戏内上报中断 | 请求、下发正常，但曝光、点击、显示失败的上报量比近 7 天同时段低一半以上；或某客户端版本返回项目不少于 100、上报为 0 | 该版本返回 ≥ 100 项 | 弹窗、快显 |
| 数据汇总停更 | 数据汇总超过 60 分钟没有更新；汇总停更时其余规则都不会触发，所以单独检测 | — | 全部 |

迁入项的 4 条告警（量级骤降、重复显示、开关读取失败、影子比对差异）随迁入管理一起做，规则写在 4.2.6。

- **检测与通知**：每 15 分钟检测一次。首次触发时，总览和概览顶部出现告警条，同时发邮件给收件人；条件持续时不重复通知；连续两次检测不再满足自动转「已恢复」；运营标「已处理」后 24 小时内再触发，重开原记录。
- **防误报**：某推送方式在本后台的数据不足 7 天时先不判断。阈值可改、可单条停用，改动记入操作纪录。
- **发版时间**：某平台首次收到新版本号的弹窗请求、且当天该版本请求不少于 100 次（排除测试包）时，自动记为发版时间；可手动修正，修正记入操作纪录。「新客户端版本曝光异常」、改动前后对比和趋势图的发版竖线都用它。

### 九、异常与边界

| 场景 | 处理 |
|---|---|
| 所选范围没有任何发送 | 关键数字和表格写「未发送」 |
| 对比期没有数据 | 「较上一周期」写「—」 |
| 表现最好与最差不够两条 | 只有 1 条时只写较均值；没有满足条件的写「所选日期内没有发送满 24 小时且不少于 1,000 的推送」 |
| 自定义日期超过 1 年 | 提示缩短范围 |
| 导出量大 | 导出为后台任务，完成后在页面右上提示下载；文件保留 7 天 |
| 群组被删除 | 并排比较里行名后写「（群组已删除，数据保留）」 |
| 「来源弹窗规则」字段上线前的记录 | 不回算，不计入点击后领取、购买 |

## 7.1.9 数据（验收）

1. 同一期间、同一推送方式，概览、游戏外推送数据、单条推送数据三处的发送、到达、点击一致；档期汇总各活动与「未归属活动」相加等于概览合计；受众与到达之差等于拦下与未送达各原因之和。
2. 推播发给 iOS 旧版本的条数单列「未接入」，不进到达率分母；窗口未满写「待回执」，满 5 天后转「无回执」；拿不到的数都不显示为 0。
3. 弹窗规则改排序后，版本对比和改动前后对比都能看到各项排第几与点击率的变化；旧版本的曝光、点击按版本可查；游戏发版后旧数据不变；已下架、已删除规则的数据可查。
4. 新客户端版本有弹窗请求、曝光为 0 时，下一次检测（15 分钟内）生成告警记录，总览和概览出告警条，收件人收到邮件；数据汇总停更超过 60 分钟同样告警。
5. 定时推送开始发送后，预计与实际对照的各项差额相加等于预计发出与实际发出之差。
6. 从弹窗点进礼包后 24 小时内购买，这笔计入该规则的「点击后购买」；测试发送、测试预览不计入任何数字。
