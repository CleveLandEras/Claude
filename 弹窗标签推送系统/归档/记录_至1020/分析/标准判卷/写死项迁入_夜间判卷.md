# 写死项迁入夜间稿判卷：骨架可执行，但试点选错、三项里只有礼包类能照现稿走通

判卷对象：`分析/内容补强_写死项迁入_夜间.md`（下称「作品」）。对照：`推送系统后台集成需求/4_需求文档.md` v0.9.5 的 4.1.6、4.2.1、4.2.4、4.2.6、第 9 章（grep 核对）。不改作品。

## 总判

| 问题 | 判断 |
|---|---|
| 能否执行 | 盘点、分批、验收、回退、删代码这套流程能落地；但三项走查里，通行证升级提示在现有快显上会「错位置、错文案、多弹、少弹」四处失真，新手挑战完成强制弹窗的时机语义对不上，大厅中奖播报按现设计（逐人下发、计入快显上限）不可行 |
| 会不会重弹、漏弹 | 作品抓住了「状态不继承」「在途发送」两类，但把重弹风险压在终身计数上判错了重点；真正的重弹口子是「按行为加时限」跨切换时刻（强制弹窗）和多设备；真正的漏弹口子是快显每人每天 3 次与播报类争额度、快显只有大厅顶部一个位置 |
| 基线方案 | 可行，成本中；但大半可省：事件型写死项（通行证升级、中奖播报、强制弹窗）用游戏服务端的事件日志即可当基线，客户端上报只留给「状态记在本地」的项 |
| 顺序与分批 | 试点选错：作品自己判通行证升级提示「能但失真」，又拿它当验证链路的试点，出问题分不清是链路还是维度；分批按「迁什么」排，没按「客户端发版」排，而客户端发版才是真正的批次单位 |
| 最缺的 | ① 客户端一次发版接齐全部清单项的开关；② 按行为加时限的规则须只认切换之后发生的行为；③ 播报类不走逐人快显通道，或至少不计每人上限＋全服节流＋聚合上报 |
| 过度 | 多设备重复比例 5% 门槛、80%–120% 折算验收带、趋势图虚线衔接、「7 天切回两次转下批」、按平台首切 Web |
| 依据过时 | 作品写于 v0.9.4 之后却没吸收它：弹窗已有「指定行为后」「每人总次数」「关闭后冷却」（4.2.1），快显中奖已有「中奖金额不低于 N」，快显已有「本条不受频率上限（不计入）」（4.1.6）。1.2 缺维度表六项里两项半已不缺 |

## 走查记录

### 一、通行证升级提示（作品定为第 0 批试点）

| 阶段 | 照作品与需求文档走 | 卡在哪 |
|---|---|---|
| 准备 | 客户端清单登记；快显页建 ID 32「按行为·通行证升级」，事件来源游戏服务端（需求文档 4.1.4 事件表） | ① **位置不符**：写死的是「游戏界面右上角横幅」，快显「显示位置」只有「大厅顶部横幅」（4.1.6、5.x 序号 3）。照建会在大厅顶部出、局内不出——这是漏弹，作品没发现<br>② 文案：没有「通行证等级」变量，且文案变量是可选功能，只能写固定文字<br>③ 对象：没有「等级 ≤ N」，全部等级都弹——多弹<br>④ 点击跳转只能选活动页面／礼包／大厅，写死的是不跳转，需确认能否留空 |
| 切换前检查 | 「内容与触发已核对」须与清单一致，勾选人照实勾不下去 | 四处不一致，按现规则通不过检查；要么先补位置、变量、阈值，要么业务负责人书面接受差异 |
| 双轨 | 事件型、无累计状态，切换本身不会重弹 | 原来由客户端本地收到升级结果就弹，迁入后走「游戏服务端事件 → 推送服务 → 长连接下发」，有延迟；连升多级时下发顺序与写死不同。可接受，但要在验收里写明 |
| 漏弹 | 快显每人每天 3 次，一天连升多级被截 | 作品把它记为「预期差额」来扣基线；其实快显已有「本条不受频率上限·不计入」（4.1.6），勾上即与写死时一致，不必算差额 |
| 灰度 | 需求文档只有全切／全不切 | 试点必须先有「仅测试账号」一档，否则第一次切就是全量新版本玩家 |
| 切换、验收 | 24 小时检查有曝光；7 天对照 | 基线可直接用游戏服务端「通行证升级」事件数（前 N 级）作上限，不需要客户端上报 |
| 回退 | 切回即恢复写死 | 可行 |
| 删写死代码 | 作品：连续 30 天未切回且新版本占比 ≥ 95% | 删代码只影响此后的新版本，旧版本照旧写死；占比与能否删无关，删的代价是新版本失去回退兜底。条件应改为「30 天稳定＋业务负责人确认放弃回退」 |

结论：作为试点不合格。要么先补位置、变量、阈值再试点，要么改用礼包推播（#6，4.2.2 已设计完、不依赖客户端发版）先验证切换事务与操作流程，再用一条与快显能力完全对得上的写死项验证长连接与旧版本兜底。

### 二、新手挑战完成后的强制弹窗

| 阶段 | 照作品与需求文档走 | 卡在哪 |
|---|---|---|
| 准备 | 建一条单独弹窗规则，触发时机「指定行为后」，行为「完成新手挑战」 | ① 行为：已知五种里没有「完成新手挑战」（是否算「完成任务」待客户端 19）；事件要由游戏服务端发出<br>② **时机语义不符**：「指定行为后」是「时限内下次进入大厅时弹」（4.2.1）；写死的「强制弹窗」大概率是完成当下立刻弹。迁入后变成延后弹，或玩家不回大厅就不弹<br>③ 「强制」：弹窗形式只有活动本身／活动广告页，没有不可关闭；弹窗每人每天上限可能截掉它，弹窗没有单条不受上限 |
| 双轨 | 作品把它列为「带终身频次、需继承状态」 | 判错重点：完成新手挑战一生只发生一次，事件型，切换前已完成的不会再触发，无需继承状态。**真正的重弹口子**：行为发生在切换前（新版本客户端当场弹了写死），切换后玩家在 72 小时时限内进大厅，服务端按「指定行为后」再弹一次。需规定「只认切换时刻之后发生的行为」 |
| 漏弹 | 切回时同理：服务端期间完成、尚未进大厅的玩家，切回后客户端写死只在完成当下弹，已错过 | 规模小，写入回退说明即可 |
| 与新手两项的关系 | 作品把 #1、#2 放第 2 批，#3 放第 3 批 | 三项可能共用客户端新手状态与代码；若共用，拆两批会出现「前两项服务端下发、强制弹窗仍写死」的混合态，需客户端先确认能否分开切 |
| 位置冲突 | 单独规则也在大厅位置，与规则 12 同位置 | 要给优先级与互斥组，否则可能挤掉新手挑战弹窗或被挤掉 |
| 灰度、验收 | 基线 | 游戏服务端「完成新手挑战」事件数即基线；验收看「完成后 N 小时内曝光人数 ÷ 完成人数」 |
| 删代码 | 同上 | 同上 |

结论：现阶段不能迁，作品放第 3 批对；但缺的不是作品说的「行为事件、终身频次」（已有），而是「行为当下立刻弹」的时机、「强制」的形式与不受上限、事件来源。

### 三、大厅中奖播报

| 阶段 | 照作品与需求文档走 | 卡在哪 |
|---|---|---|
| 准备 | 按行为快显「中奖，金额不低于 N」；对象按第 9 章运营 3 加「当时在线的全部玩家」 | 金额门槛已有（作品列为缺口，过时）；缺的是中奖者昵称、游戏名这类**事件主体变量**，现有变量都按接收者取值 |
| 漏弹（最大问题） | 运营 3 写「每次触发对在线玩家各显示 1 次、计入快显上限」 | 快显每人每天 3 次。中奖频繁时，在线玩家早早被播报占满 3 次，之后通行证升级提示与运营配置的快显全部被拦；反过来播报本身每人每天只能看 3 条，比写死时少得多。运营 3 的方向错了，播报类必须「不计入」，另设全服节流 |
| 负载与数据 | 研发 21 只给了「按玩家下发」「开关广播」接口 | 每次中奖按在线人数逐人下发，每人一条曝光明细（4.1.6 带显示明细 ID）；在线 3,800 人 × 每天播报条数，明细量级失控。需全服广播通道＋曝光按条聚合上报 |
| 双轨、灰度 | 无个人状态，切换不重弹 | 灰度按会员分组时，同一条中奖播报一半人由服务端、一半由写死显示，可接受 |
| 基线 | 游戏服务端达门槛的中奖次数 × 当时在线人数 | 不需客户端上报 |
| 另一条路 | — | 播报本质是社交证明跑马灯，不针对人、不由运营写内容，性质更接近已排除的「常驻入口」。可选：不建成快显推送，只把门槛、节流、文案模板、开关做成一个「播报设定」，曝光按条汇总。成本由大降到中小 |

结论：照现稿不可行；建议把「播报类怎么迁」作为单独决策交 Dk（作为快显迁入／作为播报设定迁入／本期不迁），而不是在第 3 批里默认「补维度后迁」。

## 新缺口

| 缺口 | 影响 | 补法 | 重要度 | 成本 |
|---|---|---|---|---|
| 快显只有「大厅顶部横幅」一个位置，写死横幅有局内右上角 | 通行证升级提示迁入后局内不显示，试点即漏弹 | 清单加「显示位置」字段；快显位置枚举按清单补，或位置对不上的项不进试点 | 高 | 中（客户端渲染位置） |
| 按行为加时限的规则跨切换时刻 | 切换前已当场弹过写死的玩家，切换后在时限内又被服务端弹一次 | 规定迁入项只认 `switchedAt` 之后发生的行为；切回同理 | 高 | 小 |
| 播报类计入快显每人每天 3 次 | 播报占满额度，挤掉其他快显；播报本身也被截 | 推翻运营 3 的「计入上限」；播报类固定「不计入」＋全服节流 | 高 | 小（规则）／中（节流） |
| 播报逐人下发、逐人明细 | 长连接与明细表负载失控 | 全服广播通道；曝光按条聚合上报 | 高 | 大 |
| 客户端发版才是批次单位，作品没写 | 按四批迁就要多次发版，周期拉长；或某批的开关代码不在已发布版本里 | 一次客户端发版接齐清单全部项的读开关（与上报），之后只在后台逐项切 | 高 | 小（计划） |
| 弹窗「强制」形式与「行为当下弹出」时机 | 强制弹窗变延后弹或不弹 | 弹窗加「行为发生时」时机与不可关闭形式，或认定此项本期不迁 | 中 | 中 |
| 新手三项是否共用客户端状态与代码 | 分批切出现混合态，状态错乱 | 问客户端；共用则三项同批切 | 中 | 小 |
| 事件主体变量（中奖者昵称、游戏名） | 播报建不出 | 文案变量区分「接收者」「事件主体」两类 | 中 | 中 |
| 删写死代码的条件用错了指标 | 以新版本占比判断能否删，实际删的是回退能力 | 改为「稳定 30 天＋业务负责人确认放弃回退」；旧版本靠强制更新另算 | 中 | 小 |
| 「灰度中」第三态与 4.2「只有两种状态」冲突未处理 | 并入时两处规则打架 | 写明迁入项开关例外，或灰度做成开关外的「生效范围」字段 | 低 | 小 |
