# 核心② 整体控制：结果（10/18）

**结论**：运营靠整体控制完成的 13 个任务，原来没有一个能完整走通（游戏外 8 项、游戏内 7 项都只能做一半，C4「一天破产三次」走不通）；现在 12 个能在原型上从头走到尾，C4 部分完成（剩一项要 Dk 定）。资深同行复评后两条甲级已清零（见第三节）。
**最大的变化**：从「每条推送各管各的」变成「一个人一天看得见、算得清」——玩家查询能看到每个上限子项还剩几个、今天接下来哪条会被截、下次进大厅会弹什么；同一活动跨推送方式由合并组保证一人只收一则；谁让谁的规则补齐并统一。
交付物：原型 `推送系统后台集成需求/3_原型.html`，需求文档 `4_需求文档.md` v0.9.43；验收用例增加到 T01–T579（新增 T522–T579）。

## 一、原来能做到什么，现在能做到什么

任务出处与定义见 `分析/标准判卷/推送后台_核心整体控制_1018/任务表.md`。

| 任务 | 原来 | 现在 |
|---|---|---|
| C1 一位潜在流失玩家今天的全部触达 | 事后能查已收；剩余名额只算一个总数（不含服务通知、重要预留、每周）；「下次进大厅弹什么」要在两页间对 29 项手推 | 玩家查询按两层各子项列今日计数；「今天接下来」列出今天还会发的推送与预计结果；「此刻预演」逐项写下次进大厅、下次破产会弹、跳过还是被截 |
| C2 大活动当天游戏外推送抢名额 | 只在新建那一条看得到被拦人数；同一分钟到点谁先没写；一周撞上限无处可看 | 截断顺序写全（重要预留 → 受理先后 → 同分钟重要先）；频率上限页有今天与未来 7 天名额占用；列表有「重要」「预计被上限拦下」，后建的推送会让已排推送的估算重算 |
| C3 大活动当天弹窗抢位 | 上架前只看到重叠人数，看不到会多截掉哪些项 | 保存确认框给名额截断影响：每天多截几项、被截最多的项、首储与破产礼包被截人数 |
| C4 一天破产三次 | **走不通**：破产与大厅共用每天 8 个，破产礼包不能豁免，大厅弹满后被截 | 破产位储值项可勾「不受每人每天弹窗上限」；破产规则可按发生破产的游戏区分；多次破产怎么换项、怎么配「不再弹」写在页上。**仍部分**：初始配置是否勾豁免待 Dk |
| C5 同一活动推播、短信、LINE 不重复收 | 只能手工串「排除前序」，前序没发完或顺延时同一人收两条；按行为推送没有手段 | 合并组可跨推送方式：按行为同一触发、或立即定时同一时刻，每人按渠道顺序只发一则，只在不可触达时补位；排除前序改为逐人判定，未出结果的按已收排除；同一地址在一条推送里只发一次 |
| C6 两层上限各管什么、互相影响吗 | 两层分开计看得清；跨层只在「点推送进入那一次」让位；快显与弹窗去重单向 | 推送落地到某项目，当天视同已弹该项；快显与弹窗同项去重双向；按行为推送可选「玩家在线时不发」 |
| C7 一人同属多个人群 | 页面写「只弹最高一条」，实际会由次高规则接着弹 | 统一为「取此刻有可弹项的最高优先级规则」，重叠检查写出接替人数 |
| C8 服务通知不被营销上限挤掉 | 系统活动提醒占满服务通知 3 条后，补偿、停权会被拦；没有用量监看 | 拆出「活动提醒」类（只给迁入的系统提醒与玩家自身事件），服务通知只用于补偿、维护、账号安全，不设类别上限；账号安全通知默认不受勿扰；豁免用量按类别、创建人可看 |
| C9 按行为推送对同一人反复触发 | 被拦、放弃算不算一次没写；判断顺序缺五项 | 被拦、放弃不算一次、不起算间隔；判断顺序与通用规则统一 |
| C10 跨天不重复打扰 | 玩家关掉弹窗只是改弹次高规则；每人总次数在原型没有周期；推送没有再次可收间隔 | 关闭后冷却可扩到本位置同类型；总次数有累计、每日、每周；重复的定时可设「再次可收间隔」「连续未点暂停」 |
| C11 调上限 | 改前影响只有近 7 天日均，调高算不出；中途修改规则没写 | 估算改用「受理＋拦下」；列出已排推送逐条影响；中途修改规则写在页上；游戏内加打扰后果附表，改弹窗上限也给名额截断影响 |
| C12 为什么没收到、没看到 | 只逐条记勿扰放弃与频率上限两种；快显除上限外不逐人记 | 原因码补齐（间隔未到、重要预留、每周、合计、类别、合并组、前序、在线不发、接替、延后后放弃等）；拦下写命中子项与占用名额的推送 ID；快显每次判定都记 |
| C13 与中奖动画、破产流程的时序 | 延后超过 5 分钟名额预占就释放，会超发 | 延后期间名额保持到显示或 10 分钟到期；只在实际显示时计 1；快显有效期页上可见 |

## 二、改了什么——为什么

每条都先查了顶尖产品的官方文档（`对标_游戏外.md`、`对标_游戏内.md`，共 8＋9 个设计点，每点 2–7 家），需求文档 4.1.7、4.2.1 末各有一张「对标与取舍」表带出处链接。截图见 `分析/标准判卷/推送后台_核心整体控制_1018/图/`（19 张，说明在 `截图说明.md`）。

**谁让谁**
1. **游戏外截断顺序写全**：重要推送预留 1 条 → 其余按每人受理先后 → 同一分钟到点重要先、再按排程时刻与推送 ID；预留只在确认排程和开始发送前各算一次。
   为什么：原来同一分钟到点谁先没有规则。Braze、MoEngage 按先后占名额，Braze Message Prioritization、Adobe 用优先级为后面的重要消息让位；我们只分重要、普通两级，规则简单、运营可预期。
2. **弹窗规则接替说法统一**：取此刻对此人有可弹项的最高优先级规则，用完才由次高接替；重叠检查写出接替人数。
   为什么：页面写「只弹一条」与实际不符。Unity Game Overrides、Firebase Remote Config 都是「优先级＋第一个匹配」；Jira 记录运营要「不符往下补满」。

**看得见、算得清**
3. **玩家查询加「今天接下来」与「此刻预演」**，今日计数按上限子项列，原因码补齐并写出占用名额的推送 ID。
   为什么：客服照原页面会答错剩余名额。MoEngage Push Debug、Adobe 排除原因码都逐人逐条给原因；预演比业界多做一层，因为不设审批，客服要直接答复玩家（Jira RICH-19069 等）。
4. **名额占用预估与名额截断影响**：频率上限页给今天与未来 7 天各推送方式的已排条数、预计达上限人数、预计被拦人次；弹窗保存与改上限时给每天多截几项、首储与破产礼包被截人数。
   为什么：几个运营各自排期，最重要那条会不会被挤只能靠系统算。顶尖官方文档未见排程前估算，是有意多做；预测层只给数，不做逐条归因（评审指出近似值不该写成精确拆分）。

**不重复打扰**
5. **合并组跨推送方式**：组内按渠道顺序（例：推播 → LINE → 短信）每人只发一则，只在不可触达时补位，被上限拦下不改走下一渠道。
   为什么：按行为推送同时建推播和短信时，同一玩家每次触发两条都收（评审甲级）。对标 Airship Channel Coordination「Priority Channel」；每种推送一页的结构不动。
6. **跨层同项与在线不发**：推送落地到某项目，当天视同已弹该项；快显与弹窗同项去重双向；按行为推送可选玩家在线时不发。
   为什么：我们的推送本身跳到活动页，再弹即重复。业界不自动去重，MoEngage 用推送后接力应用内消息；游戏运营常见做法是在线玩家不发营销推播。
7. **重复的定时可设再次可收间隔、连续未点暂停**；弹窗关闭后冷却可扩到本位置同类型。
   为什么：同一推送内容对同一人原来没有最短间隔；玩家关掉弹窗后只是换一条继续弹。对标 Braze re-eligibility。

**豁免与破产**
8. **拆出「活动提醒」类**，只给迁入的系统提醒与玩家自身事件（奖励到期、掉榜）；服务通知只用于补偿、维护、账号安全，不设类别上限，用量按类别、创建人监看。
   为什么：系统活动提醒会挤掉补偿、停权通知；评审又指出手选活动提醒能绕过营销上限。Iterable 消息类型、Braze 按标签上限：交易类豁免只限非促销内容，群发倒计时按营销计。
9. **破产位储值项可勾「不受每人每天弹窗上限」**，破产规则可按发生破产的游戏区分。
   为什么：原型示例近 7 天 3,110 次破产请求被上限拦下；德州扑克要先弹棋牌专属礼包（Jira RICH-23752）。Braze、MoEngage 都用单条豁免；默认不勾，与呈交版「大厅与破产合计」一致。

自行决定与可推翻的事已写进推送后台清单第六节（例：合并组只在不可触达时补位、立即推送入组最长等 30 分钟、排除前序未出结果按已收排除、按行为在线不发的默认值）。
