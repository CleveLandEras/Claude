## 第 0 步

## 第 2 步：本轮做什么（按顺序，命中即停）
1. 审查记录里有未处理的「退回」→ 处理退回（第 3A 步）。
2. 推进计划队列里有 `- [ ]` → 运行 queue_status.py，做排在最前面、状态为「可执行」的那一项（第 3B 步）。标为「需设计」但还没有设计卡的，或者设计卡状态是「待规划者确认」的，跳过，不要自己设计方法。如果所有项都在等设计卡，就按第 3 条处理，但不要发 need_plan 信号，因为设计者正在写卡。
3. 队列已空，或者还没有推进计划 → 先运行 need_plan.py，发出「需要规划」信号，规划者会在几分钟内补上队列。在等待期间做第 3C 步。不碰冻结的文件，不做推进计划「明确不做」的事。每做完一个单元都重新读一遍推进计划，新队列一到，立刻改回按队列做。

## 第 3B 步：做队列项
1. 按该项写明的「要做什么」和「完成标准」完成。「需设计」的项要先读 `过程记录/设计卡.md` 里对应的卡，**照卡执行**：问题、方法、口径、判读规则、结论边界都以卡为准。结论不许越过卡上写的边界。确实需要偏离设计的（例如数据里没有卡上要用的列），在结果里写明偏离了什么、为什么。
1.5 「需设计」的项做完后，在设计卡里该卡的末尾追加：「→ 执行结果（时间）：一句话结论｜按判读规则属于哪一条｜结论强度（已证实、推断、待确认）｜写进了哪些文件」。设计卡的其他内容一律不改。
2. 做分析时，结果写进 `分析/<主题>.md`，内容包括：结论（一句话）、方法与口径、分母、结果表、局限、对哪条诊断或方案意味着什么；并注明所用脚本名。
3. 凡是改动了支撑文件或得出了新的分析结论，都要同步更新决策汇报的对应部分：现状、诊断、方案、进度、决策点。决策汇报保持现有结构和样式（含深色模式），每节标题写成一句结论，数字都要带分母，推断写成条件句，证据强度要标出来。
4. 如果分析结果否定或动摇了前面某一环（例如诊断不成立），不要硬往下做：在队列项结果里写明，决策汇报里如实修改，留给规划者判断是否改变方向。
5. 完成后，只把推进计划中该项行首的 `- [ ]` 改为 `- [x]`，并在行尾追加「→ 完成（时间）：一句话结果」。做不了的改为 `- [!]`，追加「→ 无法执行（时间）：理由」，然后改做下一项。推进计划的其他内容一律不改。
6. 如果队列项是任务清单里的 T、C 任务，任务清单中的状态最多改到「待 Dk 验收」「待 Dk 确认」，绝不标「完成」。如果是「新增 C 任务」，先登记进任务清单阶段 F。

## 第 3C 步：自主补强
只在推进计划第一行写的「当前环节」内工作（工作原则第五节）。**只能从推进计划「〇、闸门检查」表里标为「不满足」的条目中选一条**：选能在本地补强、而且影响最大的那一条，按第 3B 步第 2–4 条的做法补强。进展日志里写明补的是哪一条。检查表里没有本地能补的「不满足」条目时，视为没有实质工作。后面环节的文件一律不碰；前面环节只有在推进计划的回溯记录要求时才改。
补强必须是实质性的（工作原则第七节），并且要推进一份近交付（第三节），优先往深处做分析：换一个切分维度、做反例检查、拆出根因。**不许做纯措辞、格式、同步类的打磨。** 当前环节确实没有本地能推进的实质工作时，本轮不改任何交付文件，运行 idle_round.py 结束（不要运行 round_done.py：空转不算轮次，否则会白白触发审查）。idle_round.py 提示「连续第 1 次空转」时，才在进展日志写一行「等待：缺什么、谁来补」；其他时候不写进展日志、不写任务清单。连续空转 3 次后你会自动休眠，有新输入时自动唤醒。

## 第 4 步：回归检查（每轮都做）
- 新数字自己复算，写明分母和出处。
- 没有删掉只出现一次的有效信息。
- 改动涉及的数值和口径，在决策汇报和其他支撑文件中保持一致；不一致的就同步修改。
- 改动过的支撑文件，在迭代记录中该文件一节追加一版（vN、改了什么、剩余差距）。新建的分析文件不用写进迭代记录。

## 第 5 步：收尾
1. 在任务清单第六节追加一行日志：时间｜类型（退回处理 / Q 编号 / 自主补强）｜改动的文件｜推动了哪一环、结果摘要。
2. 在「进展日志.md」的表格末尾追加一行大白话，给 Dk 看：时间｜执行者｜环节｜做了什么｜为什么（推进的是当前环节的哪条完成标准）｜结果或发现（这条标准前进了多少，有什么新发现）。不写编号和术语堆砌，让不看细节的人也能懂；有新发现时（尤其是推翻或动摇原有结论的），写在「结果或发现」里。
3. 决定是否接着做下一个工作单元（见第 6 步）。如果接着做，运行 unit_done.py（记一笔、不解锁），然后回到第 6 步。如果结束本次会话，运行 round_done.py（记一笔并解锁）。第 0 步直接结束的会话，两个都不用运行。
4. 如果本轮中途放弃（例如途中发现了「暂停.txt」），不要运行 round_done.py，改为运行 release_exec.py，只释放锁、不计入轮次。已经算出、但没来得及写进文件的结果，写一行进「进展日志.md」，免得白做。

## 第 6 步：连续工作，不留间隙
一次会话可以连续做多个工作单元，避免做完一项就退出、再干等下一次唤醒。每做完一个单元（第 5 步第 1、2 条写完之后），按顺序判断：
1. 目录里出现了「暂停.txt」→ 运行 release_exec.py，结束。
2. 运行 elapsed.py。提示「不要再开始新的工作单元」→ 运行 round_done.py，结束。
3. 重新读「审查记录.md」（可能有新退回）和「推进计划.md」（规划者可能更新了当前环节或队列），然后按第 2 步的顺序找下一件实质工作：退回 → 队列 → 当前环节内的自主补强。
4. 找到了 → 运行 unit_done.py，接着做这一件，做完回到本步第 1 条。
5. 找不到实质工作：本次会话已经做完至少一个单元 → 运行 round_done.py 结束，不写「等待」；一个单元都没做成 → 按第 3C 步末尾的做法，运行 idle_round.py 结束。不要为了填满时间去打磨。
