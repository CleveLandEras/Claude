# 推送系统的后台集成需求

2026-10-12 建。细化这项需求的人先读本文件。已确认的与未确认的分开写，未确认的不要写成定论。

## 一、已确认
- **主管原句**（产品计划，推送一条）：「推送：統一推送入口，提高易用性，并增加數據情況（發送量，到達率等）」。原文见 `来源资料/产品计划原文_1010.md`。
- **10/10 Dk 与主管同步**：「确实要后台集成数据」。这是 Dk 的转述，主管原话没有记录。
- **对外名称**：「推送系统的后台集成需求」，标题用「推送入口与数据统一」。Dk 10/12 定的这两个名称有意写得保守：「集成」既可以指入口、数据，也可以指操作，不排除任何一种理解。

## 二、未确认：统一到什么程度（10/13 起过时，仅作背景：统一入口已定，见已定事项 23）
主管原句说的是「入口」，没有说「操作」。Dk 不确定主管是否要求统一操作界面，也不确定有没有这个必要。评估完成后，带着下表三档去问主管。确认之前，任何文件都不能写成只统一数据，也不能写成必须统一操作。

| 统一程度 | 做法 | 与原句的关系 |
|---|---|---|
| 只统一数据 | 各推送方式在原处操作，数据在后台一处查看 | 只满足「增加數據情況」 |
| 统一入口 | 一个后台进入五种推送，各自的配置页面可以不同 | 字面满足「統一推送入口」 |
| 统一操作 | 一个「新建推送」流程覆盖五种推送 | 原句没有明说 |

## 六、10/12 问答定下的做法（Q1–Q16，Dk 逐条答复）
本节与上文冲突时以本节为准。第五节的天数拆解改为：先出界面，再带界面去核实第四节的问题。

| 事项 | 定了什么 |
|---|---|
| 交付 | 分两步。① 界面展示稿：给主管、运营看，用来选统一程度；先出静态网页稿，最终呈交用 pptx（Dk：「最终呈交的时候还是会用ppt」）。② 主管选档后再写研发用的需求文档（字段、异常、日志、验收用例）。（已过时：见第八节阶段表、原型任务说明） |
| 展示形式 | 不做可点击原型（Dk：「主要是为了提升阅读而不是互动性」）。照 `~/Downloads/通行证后台配置原型.html`：每屏一个后台窗口，下拉画成展开状态，示例数据不必真实，每屏下 2–3 张注释卡，末尾一张覆盖对照。改动标注借 `~/Downloads/新手通行证重构方案-3.pptx` 第 16–19 页：在现有页面上标「新增」「改」。（已过时：见第八节阶段表、原型任务说明） |
| 统一程度 | 按最完整的「统一操作」设计，界面上标出每处属于第二节哪一档。 |
| 风格 | 在现有后台基础上做最小成本优化（Element UI 风格，推断），不完全照搬旧页面；每处改动标出成本。（已过时：见第八节阶段表、原型任务说明） |
| 使用者 | 运营。不设审批：发送前一页确认（受众人数、各渠道预计条数、文案预览）＋发给测试账号＋操作纪录。 |
| 指标 | 四步漏斗：发送 → 到达 → 曝光 → 点击。各渠道只显示能回传的步骤，回传不了写「该渠道不回传」，不估算；快显从曝光开始。具体字段待和数据平台确认。 |
| 受众 | 选现有标签群组（含五类人群），显示预计人数与各渠道可触达人数。 |
| 频率上限 | 核心：每种渠道每人每日上限。合计上限列为可选。 |
| 弹窗 | 纳入同一后台（Dk：「弹窗本身就是推送的重要部分」）。每种推送各一页、各自的新建表单；弹窗保留自己的配置页，在现有「大厅弹窗顺序设定」上优化；共用入口、受众选择、频率上限、数据看板、玩家查询（扩展「玩家弹窗顺序查询」为查一个玩家收到的全部弹窗与推送）。弹窗可以加新功能，最终合进 V4 的后续版本。 |
| 名称 | 仍为「推送系统的后台集成需求」。 |
| 工作方法 | 参考顶尖 AI 公司的做法（Dk：「因为是ai写不是人写」）：先写评分表 → 界面元素标来源（现状事实／成熟产品做法／假设）→ 对标调研 → 关键页 2–3 个方案比较 → 先做一屏给 Dk 看 → 无上下文子任务独立评审（按清单判到通过）。 |
| 页面组织（10/12 晚，覆盖上面「统一程度」一行） | 先功能后人群，按功能分页，一个入口（Dk：「先选人群感觉还是不符合习惯，先功能，功能分页显示就好，不同页面操作不同功能，只不过都一个入口」）。侧栏「推送管理」下每种推送方式（弹窗、快显、推播、短信、Facebook、LINE）各一页。设计落在「统一入口」一档；「一条推送同时发多个渠道」降为可选。新建表单不再先选功能（页面已定渠道），按通用顺序 内容 → 对象 → 时间（含功能触发）→ 频率上限 → 确认（Dk：「最通用的做法或者说最专业的是哪个就用哪个吧」）。 |
| 推送分两层（10/13，已定事项 24） | 游戏内（弹窗、快显：玩家在游戏里才看得到，数据从曝光算起）与游戏外推送（推播、短信、Facebook、LINE：不在游戏里也收得到）分开列，侧栏、总览、频率上限、数据看板、玩家查询都按两层分。名称与呈交版对齐：后台叫「推送统一后台」；「按行为」触发（玩家升级、完成任务、礼包快到期时自动发）；上限写「每人每天」。 |
| 提问 | 推进中碰到的问题攒到一起统一问（Dk：「之后推进时碰到问题再统一问吧」）；只限业务方向取舍、验收、Dk 对外安排的事，其余在清单记「自行决定」（标准体系第〇节）。 |

## 七、需求清单（2026-10-13 Dk 通过：「没问题 按你推荐来就行」——清单与分级通过；统一程度：统一入口（已定））
按现状问题组织（简报 `推送系统后台集成需求/1_需求清单.html` 为准）。分级：必须＝不做就达不到产品计划原句或方案三项目标；建议＝不做也能达到目标，做了运营更省事、更少出错；可选＝可后做。

**现状问题**
1. 配置分在四处：礼包后台（推播）、营销侧（短信、Facebook、LINE）、客户端（快显）、弹窗后台（弹窗）。
2. 不能按人群发：游戏外的推播只用于限时加码礼包未购买提醒，短信、Facebook、LINE 按名单发；游戏内的快显发给所有在线玩家。
3. 每人每天收到多少没有上限：推送没有每人每天上限；弹窗只有单项次数与冷却，没有总上限。
4. 数据分散且不全：推播报表没有到达；短信数据在数据平台；Facebook、LINE、快显查不到。

| # | 需求 | 分级 | 对应原句 |
|---|---|---|---|
| 1 | 一个入口进入全部推送；游戏外（推播、短信、Facebook、LINE）与游戏内（弹窗、快显）分开列，每种推送一页 | 必须 | 統一推送入口 |
| 2 | 每种推送都能按标签群组选发送对象，并可排除部分玩家 | 必须 | 統一推送入口 |
| 3 | 运营自己设内容、点击跳转和发送时间（立即、定时、按行为，如礼包快到期、玩家升级） | 必须 | 統一推送入口 |
| 4 | 限时加码礼包的推播迁入，礼包后台不再单独配置 | 必须 | 統一推送入口 |
| 5 | 短信、Facebook、LINE 的发送从营销侧接入 | 必须（依赖营销侧，研发评审确认） | 統一推送入口 |
| 6 | 快显改由后台配置 | 必须（依赖客户端，研发评审确认） | 統一推送入口 |
| 7 | 每种推送每人每天上限，游戏内与游戏外分开算 | 必须 | 方案目标：每人有上限 |
| 7a | 游戏外推送设勿扰时段 | 建议 | 提高易用性 |
| 8 | 发送前看到预计人数、可触达人数、会被上限挡下的人数 | 建议 | 提高易用性 |
| 9 | 先发给测试账号看效果 | 建议 | 提高易用性 |
| 10 | 发送状态可查，可停止，失败可重试 | 建议 | 提高易用性 |
| 11 | 查一个玩家能不能收到、收到过什么、被什么挡下 | 建议 | 提高易用性 |
| 12 | 游戏外推送查发送、到达、点击；短信另查发送对象一定时间内登录的人数（已定事项 3 的例外）；游戏内推送查曝光、点击 | 必须 | 增加數據情況 |
| 13 | 按推送方式、人群、单条推送、日期查看，可导出 | 必须 | 增加數據情況 |
| 14 | 拿不到的数据写明原因，不估算 | 必须 | 增加數據情況 |
| 15 | 没送达的原因：被上限挡下、勿扰、无联系方式、通知关闭、发送失败 | 建议 | 增加數據情況 |
| 16 | 一条内容复制到其他推送方式 | 可选 | 提高易用性 |
| 17 | 游戏外推送合计每人每天上限 | 可选 | 提高易用性 |
| 18 | 同一位置两个弹窗的最小间隔 | 可选 | 提高易用性 |
| 19 | 文案插入变量（如玩家昵称、礼包剩余时间） | 可选 | 提高易用性 |

**不在本需求**：会员标签设定的改动（属标签需求）；弹窗按人群拆规则（用现有功能，V4 已列）；审批流程；A/B 测试；多步自动化流程；埋点。
