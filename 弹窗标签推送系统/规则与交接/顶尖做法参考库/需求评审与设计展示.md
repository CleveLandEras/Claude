# 需求评审与设计展示

范围：需求评审、设计评审的材料怎么组织，以及「产品或后台本身的结构」怎么展示。评-01 至评-12 回答「评审材料每一块的通行组成」，评-13 至评-20 回答「结构用什么图、画到哪一层、和目录怎么分工」。做法按「设计点」去重合并；同一做法多家共有时合为一条。「我们的取舍」是 10/19 的建议，不是已确认的决定，落地以需求评审版任务说明与 Dk 的意见为准。10/19 晚按 README 用途第 3 条普查：评-01、02、03、06、07 与写作标准冲突的部分改为不采纳或部分采纳，各条写了「对照过」；文中「写作标准第 N 行」指 `../写作标准_合并版.md`，「任务清单第 N 行」指 `../../过程记录/任务清单.md` 答复登记。核对日期 10/19，出处链接均已打开核对；官方页面常改，落地前对关键口径再核一次。

## 两个问题的归纳

**A．评审材料每一块的通行组成**（评-01 至评-12）

- 骨架一致：问题（具体故事或事实）→ 目标与非目标 → 设计（先概览后细节）→ 考虑过的其他方案与缺点 → 未决问题集中成节（评-01、02、04、06、07、08）。本项目的评审材料不采纳其中「考虑过的其他方案与缺点」一块（评-06）。
- 场景和用户故事在其中是佐证：或放在「问题」里说明现状为什么不行，或放在方案之下说明用起来是什么样；操作步骤是另一份用户手册，不是评审材料的主体（评-05）。
- 评审是先读后议，议的是问题定义得对不对、方案对没对上、有没有更好的替代（评-11）；国内顺序同样是先价值与流程，再功能架构，最后才点开原型（评-12）。

**B．产品或后台本身的结构怎么展示**（评-13 至评-20）

- 用什么图：外层是系统上下文图，回答边界在哪、与谁相连（评-13）；内层是站点地图一类的树，回答由什么组成、分几层（评-15、19）；再用「地方、可操作项、连线」画页面之间的跳转（评-17）。国内把后两者合称产品结构图（评-19）。
- 画到哪一层：按缩放层级取舍，只画有价值的层；站点地图类图常见三层，国内功能结构图建议不超过 3 级，字段另有信息结构图承担（评-14、19）。弹层与从列表进入的页面作为连线终点画出，桌面产品的 wireflow 只画变化的部分（评-17）。
- 和目录的分工：目录或议程管讲什么、先后；结构图管产品是什么。信息架构是底层结构，菜单与目录是它的一个入口，不能当作结构本身（评-16、20）。

**C．图与介绍文字怎么排**（评-21 至评-27）

- 先后：组成类说明，图在说明之上（评-21）；规则类小节，Carbon 是文字在前、示例图在节末，Atlassian 是图在前（评-23）。纯文字的「何时使用」类小节没有图；整页的介绍文字压在界面图上面的页面，在所查来源中没有见到。文字需求在前、原型在后的是 PRD 模板，对象是文字需求文档（评-25）。
- 对应：图上编号、图下按编号列组成清单，清单项只写名称（评-22）；批注挂在被批注处（评-24）。
- 规则：放在图之后，按主题或图上区域分成独立小节（评-23），每个小标题单独可读（评-27）；版式每页一致（评-26）。
- 推荐给需求评审版每页的阅读顺序：页标题与 2–4 个要点短语 → 原型图（图上标数字）→ 组成（按图上数字列）→ 关键规则（按图上区域分组，各配小标题）。
