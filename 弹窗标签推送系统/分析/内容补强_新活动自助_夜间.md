## 结论

- 缺的东西是一张表：「项目目录」与「事件目录」。弹窗项目下拉、按行为的触发行为、推送的点击跳转三处都改为读这张表，不再写在代码枚举里。新活动只要在表里多一行，不发后台版本。
- 新活动的系统推送用 3 个「活动事件模板」配置：时间偏移、排名变化、每日定点＋状态。RICH-17579 第 4.4 节的 34 种系统推送已逐条对上模板（3.6）；这 34 种同时作为服务端写死清单的初版（第 9 章研发 27 目前只查到 1 种）。
- 项目时间是唯一时间源：推送、弹窗规则、快显选了项目即默认跟随项目上架时间，触发点按项目开始、结束加减偏移计算。活动提前结束或延期时，引用它的设置自动跟着改，改前列出受影响清单（3.7）。
- 漏登记由系统拦：运营可先建草稿并配好规则，活动配置里出现未登记的活动也会自动建草稿；草稿不能上架，卡在哪一项、等谁、等了几天在目录与总览可见（3.2）。
- 客户端按「展示模板类型」渲染，新一期活动不发版；没有对应模板的客户端不显示并上报原因（3.8）。发版只剩一种情况：客户端没有对应的展示模板（新玩法、新弹窗形式、新显示位置），而这次发版本来就是活动自身要发的。
- 成本分三层：项目目录与草稿、下拉改读目录、时间偏移（项目锚点）、时间变更传导属于小改动；下发协议、通用模块发标准事件、信箱奖励带项目编码、排名快照比对、批量复查属于较大开发；流程规范、34 种清单入文档现在就能写。
- 不需要 Dk 定。模板本期范围、排名变化的产出方式、时间变更的默认处理列为第 9 章研发、客户端、运营确认项，由需求评审定。

共同点：
1. 事件与目录是数据，由研发登记一次（名称、参数、来源），之后运营在下拉里选。
2. 时间型触发（开始前、到期前）由平台按目录或事件里的时间字段自己排程，不要求业务端准点发事件。
3. 登记项都有引用清单、停用保护与上报状态。
4. 客户端能力是硬边界，用版本号表达。

## 三、补法

### 3.1 两张目录，一处登记，三处读取

| 目录 | 一行是什么 | 读它的地方 |
|---|---|---|
| 项目目录 | 一个能被弹出、能被跳转的游戏内容：一个活动（含期次）、一个礼包、新手项、公告 | 弹窗规则「项目」（§5.12 序号 18）；推送「点击跳转页面」（§5.4 序号 7）；快显点击跳转；活动事件模板选「哪个活动」；生效期间「跟随项目」 |
| 事件目录 | 一种能触发推送或弹窗的事件：玩家行为（升级、完成任务）、业务事件（榜单变化、奖励到期） | 按行为「触发行为」（§5.5 序号 3）；弹窗「指定行为」（§5.12 序号 35）；文案变量可用范围（§4.1.13） |

位置：侧栏「迁入管理」上方加「活动与事件目录」，原型页 #16a（插页，不改后续页码），两个页签：项目、事件。

与已有概念的分界（避免同名混淆）：

| 名称 | 是什么 | 谁建 | 例 |
|---|---|---|---|
| 项目（本文新增目录） | 游戏里的活动、礼包实体 | 研发登记类型；运营建期次或草稿；系统发现未登记的自动建草稿 | 活动排行榜 · 万圣节榜 |
| 所属活动（§4.1.17，已有） | 运营的营销分组，跨推送方式合计 | 运营 | 10 月回流季 |
| 模板（§4.1.17，已有） | 某推送方式的内容模板 | 运营 | 每日补给 · 推播 |
| 活动事件模板（本文新增） | 触发逻辑模板，选定项目后生成一条按行为推送 | 研发定义模板，运营套用 | 时间偏移 × 红包狂欢结束前 2 小时 |

所属活动与项目两者不合并：一个营销活动常跨多个项目（回流季含回流任务、每日补给），一个项目也会跨多个营销活动。所属活动加「关联项目」、按项目优先排序下拉属看板口径改进，与新活动上线无关，延后，不进本期。

### 3.5 三个活动事件模板：新活动的系统推送在后台配

模板是研发定义好的触发逻辑。运营在按行为推送里选「活动事件 → 模板 → 项目」，再填偏移量与条件。一个模板 × 一个项目 = 一条按行为推送，其余设置（只限群组、提醒次数、勿扰、频率上限、生效期间）沿用 §4.1.4、§5.5；选了项目时生效期间默认跟随项目（3.7）。

| 模板 | 运营填什么 | 触发怎么算 | 发送前复查 | 数据从哪来 | 成本 |
|---|---|---|---|---|---|
| 时间偏移 | 项目；锚点：项目开始／项目结束／事件时间（取事件中标「用于排程」的字段，如 `expireAt`、`availableAt`）；前或后 N 分钟（0–4320，界面可按小时填）；锚点为事件时间时可勾「到点仍未完成才发」 | 项目锚点：推送服务按项目上架开始、结束自己排程，到点按只限群组取人；事件锚点：按事件里的时间字段 ± N 排程，同 GIFT_EXPIRING 的做法（第 9 章研发 20） | 项目锚点：项目仍在架、时间未改（改了按 3.7 重算）；事件锚点：批量复查仍未领、仍未买、仍可领 | 项目锚点：项目目录；事件锚点：信箱、礼包后台、保留座、通用冷却各接一次 | 项目锚点小改动；事件锚点较大开发（按模块一次，不按活动） |
| 排名变化 | 项目（排行榜类）；掉出前 K 名（K 1–100）；只在结束前 N 小时内发（1–72）；同时掉多个榜时按榜单权重只发 1 条 | 不逐次加分发事件。排行榜模块或推送服务每 5–10 分钟（暂定）比对一次前 K 名快照，产出本轮「掉出前 K」名单，一次批量交推送服务；备选：排行榜模块只在玩家跨过第 K 名时发事件（第 9 章研发 47） | 产出名单即当时状态；同一人同一榜一个比对周期最多 1 次 | 排行榜模块 | 较大开发（一次） |
| 每日定点＋状态 | 项目；每天 HH:mm；状态条件：选一个标签群组（例「持有占星石 ≥ 1」「有可领奖励」「今日未登录」） | 活动把状态写成玩家属性（例 `astroStoneCount`），标签系统据此生成标签群组；到点按该群组当时的成员发，复用人群与标签能力，不另做每个活动一个状态名单接口 | 群组成员即当时状态 | 各活动写玩家属性；标签系统 | 较大开发（每个活动写一次属性，比单独做接口小）；「今日未登录」用现有登录数据，小改动 |

模板通用规则：
- 文案用现有内容模板与文案变量。模板多出三个变量：活动名称、剩余时间、当前名次。§4.1.13 整体仍为可选功能；变量没做时，运营按项目写固定文案，一条推送只对一个项目。
- 时间、文案、暂停都在后台改，满足 RICH-15154「推播时间都需要可以在后台编辑异动」。
- 跨推送方式：同一模板可用于推播、短信、Facebook、LINE、快显；时间偏移、排名变化也可用于弹窗「指定行为后」。
- 重复触发提示（§4.1.4）的判断从「同一触发行为」改为「同一模板＋同一项目＋同一锚点」。

### 3.7 项目时间变更：引用它的设置自动跟随，改前看受影响清单

#### 跟随方式

| 对象 | 跟随什么 | 规则 |
|---|---|---|
| 按行为推送（游戏外四种与快显）的生效期间 | 项目上架开始、结束 | 选了活动事件模板的项目后，生效期间默认「跟随项目上架时间」，可改回固定日期；跟随时按项目时刻生效，不按整天 |
| 弹窗规则的生效期间 | 排序项中选定的一个项目 | 生效期间可选「跟随项目」，从本规则排序项里选一个项目，取其上架开始、结束；第一个排序项为有结束时间的活动类项目时默认跟随它 |
| 时间偏移（项目锚点）的触发点 | 项目开始或结束 ± 偏移 | 项目时间一改按新时间重算，不需要改推送 |
| 排名变化的「结束前 N 小时」窗口 | 项目结束 | 按新结束时间重算 |
| 每日定点＋状态 | 生效期间 | 只在新的上架期间内每天执行，期间外的日期取消 |
| 定时推送与快显（点击跳转到该项目） | 不自动跟随（发送时间是运营定的固定时刻） | 列入受影响清单，确认框可勾「按同样偏移平移」：保持原发送时刻与最近锚点（开始或结束）的间隔；不勾则保持原时刻，落在项目期间外的按 §5.4 序号 63 跳转失效处理 |
| 弹窗排序项本身 | 项目上架时间 | 已有：未到开始不弹，过了结束自动跳过 |
| 时间偏移（事件锚点），如信箱奖励到期 | 不跟随 | 跟奖励自身的 `expireAt`，活动延期不一定延长奖励到期；写明在模板说明里 |

#### 各种变更怎么处理

记旧时间为开始 S0、结束 E0，新时间为 S1、E1，当前时刻为 now。

| 情况 | 处理 |
|---|---|
| 已发出的触发点 | 不撤回；旧触发点重算后的新触发点仍在将来时，默认再发一次（例：已按 E0 前 2 小时发过「还剩 2 小时」，延期后旧文案已不准，到 E1 前 2 小时再发），确认框可逐条改为「不再发」 |
| 未到的触发点，新触发点仍在将来 | 重排到新时刻 |
| 未到的触发点，新触发点已过 | 跳过，不补发，逐人明细与该推送数据记原因「项目时间变更后触发点已过」；项目仍在架（now < E1）时确认框可逐条勾「立即补发一次」，默认不勾；项目已结束的不能补发 |
| 提前结束，且 E1 ≤ now（立即结束） | 结束锚点的未到触发点全部取消，记「项目已提前结束」；跟随型的推送与弹窗规则随即变为已结束；排名变化窗口关闭；弹窗排序项即时跳过。不自动改发「活动结束」通知，确认框给入口「新建结束通知」（打开立即推送表单，点击跳转预填该项目） |
| 提前结束，且 E1 > now | 结束锚点的触发点按 E1 重算，按上面三行处理；开始锚点不受影响；跟随型生效期间缩到 E1 |
| 延期（E1 > E0） | 跟随型生效期间延到 E1；结束锚点触发点后移；固定生效期间早于 E1 结束的推送、规则在受影响清单标「生效期间早于新结束时间，最后 N 天不弹（不发）」，确认框默认勾「改为跟随项目」 |
| 开始时间改晚（S1 > S0） | 开始锚点触发点后移，已发过的「开始前」默认再发一次（同第一行）；未到 S1 弹窗不弹 |
| 开始时间改早（S1 < S0） | 开始锚点触发点前移，新触发点已过的跳过（同第三行） |

#### 改前确认与通知

| 改动来源 | 流程 |
|---|---|
| 运营在目录改时间（方式 B） | 点「保存」先弹「时间变更影响」确认框：按对象类型列出被引用的弹窗规则（生效期间、排序项）、按行为推送、定时推送与快显；每条写名称、负责人、原触发时间 → 新触发时间、处理（自动跟随／再发一次／将跳过／可补发／需选择）；顶部汇总「受影响 N 条，其中将跳过 N 个触发点、需选择 N 条」。按钮「确认变更」「取消」 |
| 活动配置同步来的改动（方式 A，随同步上线） | 源头已改，不能拦：目录按源更新，跟随型按上表默认处理，需选择的项按默认值（不补发、定时不平移、固定生效期间不改）处理；整次变更列入总览待处理「项目时间变更」，通知引用项的负责人；点进去为同一张影响清单，可逐条改处理方式 |
| 方式 B 期间活动配置改了时间但目录没改 | 系统发现（3.2）读活动、礼包列表时比对名称与上架时间，不一致的目录项标红「与活动配置不一致」并列入总览待处理「项目时间变更」；点「按活动配置更新」走方式 B 的确认框。流程上写明：方式 A 上线前，活动配置改时间必须同步改目录 |

操作纪录：对象「项目」加动作「时间变更」，记操作人（同步来的写「系统 · 同步」）、改前改后、确认人与时间、受影响清单快照（每条的处理结果：重排至 HH:mm、再发、跳过、补发、平移、保持）；每条受影响的规则、推送各记一条「随项目时间变更」，操作人「系统」，附项目变更纪录编号。

### 3.8 下发协议：客户端按展示模板类型渲染

#### 弹窗下发（§4.2.1 第 8 步「下发」的每一项）

| 字段 | 说明 | 例 |
|---|---|---|
| `itemKey` | 项目编码（期次级） | `ACT_RANK_HW26` |
| `typeKey` | 所属类型编码；类型本身下发时同 `itemKey` | `ACT_RANK` |
| `templateType` | 展示模板类型，客户端据此选渲染组件 | `RANK_BOARD` |
| `form` | 弹窗形式：活动本身／活动广告页 | `AD_PAGE` |
| `params` | 期次参数，键按该展示模板类型的参数结构 | `{"boardId":"HW26","theme":"halloween"}` |
| `route` | 点击跳转路由，推送与快显用同一值 | `activity/rank?id=HW26` |
| `validTo` | 项目上架结束；客户端显示时已过该时刻的不显示，上报「项目已结束」 | `2026-11-02T23:59:00+08:00` |
| `displayDetailId` | 逐次显示明细 ID（已有） | — |
| `legacyItemId` | 旧编号，只对旧客户端下发（见下） | `20` |

推播消息体、快显下发的点击跳转同样带 `itemKey` 与 `route`；旧客户端只认旧跳转类型与页面 ID，按旧编号下发，没有旧编号的新项目对旧客户端改为只打开 App。

#### 客户端渲染与降级

- 客户端按 `templateType` 找本地组件，用 `params` 渲染；同一展示模板类型的新期次不发版（①档）。
- 未知的 `templateType`、`params` 缺必填键或类型不对：该项不显示，上报显示失败与原因码（`UNKNOWN_TEMPLATE`、`PARAM_INVALID`），接着显示下一项；服务端记「已下发 · 显示失败」（§4.1.10 已有）并写原因，不计曝光、不计次数与冷却。
- 显示失败率进游戏内推送数据（v0.9.8 已加），同一项目近 1 小时显示失败占比超过 5%（暂定）时列入总览待处理。

#### 客户端版本门槛

| 门槛 | 规则 |
|---|---|
| 请求必带 | 弹窗请求带平台与客户端版本（§5.12 序号 37、38 已用）；缺失时按「低于协议门槛」处理 |
| 协议门槛版本 | 支持按 `templateType` 渲染的首个客户端版本（第 9 章客户端 33）。低于该版本的客户端：只下发有旧编号的项目，用旧结构（旧 itemId）；没有旧编号的新项目不下发，记「客户端版本不支持该项目」 |
| 展示模板最低版本 | 每个展示模板类型按平台登记能渲染的最低版本（第 9 章客户端 34）；项目最低版本取协议门槛、展示模板最低版本、项目自身填写三者中最高的 |
| 推送 | 推送不按版本拦，跳转按上面规则降级为只打开 App；预计人数暂不按版本扣除，与 §5.12 序号 38 同口径 |

### 3.10 边界与异常

| 场景 | 处理 |
|---|---|
| 客户端低于项目最低版本 | 弹窗：该项不下发，逐次显示明细记未弹出原因「客户端版本不支持该项目」（§5.18 序号 51 原因码加一项），继续取下一项；推送跳转：改为只打开 App（3.8） |
| 客户端不认识展示模板类型（登记有误或版本判断有误） | 不显示、上报 `UNKNOWN_TEMPLATE`，取下一项（3.8）；草稿期的清单 5 验证不通过，不能转可用 |
| 项目下线或过了结束时间 | 引用它的弹窗排序项自动跳过，在规则编辑页与列表标红「项目已下线」；推送按 §5.4 序号 63 跳转失效处理；跟随型推送到期自动变为已结束 |
| 有上架引用时下线或删除项目 | 不能删除，只能下线；确认框列出引用的规则与推送（参照 Braze 停用事件时的警告） |
| 项目上架时间变更（含提前结束、延期） | 按 3.7 |
| 草稿临近上架仍未补齐 | 预计上架前 3 天列入总览待处理「项目草稿临近上架」，通知研发负责人；到了预计上架时间仍为草稿的，引用它的规则、推送继续不能上架，不自动放行 |
| 事件长时间没有上报 | 并入总览待处理「按行为异常」（§4.1.2，24 小时 0 次触发） |
| 事件参数缺失（如缺 expireAt） | 该次事件丢弃、不发，记服务端日志；本期不在后台展示格式错误计数 |
| 状态复查接口超时或失败 | 本次不发，记原因「复查失败」，1 分钟后重试一次，仍失败则放弃 |
| 运营想要一种目录里没有的事件 | 不支持运营自建事件，提研发需求按③档登记；§3.5 写明不做「运营自定义事件」与理由（事件语义要研发保证） |
| 迁入的旧写死推送与新模板推送重复 | 同一模板＋同一项目＋同一锚点时由重复触发提示提醒；旧写死项按 §4.2.6 切换开关停发后再启用新推送 |

## 五、需 Dk 定的点

无。W1、W3 的方向已由参照 B4-20、B8-14 定为「要（本期）」。

以下交需求评审，已列入第 9 章，不报 Dk：
- 模板本期范围（研发 46）：建议时间偏移（项目锚点）本期，事件锚点随模块接入，排名变化随快照比对，每日定点＋状态分批。理由：项目锚点不依赖外部事件；其余都依赖其他模块的改造。
- 排名变化的产出方式（研发 47）：建议快照比对。理由：不要求排行榜逐次发事件，避开事件风暴，改造集中在一处。
- 时间变更的默认处理（研发 46、运营 24）：建议新触发点已过的跳过不补发、可勾补发，已发过的到新时间再发。
- 同步方式（研发 42）：建议能同步的用方式 A，不能的先用方式 B 加系统发现。方式 B 是小改动，加上发现与不一致比对后，即使同步排不进本期，也能消除急单、拦住两处手改的遗漏。
