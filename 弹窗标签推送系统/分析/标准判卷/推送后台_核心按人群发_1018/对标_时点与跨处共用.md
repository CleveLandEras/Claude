**对我们的启示**
1. **相同，保持**：立即、定时在开始发送那一刻取名单，重复的定时每次各取一次。Airship 明写「运行时评估、重复同样」，Braze、MoEngage 同为发送时评估。
2. **批量与实时混用，相同**：顶尖做法是批量部分用最近算完的结果，实时条件另走触发判定（TE 触发型任务、MoEngage RTSE、CleverTap Live）。我们按行为推送「触发时判只限群组、读最近批次」是同一模式。标签是 BigQuery 脚本、最快 25 分钟，不追求标签实时化；要实时的身份走登录时判定（见 P7）。
3. **计算中沿用旧名单，相同**：Braze 刷新中用之前的成员、Airship 新版本处理完前用旧版本，与我们「未算完前用上一批次」一致。
4. **建议补一条时点提示（小改动）**：新建标签每日 06:00 换批，脚本跑完需要时间。定时推送的发送时刻早于所引用标签当日批次算完（如 06:05）时，确认页提示「所引用标签今日批次尚未算完，将用前一日名单」。依据：Braze 写明批量刷新最长约 60 分钟，建议排在发送前约 1 小时。

**对我们的启示**
1. **弹窗相同，保持**：「回流身份（登入时判定）」由服务端在登录时比较本次与上次登录间隔是否不少于 N 天，成立则整个回流周期（D 天）都算回流，回来第一次进大厅即可命中。这与 PlayFab 挂在登录事件上的规则、Unity 按会话拉取时的属性判定是同一思路，是在批量标签约束下拿到准实时身份的正确做法。「新增身份（登入时判定）」同理。
2. **召回推送不同，建议补即时排除（小改动）**：我们靠每次发送时读最新批次把已回来的人移出，空窗最长约一个批次；若「回流」或「N 天未登入」标签按日计算，空窗可到一天。OneSignal「回来即退出」、Braze 事件退出都是即时的。建议召回类推送（发送对象含「N 天未登入」类群组时默认勾选）加即时排除「发送前 N 小时内登录过的不发」，N 默认 24，可改。读按会员已存的最近一次登录记录（版本条件已要求按玩家存最近登录值），与敏感状态一样在发送时即时判定；被排除的人记不在受众原因「发送前已登录」。
3. **把进出时点写给运营**：群组下拉里「回流」旁注明「登录后最迟一个刷新批次进入；弹窗可改用回流身份（登入时判定）」，避免运营以为群组是即时的（S6）。
4. **按行为推送就是触发型**，与 TE 触发型任务、PlayFab 事件规则同类，保持。

**对我们的启示**
1. **相同，保持**：六处（弹窗、快显、推播、短信、Facebook、LINE）读同一个最近全部算完的批次、同一套排除口径。弹窗每次请求时判定，比 Braze 会话开始时拉取并缓存更及时。
2. **人数分层相同**：顶尖产品的分群总数不等于渠道可达数（Braze、TE、OneSignal），与我们「原始符合 → 排除后 → 各推送方式可触达 → 预计发出」一致。建议每处人数旁固定写口径与批次时间：群组页「原始符合，批次 10/12 15:25」；推送「可触达（推播）」；弹窗「预计人数（未扣固定排除，弹出时扣）」，避免两处数字被当成同一个数（S10）。
3. **时点差异写给运营**：同一群组，推送用开始发送那一刻的批次，弹窗用每次请求时的批次，两者可能差一个批次。玩家查询记录命中所用的批次号，客服据此解释「推送收到、弹窗没弹」这类问题。

1. **规则型相同，保持**：Unity 标准 Audience、Airship 生命周期名单都是规则型、按天刷新；我们五类人群都按规则建标签（定 17），每日 06:00 或每 25 分钟刷新，方向一致。
2. **评审时核对未活跃分层（小改动）**：Unity 用「沉睡 7–14 天、流失 ≥14 天」两档；我们现有「7–30 天未登入」「30 天未登入」，回流身份默认 N＝7 天。建议评审时确认未登入分档与回流的 N 衔接（未登入满 N 天的人回来即算回流），缺档时补一个标签脚本。

4. **首次识别相同**：Unity 新玩家按首次会话 ≤2 天、CleverTap 首次使用为实时分群；我们弹窗有「新增身份（登入时判定）」，游戏外用「新增·注册次日未再登录」等每日换批的标签（S5），保持。
