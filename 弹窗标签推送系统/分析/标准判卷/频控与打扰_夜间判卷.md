# 频控与打扰判卷：方向对、对标扎实，但「重要推送能否发出」走不通，紧急类成了新的豁免口子，方案内外边界在先做清单里混写

判卷对象：`分析/内容补强_频控与打扰_夜间.md`（下称「作品」）。判卷人视角：做过推送平台频控与消息治理的产品经理，第一次看本项目。未改作品。

## 总判

| 维度 | 判断 | 依据 |
|---|---|---|
| 方向 | 对 | 消息类别、重要推送优先、同活动去重、短信费用封顶四块，是推送平台频控的标准拼图；对标四家有出处，「受理才计数」「豁免＋计入方式」保留的理由成立 |
| 核心场景能否走通 | **不能** | 周五大型活动走查：重要推送只在推播上有 1 个预留名额；短信、LINE、Facebook 上限为 1 时预留取值只能是 0；预留不覆盖合计与每周上限；最小间隔还会把 20:00 活动开始推播拖到 20:55 |
| 是否误伤 | 有三处 | 预留天天吃掉一个普通名额；服务通知内容校验挡住「補償禮包」；服务通知限「名单或群组」挡住全体维护通知 |
| 是否过度 | 局部 | 合计每周、同一方式最小间隔、页面上的时区字段可删；超限顺延到次日可降为后做 |
| 方案外边界 | 没写清 | 同活动去重、合计默认开都标「方案外·跨方式」，却排在第六节「低成本先做」第 4、5 项；原型已有合计开关，与「跨方式上限为方案外」的关系没交代 |
| 字段能否画 | 基本能 | 缺三处：类别规则表哪些格可改、用什么控件；页 11 九块的分组；改动何时生效、进不进变更记录 |
| 结论 | **补 4 处后再并入** | 预留机制改为能覆盖所有方式与所有上限；重要推送不受最小间隔；紧急类加护栏；第六节按本期／方案外分开 |

## 走查记录

设定按作品默认值：推播每日 2（预留 1 给重要）、短信 1、Facebook 1、LINE 1；合计每日关；每周关；最小间隔开、60 分钟；同活动去重开、每人每天 1 条；勿扰四种共用 00:00–08:00。

### 场景一：周五晚 20:00 大型活动，白天已有日常推送

| 时刻 | 操作 | 按作品规则的结果 |
|---|---|---|
| 09:30 | 按行为推播（普通） | 发出，推播 1／2 |
| 12:30 | 任务提醒推播（普通） | 已收 09:30 的人被拦：普通只能用 2 − 1 ＝ 1 条（5.3） |
| 14:00 | 按行为短信（普通） | 发出，短信 1／1 |
| 18:00 | LINE 日常（普通） | 发出，LINE 1／1 |
| 上午建 20:00 定时推送时 | 看「确认与测试」预估 | 定时按「近 7 天同一时刻已收」估算（5.10），不看今天已排的推送，预估偏少；表单也不提示「今晚已有重要推送、本条将占用名额」 |
| 19:55 | 活动预告推播 | 标普通：被拦（普通名额已用）。标重要：发出，推播 2／2 |
| 20:00 | 活动开始推播（重要） | 预告标了重要的人：每日 2 已满，被拦。预告没发出的人：发出，但若该人 19:55 收过其他推播，被最小间隔顺延到 20:55 |
| 20:00 | 活动开始短信、LINE（重要） | 全部被拦：短信、LINE 上限为 1，预留取值「0 到上限 − 1」只能是 0（5.3），白天已用满 |
| 若开了每周上限（推播 8） | — | 周一至周四每天收满 2 条的人，周五重要推送在第 9 步被「每周」拦下；预留只扣按方式每日，不扣每周（5.2 自带例子正是这种情况） |
| 若开了合计每日（3 条） | — | 09:30、14:00、18:00 三条已占满，20:00 重要推送在第 8 步被拦；预留不覆盖合计 |

**结果**：重要推送一天只有推播 1 条能保证；预告与开始两条重要推送只能保一条；短信、LINE、Facebook 的重要推送完全没有保障。运营唯一的出路是勾「本条不受频率上限」，回到作品想解决的豁免滥用。

### 场景二：周三 06:00–10:00 停服维护与补偿通知

| 时刻 | 操作 | 按作品规则的结果 |
|---|---|---|
| 周二 22:00 | 维护预告，推播＋LINE，类别「服务通知」，对象全部玩家 | 服务通知「可选范围：名单或群组」（5.1），全部玩家能否选不明确；若不能，运营只能改选营销（受上限）或紧急 |
| 周二 22:00 | 同上 | 服务通知受勿扰（默认顺延），22:00 不在勿扰内，发出；不计入当天条数，晚间营销不受影响 ✓ |
| 若预告排在 04:00 | — | 顺延到 08:00，晚于维护开始；作品没有「有截止时刻的通知顺延后已过期」的处理 |
| 周三 06:00 | 停机公告，类别「紧急」 | 勿扰内照发 ✓；须填原因并「走高风险确认（推送配置 5.6）」，但推送配置 5.6 已把高风险确认收窄为三类触发，紧急类不在其中，两份文件冲突 |
| 08:30 | 延长维护通知 | 选紧急或服务通知都能发；同一天服务通知已用 1 条，未到 3 条上限 ✓ |
| 10:30 | 补偿到账「維護補償：登入領取禮包」，服务通知，推播＋短信 | 内容校验命中「禮包」，不能选服务通知（5.1），被迫改营销（受上限、可能被截断）或改紧急 |
| 10:30 | 补偿短信发给退订过营销短信的人 | 法务确认前按全退，不发；合理 ✓ |

**结果**：维护与补偿能发出，但要绕两道弯；「紧急」没有数量、内容、勿扰内渠道的约束，会成为运营的新兜底选项。

### 场景三：同一活动推播＋短信＋LINE 三管齐下

| 步 | 按作品规则的结果 |
|---|---|
| 三条都排 20:00，所属活动相同 | 同活动去重按「推播 → LINE → Facebook → 短信」顺序判断，每人只收 1 条；短信则数大降 ✓ |
| 去重依据 | 前一方式「服务商受理」即算已发。推播受理后实际送达、展示比例低，被推播「受理」的人失去 LINE、短信触达，活动总到达反而下降 |
| 三条推送同时到点、推播 4,310 人要发数分钟 | 「同一分钟到点按方式顺序判断」与「受理才计数」并存：LINE 判断时推播多数还未受理，去重按计划还是按受理没写 |
| 运营就是要同一人收三条 | 每条要勾「本活动允许再发」；之后最小间隔 60 分钟把 LINE 顺延到 21:00、短信 22:00；若开了勿扰按方式分设（短信 21:00–09:00），短信再顺延到次日 09:00，活动已结束 |
| 所属活动不填 | 去重只对填了所属活动的营销推送生效，不填即绕开 |

**结果**：省钱的目的达到；要「多方式加大覆盖」时，规则互相叠加，运营很难预判每人会收到哪条、几点收到。

## 新缺口

| 缺口 | 影响 | 补法 | 重要度 | 成本 |
|---|---|---|---|---|
| 上限为 1 的方式无法预留 | 短信、LINE、Facebook 的重要推送在白天已发过时必被拦（场景一） | 把「预留」改为「重要推送额外额度」：每种方式可设 +0／+1，重要推送可超出每日上限这么多条；或允许预留等于上限（只重要可用） | 高 | 小改动 |
| 预留不覆盖合计、每周上限 | 开了合计或每周后，周五重要推送在第 8、9 步被拦 | 重要推送的额外额度同样作用于合计每日、每周；第四节判断顺序写明 | 高 | 小改动 |
| 最小间隔拖延重要推送 | 20:00 活动开始被顺延到 20:55 | 重要推送不受「任意两条」间隔；默认间隔改 30 分钟 | 高 | 小改动 |
| 紧急类别没有护栏 | 不受上限、勿扰、费用封顶，也不校验内容，运营不审批时成为新的豁免口子；凌晨可对全体发短信 | 紧急在勿扰内默认只发推播，短信、LINE 须单独勾选；高风险确认的触发条件加「紧急类」（同步改推送配置 5.6）；当天紧急 ≥ 2 次时页顶提示，日报单列（已有） | 高 | 小改动 |
| 预留天天吃掉一个普通名额 | 没有重要推送的日子，日常推播实际只能发 1 条，日常触达下降 | 若保留预留：只在当天有覆盖该人的重要定时推送时才预留；改用额外额度则此问题消失 | 中 | 小改动 |
| 建推送时看不到当天其他推送 | 白天的日常推送不知道会挤掉晚上的重要推送；定时预估不含当天已排推送 | 新建表单「类别与上限」块加「当天已排」：同一方式已排几条、与重要推送重叠多少人；定时预估加上当天已排计划 | 中 | 小改动（估算已有） |
| 重要推送被拦无告警 | 重要、服务通知被拦时运营事后才知道 | 告警（数据能力 4.11）加「重要／服务通知／紧急推送拦下人数 > 0」 | 中 | 小改动 |
| 同活动去重按「受理」判，推播受理不等于送达 | 多方式活动总到达下降 | 「每人每天最多 N 条」与「方式先后」移到「活动」实体上，每个活动自己设；全局只给默认值。推播按送达回执判断列为后续 | 中 | 小改动 |
| 服务通知校验与范围误伤 | 「補償禮包」被挡；全体维护通知可能选不了 | 关键词命中改为提示＋填原因，不阻断；删「名单或群组」范围限制 | 中 | 现有可做（改规则） |
| 有截止时刻的通知被勿扰顺延后过期 | 04:00 维护预告顺延到 08:00，维护已开始 | 服务通知填「截止时刻」时，顺延后晚于截止即放弃并提醒运营 | 低 | 小改动 |
| 所属活动可不填，绕开去重 | 去重形同虚设 | 营销类必填所属活动，可选「日常」作为一个活动 | 中 | 现有可做 |
| 看不到打扰的后果 | 上限设多少只能凭感觉；数据能力 4.8 只有收到条数与拦下，没有退订、封锁 | 4.8 加一张：按当天收到条数分组的次日短信退订率、LINE 封锁率、推播关闭率 | 中 | 小改动（依赖退订、封锁有时间戳） |

## 含糊处

| 位置 | 含糊在哪 | 建议写法 |
|---|---|---|
| 第三节 P1、P2 与第六节第 4、5 项 | 标「方案外·跨方式」的同活动去重、合计默认开，排进「低成本先做」，读者会当本期做 | 第六节拆成「本期（每日上限项下）」与「方案外后续（若提前做）」两张表 |
| 结论第 1 条与已定事项 | 原型页 11 已有「游戏外合计（可选，默认关）」，已定又说跨方式上限为方案外；本期到底交付开关还是不交付 | 写明：本期原型保留开关、默认关、不宣传；开启与默认值属方案外 |
| 5.3「0 到（每日上限 − 1）」 | 上限为 1 的方式实际不可预留，正文未提 | 见新缺口第一行 |
| 5.1「走高风险确认（推送配置 5.6）」 | 推送配置 5.6 的三类触发不含紧急 | 两边对齐，在推送配置 5.6 加第四类或此处删引用 |
| 5.4「同一分钟到点按方式顺序判断」 | 判断依据是计划名单还是已受理名单；发送持续数分钟时如何处理 | 写明：同活动同一分钟到点的多条，按计划名单串行判定，不等受理 |
| 5.1「计入当天条数」 | 服务通知选「计入」时，计入按方式每日还是只计入合计（5.2 只写了合计） | 两处统一 |
| 5.1「改动对之后的发送生效」 | 已排好的定时、按行为推送用新规则还是创建时规则 | 写明：到点时按当时规则判断，确认框列出受影响的已排推送 |
| 第四节「每人次只记第一个命中的原因」 | 第 6 步顺延后重新判断时，最终原因记哪一个 | 写明：顺延后以最终结果的原因为准，顺延记为过程 |
| 5.1 维护预告「提前 ≥ 2 小时」 | 不足 2 小时的预告算服务通知还是紧急 | 删此限定，或写明不足 2 小时归紧急 |

## 可删

| 项 | 理由 |
|---|---|
| 5.2「游戏外合计每周」 | 按方式每周与合计每日已能挡住；多一条规则只增加拦下原因与解释成本 |
| 5.5「同一方式两条」间隔 | 与「任意两条」间隔、按方式每日上限重叠 |
| 5.6 时区字段「按玩家所在地（后续）」 | 页面上放不可选的后续选项无用；保留「先取数」分支即可 |
| 5.1「可选范围：名单或群组」 | 误伤全体维护通知，防绕过已由内容校验承担 |
| 5.8 超限顺延到次日（降为后做，不删） | 次日 08:00 补发前一晚的活动预告，内容多已过时；实际需要它的场景少，先只做丢弃 |
