# 推送后台「核心写死迁入」对标（2026-10-19）

资料均来自 WebFetch 读到的官方文档或官方博客；标「未读到原文」的是没核实的部分。

### D1 盘点与登记
| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| LaunchDarkly code references | 开源工具 ld-find-code-refs 接进 CI/CD 或 cron 扫描代码，把仓库、提交、文件、行号推给每个旗标的「Code references」页（附上下各 2 行代码），平台不碰源码；引用删光并重扫后记一条 extinction 事件 | [code references](https://launchdarkly.com/docs/home/code/code-references) |
| Fowler／Hodgson Feature Toggles | 开关当库存管：新增时就挂「移除任务」；元数据带过期日，过期后测试或启动直接失败；精益做法给开关数量封顶，新增须先删旧 | [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) |
| Uber Piranha | 输入「旗标名＋预期行为＋作者」，生成删码改动派给旗标作者；流水线每周跑，机器人催未处理任务 | [Piranha](https://www.uber.com/blog/piranha/) |

**对我们的启示**：①登记表每项存「开关键、负责人、代码位置」，CI 扫描开关键，登记页显示「代码引用数」；开关仍在「原处」而引用数为 0，说明接入点丢了，报警。②登记当天生成「移除任务」和到期日（切换完成日＋30 天）。
**不照搬的地方**：扫描只能找到已接入 SDK 的开关，找不到尚未登记的写死项；首轮盘点（34 种服务端推送、客户端弹窗与快显入口）须人工完成，扫描只核对已登记项。体量几十项，不需要 Piranha 的自动改码。

### D2 迁移的阶段模型
| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| LaunchDarkly 迁移旗标 | 六阶段 off→dualwrite→shadow→live→rampdown→complete：dualwrite 读旧、写两边；shadow 读两边、仍返回旧结果；live 返回新结果、旧作备份；rampdown 只读新；complete 才可下线旧系统。dualwrite 的门槛是新旧数据一致；各人群可独立推进、可退回上一阶段。shadow 阶段文档未给数值门槛 | [迁移指南](https://launchdarkly.com/docs/guides/flags/migrations)　[定向](https://launchdarkly.com/docs/home/flags/target-migration) |
| Stripe 在线迁移 | 四步：双写（比例逐步加大）→改读（Scientist 比对，不一致报警）→改写→删旧；每次改动不超过几百行；清理前用离线任务确认无缺漏 | [Online migrations](https://stripe.com/blog/online-migrations) |
| Fowler Strangler Fig | 先找「接缝」，先换小组件，按块把行为搬进新系统；共存用的过渡代码迁完后移除；文章未讲回退 | [Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html) |

**对我们的启示**：①每个写死项一条状态线，阶段名可见：「已登记→规则已建（草稿）→影子比对→仅测试账号→全部玩家→观察期→已清理」，页面列出每阶段通过标准（如影子比对：连续 N 天应发与实发一致）。现有设计缺「影子比对」一步。②按单项推进，不整批切。
**不照搬的地方**：LD 的 dualwrite、rampdown 服务于数据存储双写。我们切的是「谁触发展示或发送」，两边同时真发会重复打扰玩家，所以影子只能是后台空跑、只记录。

### D3 新旧一致性核对

| GitHub Scientist | 旧逻辑（control）与新逻辑（candidate）都跑、顺序随机；永远返回 control 的结果；记录差异与耗时；candidate 异常只记录不抛。只用于无副作用的读，让 candidate 写数据是「dangerous and incorrect」；可按百分比启用；差异的根因可能在旧代码或数据 | [Scientist](https://github.blog/engineering/infrastructure/scientist/) |
| Braze／Satori 的预填 | Braze：campaign 可复制到另一工作区，但落地为草稿，上线前须改 segment 与触发条件。Satori：配置导入导出可单选 Feature Flags、Live Events、Message Schedules | [Braze](https://www.braze.com/docs/user_guide/administer/global/create_and_manage_workspaces/migrate_workspace_data)　[Satori 版本记录](https://heroiclabs.com/docs/satori/concepts/introduction/release-notes) |

**对我们的启示**：①影子比对只比「决策」：34 种服务端推送，后台规则空跑不发送，每天把「应发对象数＋时刻＋文案」与旧任务实发日志对账，差异清单上页面，归因分「新规则错／旧逻辑错／数据错」。②新规则由研发从旧配置（时间、文案、对象条件）导出成草稿，运营只审不抄，草稿不生效。
**不照搬的地方**：Scientist 在同一次请求里同时执行；客户端弹窗在同一设备上不能新旧都跑而不重复展示，客户端项只能靠登记的触发条件加展示日志离线核对，再加测试账号真机核对。

| Unity／PlayFab／LD Guarded | Unity：rollout 低于 100 时按 user ID 随机分配，同一玩家跨会话一致。PlayFab：实验变体含 IsControl 对照组，并提示样本比例不匹配（SRM）。LD guarded rollouts 同样等分、单步 ≤50% | [Unity](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings)　[PlayFab](https://learn.microsoft.com/en-us/gaming/playfab/features/analytics/experiments)　[LD guarded](https://launchdarkly.com/docs/home/releases/creating-guarded-rollouts) |

**对我们的启示**：①「测试账号→全部」两档保留，规则表预留「放量范围」枚举（测试账号／百分比／全部），以后加按比例不改表；放量单位用玩家 ID 哈希，同一玩家恒在同一组，调大只追加。②评估用同期对照而非前后 7 天：同一时刻「已切换组 vs 未切换组」，可排除星期、活动日、版本差异。月活约 6 万，1% 只有约 600 人，档位从 10% 起更实际（推断）。
**不照搬的地方**：Firebase、LD 的对照组测「新功能效果」；迁移要证明「没有变化」，主证据是行为一致，小盘子统计检验功效低，所以影子比对为主、对照组只当护栏。

### D5 切换时刻的去重

**对我们的启示**：①去重键＝（玩家 ID，规则或写死项 ID）；切换时把旧「已显示／已发送」带原始时间写入，写入本身不触发发送（对应 Customer.io 回填、Braze 属性建模）；状态型项导入为「已用次数」。②规则发布时自动附带「app 版本≥X」（X＝原处能读开关的最低版本）：旧版本照旧显示写死内容、后台不对其下发，避免一人两份。③切换前测试账号对账「后台已下发」与「客户端已展示」两个数，下发而未展示即冲突。
**不照搬的地方**：上述指南换的是服务商和令牌；我们通道与令牌不变，只换「谁决定发什么」。「已显示过」若只存在设备本地，服务端导入需客户端先上报，官方资料里没有这类做法（未读到原文）。

### D6 旧版本客户端与开关读取失败
| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| LaunchDarkly | 客户端连不上：先用内存里最近存的值，没有再用代码里的 fallback；fallback 设为「与应用当前正常工作状态一致的稳定行为」，安全合规场景用更保守的；初始化失败绝不阻塞应用，客户端超时建议 100–500 ms。移动端缓存细节原文 403（未读到原文） | [resilience](https://launchdarkly.com/docs/guides/sdk/resilience)　[offline mode](https://launchdarkly.com/docs/sdk/features/offline-mode) |
| Firebase Remote Config | 必设 in-app defaults；启动立即激活「上次拉到的值」，新值下次启动才生效；默认最小拉取间隔 12 小时；条件可按 app 版本、语言、国家、受众。minimum_version 示例：默认值设 "1.0.0"，离线或拉取失败不会锁死用户；强更用不可关闭对话框，可选更新用可关闭提示 | [loading](https://firebase.google.com/docs/remote-config/loading)　[get started](https://firebase.google.com/docs/remote-config/android/get-started)　[最低版本](https://firebase.google.com/docs/remote-config/use-cases/minimum-version) |
| Unity／Satori | Unity：启动或后台超 30 分钟回来才刷新设置，离线用上次缓存，变量先给默认值，可按 unity.appVersion 定向。Satori：连不上或无覆盖时取 flag 默认值 | [Unity](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings)　[Satori flags](https://heroiclabs.com/docs/satori/concepts/remote-configuration/understand-feature-flags/) |

**对我们的启示**：①官方一致做法是「读失败退回已知可用行为」，我们定的「不显示写死」是防重复的刻意取舍；建议登记表每项记「读失败默认」，并在设备缓存最近一次读到的开关值与时间（三家都缓存），有缓存按缓存，无缓存才不显示。②每月统计旧版本占比，据此定强更节奏。
**不照搬的地方**：强更对休闲游戏是留存风险，6 万月活下先用可关闭提示。旧客户端里的写死代码一直在跑，「能否删写死代码」取决于旧版本占比，不是 30 天一到就行。

### D7 发现问题与回退

|---|---|---|
| LaunchDarkly | kill switch 模板是永久旗标。Guarded rollout：约每 10 秒检查一次，每变体至少 10 个 context 才下判断，序贯检验显著变差即回归，每指标可勾「自动回退」；通知维护人，可到 Slack、Teams、PagerDuty；低流量会拖慢检测。Flag triggers：监控工具调专属 URL 关旗标，限速防来回翻。均需特定套餐 | [regression](https://launchdarkly.com/docs/home/releases/regression-detection)　[triggers](https://launchdarkly.com/docs/home/releases/triggers)　[kill switch](https://launchdarkly.com/docs/home/flags/new) |
| Firebase Rollouts＋Crashlytics | 对比两组崩溃与 ANR；回退＝比例降到 0%，或回滚模板版本（回滚本身生成新版本，例：从 10 回 6 生成 11，最多存 300 版）。生效时延：实时更新绕过最小拉取间隔，否则按 12 小时；实时连接仅 App 在前台保持。文档未给时延数字 | [rollouts](https://firebase.google.com/docs/remote-config/rollouts/about)　[templates](https://firebase.google.com/docs/remote-config/templates)　[real-time](https://firebase.google.com/docs/remote-config/real-time) |

**对我们的启示**：①「切回」按钮旁显示预期生效时延（服务端推送：下一个调度时刻；客户端：下次启动或拉取）。②护栏指标先做「告警＋人工切回」：弹窗展示量、推送送达数相对同时段基线的偏差；仅展示量为 0 或暴增数倍这类明显故障才考虑自动切回，并加限速防反复翻转。
**不照搬的地方**：LD、Firebase 的自动回退依赖等大对照组加足够样本；我们只有两档放量、月活约 6 万，序贯检验长期凑不够样本，先用阈值告警。

| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| Firebase Remote Config | 「不发布更新即可改变行为与外观」，前提是代码已读该参数且设了 in-app defaults。用例：按平台语言区分的促销横幅、JSON 配置复杂实体、最低版本；官方建议不要在用户操作时改界面。专门划「哪些不该放 RC」的最佳实践页未读到（404） | [use cases](https://firebase.google.com/docs/remote-config/use-cases)　[loading](https://firebase.google.com/docs/remote-config/loading) |
| Unity／PlayFab | Unity 建议首发就放「惰性（inert）」设置，之后再按受众启用；可设起止时间（UTC）与优先级 1–1000。PlayFab：variables 映射的配置「无需新代码部署」；Title Data 适合全局常量或静态数据，不适合当全局变量 | [Unity](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings)　[PlayFab](https://learn.microsoft.com/en-us/gaming/playfab/features/analytics/experiments) |
| Satori | 直播事件运行中可编辑所有值字段、无需发版；变体绑受众，按位置顺序首个匹配生效；优先级：实验＞直播事件＞变体＞默认 | [flags](https://heroiclabs.com/docs/satori/concepts/remote-configuration/understand-feature-flags/) |

**对我们的启示**：①划界：不发版＝已发布「弹窗／快显模板」的参数（文案、图片、跳转目标页、时间、对象、次数上限、生效版本）；必须发版＝新模板或布局、新位置、新跳转目标类型、新触发事件；每个模板声明「可改字段白名单」。②保存时标注生效时机：服务端推送＝下一个调度时刻；客户端弹窗＝下次启动，避免玩家使用中界面突变。③每次保存产生版本，回滚＝以旧版内容新建一版（Firebase 模板做法）。
**不照搬的地方**：Unity 的 JEXL 表达式（≤500 字符）、PlayFab 的 JSON 是工程师编辑方式；运营用表单字段加预览，不暴露表达式。

### D9 完成与清理
| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| LaunchDarkly | 默认「Ready for code removal」：临时旗标＋关键环境均 Launched（单一变体、7 天无配置变更）＋≥30 天＋仍有代码引用＋非他旗前置；「Ready to archive」：Inactive（≥7 天未被评估）＋≥30 天＋无代码引用。先删代码再归档；归档后旗标只返回 fallback；删除不可逆。迁移模板本身是临时旗标 | [flag status](https://launchdarkly.com/docs/home/flags/flag-status)　[archive](https://launchdarkly.com/docs/home/flags/archive) |
| Unleash／Fowler | Unleash：Release 与 Experiment 预期寿命 40 天、Operational 7 天、Sunset 90 天，超期标「疑似过期」；标过期产生事件，可通知 Slack、让含过期旗标的构建失败、自动开 PR 删码。Fowler／Hodgson：release 开关通常一两周；退役要同时删配置与引用代码 | [Unleash 概念](https://docs.getunleash.io/concepts/feature-flags)　[Unleash 技术债](https://docs.getunleash.io/reference/technical-debt) |
| Uber Piranha | 旗标 8 周未改动判过期（各团队可配）；每周生成删码 diff 派给作者；机器人催未处理任务；累计清理约 2000 个旗标 | [Piranha](https://www.uber.com/blog/piranha/) |

**对我们的启示**：①现有「30 天未切回＋负责人确认」与 LD 默认 30 天一致；补三条自动校验：自上次切回起算（任何切回清零）、扫描仍显示写死代码存在才进「可删除」、旧版本占比（我们特有）。②满 30 天当天给负责人推待办，之后每周催一次。③进入「已清理」后锁住切回按钮，因为 LD 归档后旗标只返回 fallback，切回已无意义。
**不照搬的地方**：Piranha 针对数千旗标做 AST 改码；我们几十项，用带清单的 PR 即可。Unleash 的 40 天针对持续发版的旗标，我们受客户端版本周期约束。

### D10 防止新增写死
| 产品／方法 | 它们怎么做（机制、步骤、默认值） | 出处链接 |
|---|---|---|
| Unity／Firebase／PlayFab | Unity：首发就放惰性设置。Firebase：代码一律用 get 读参数，来源是默认值还是后台对代码透明。PlayFab：variables 变体无需新代码部署。共同点：先在客户端留好参数化读取点，后来的活动才能不发版 | [Unity](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings)　[Firebase](https://firebase.google.com/docs/remote-config)　[PlayFab](https://learn.microsoft.com/en-us/gaming/playfab/features/analytics/experiments) |

**对我们的启示**：①今天的写死清单当 baseline，CI 加规则（自定义 lint 或 grep）：弹窗、快显、推送调用处出现字面量文案、时间、对象即报错，除非走后台 SDK 封装或已登记到期日。②需求评审模板加一问：「文案、时间、对象、位置哪些由运营改？不可改的写明理由和发版计划」。③客户端预置通用弹窗模板与位置槽，新活动先走模板。
**不照搬的地方**：12-Factor 的「配置」指部署间差异（数据库地址、密钥），我们借的是「会变的东西不写进代码」的原则。HardcodedText 只管 Android 布局，我们的客户端引擎待确认，规则要定制。
