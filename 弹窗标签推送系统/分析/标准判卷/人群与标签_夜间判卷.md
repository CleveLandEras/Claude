# 人群与标签夜间判卷：方向对、可圈出五类人群，但还不能直接交研发排期，高缺口 5 项

判卷时间：2026-10-15 23:03。判卷人视角：做过 Braze／MoEngage 类分群与标签系统的资深产品经理，兼看游戏后台研发排期。
待判：`分析/内容补强_人群与标签_夜间.md`（下称「作品」）。对照：`来源资料/产品计划原文_1010.md`；`推送系统后台集成需求/4_需求文档.md`（grep「标签」「群组」）。不评措辞。

## 结论

1. **运营能否圈出五类人群：条件性能。** 新增、回流用现有标签；破产按弹窗位置；潜在付费、潜在流失要等两个新标签建出来。圈法本身成立，但潜在付费口径有漏洞（见 H4），上线后人数可能与核对数对不上。
2. **能否直接交研发排期：不能。** 作品的方向（群组引用群组、嵌套 1 层、人数预览、引用清单、变更记录）与 Braze 做法一致，可作底稿。但运算顺序、刷新一致性、人数口径这三处规则还会让研发写出不同结果；另外缺承载文档、实现方、逐项估工与验收。补完 H1–H5 才能进排期。
3. **与目标的贴合**：目标原文是补「或」、后续补「交集」，以及五类人群逐步客制化。作品覆盖了这几项，范围没有越界。

## 逐项判读

| 项 | 判读 | 程度 |
|---|---|---|
| 群组交集：定义、字段、上限、示例 | 定义清楚（且处＝交集、或处＝并集、排除处＝排除整组）；示例与需求文档去重示例（重叠 1,320）一致 | 够 |
| 交集：循环引用 | 只写了「保存 A 时校验 B 没有引用其他群组」。漏了反向校验：B 已被 A 引用后，再编辑 B 加入群组条件，会形成 2 层嵌套或循环 | 不全（H2） |
| 交集：刷新与人数一致 | A 用 B「最近一次刷新的名单」，A 自身标签用当时数据，两者时点不同。结果是 A 的人数不等于此刻 B∩C，预览数、当前人数、发送时人数三者也会不一致。「不早于被引用群组最晚一次」只是约束，没有写调度顺序和名单版本 | 缺（H2） |
| 交集：异常 | 停用拦截、0 人、改被引用群组时的确认已写。「依赖刷新失败沿用上次名单」没有陈旧上限，可能连续几天按旧名单发送 | 不全（H2） |
| 「或」、群组内「排除」的确认清单 | 已上线／未上线两栏的补法可行（任一档新标签代替、互斥放到规则层，需求文档 4.2.1 已有排除群组） | 够 |
| 混合运算顺序 | 「从上到下逐行计算」有陷阱：「A 排除 B 或 C」＝(A−B)∪C，被排除的人会被后面的「或」加回来。Braze 的排除恒为「且非」、优先于纳入条件 | 错（H1） |
| 新标签：潜在付费 | 没有注册天数边界，注册 3 年从未储值的高押注玩家也算「潜在付费」；核对数 528／2,092 取自「注册 7–14 天未储值玩家」，母体与定义不同，无法核对；押注是否含赠币、单位未写 | 漏洞（H4） |
| 新标签：潜在流失 | 条件链完整（注册满 28 天、近 7 天有登录、前段≥4 天、近段 2–3／1 天）。但核对数「约 7,880」是示例值，与 5.4 显示示例同一个数，不是真实基准；「退出」只写了回升，没写近 7 天无登录时转为流失或回流 | 不全（H4、中） |
| 新标签：刷新与时间窗 | 每日 06:00 刷新，同时写「近 14 天（含当天）」：06:00 时当天只有 6 小时数据，口径前后不一 | 不全（中） |
| 人数预览 | 触发方式、逐行累计人数、2 秒／15 秒、与当前生效人数并列，设计好。但「下拉读剔除后的数」与需求文档推送侧「群组人数 → 排除后（含固定排除）」冲突：要么扣两次，要么层级错位。剔除名单也不一致：5.4 写「机器人、测试、已注销」，推送侧写「黑名单、机器人与测试」；新标签定义里又剔了一次机器人 | 冲突（H3） |
| 条件说明 | 字段、必填、存量处理清楚 | 够 |
| 引用清单与停用保护 | 引用方覆盖上层群组、弹窗、推送（含只限群组、常用受众），拦截规则清楚。缺两点：标签被群组引用时的停用保护；编辑（不是停用）在用群组时，确认框只列上层群组，没列上架弹窗与排程推送 | 不全（中） |
| 变更记录 | 对象、内容、看板竖线清楚；看板按人群出图需要「群组 → 看板图」的对应关系，未写 | 小缺（低） |
| 排期要素 | 承载文档待 Dk 定；标签系统改动由哪个团队实现未写（需求文档 3.5 排除了标签设定改动）；8 项设计只有 5.1 有验收条，全部没有工时档 | 缺（H5） |

## 缺口与补法

### 高

| 编号 | 缺口 | 补法 |
|---|---|---|
| H1 | 混合运算顺序会让排除失效 | 规定为：先算全部「且／或」纳入条件（且优先于或，或按行顺序但写明），最后统一减去所有「排除」项，与行的位置无关（同 Braze）。原型页 19 写 2 个示例，验收加「A 排除 B 或 C 的结果中不含 B 的成员」 |
| H2 | 交集的刷新一致性与嵌套校验不完整 | ① 按依赖顺序调度：被引用群组先刷新，上层群组在同一刷新批次里用同一版本名单计算，名单带批次号；② 校验改为双向：已被引用的群组不能加入群组条件，有群组条件的群组不能被引用；③ 依赖群组连续 2 个周期（约 50 分钟）未刷新时告警，推送确认页标红「名单已过期」，超过 24 小时排程推送暂停并列入待处理；④ 验收补「B 被引用后加群组条件，保存被拒」「同批次下 A 人数＝B∩C」 |
| H3 | 群组页与推送侧人数口径冲突 | 群组人数统一为原始符合人数，不剔除任何账号（新标签定义里也不剔）；固定排除只在推送／弹窗侧一处扣除，沿用需求文档 4.1.1「四」逐层显示。群组页预览只附一行参考「其中固定排除约 X 人」。剔除名单以需求文档为准，「已注销」是否进固定排除单独确认 |
| H4 | 潜在付费口径漏洞，两个新标签的核对数不可用 | 潜在付费加注册天数范围（如 7–60 天，由 Dk／数据定），或者明确不设上限并写理由；写明押注计价（是否含赠币）；核对数改为按最终定义实跑一次 SQL 得到的人数，潜在流失同样实跑，替换示例值；上线首日偏差阈值保留 30% |
| H5 | 缺排期要素 | Dk 定承载文档后，每项补：实现方（推送后台或标签系统）、工时档（小／中／大）、前置依赖（5.1 依赖 5.2 确认，5.3 依赖数据人员写 SQL）、验收条（每项至少 2 条，可测） |

### 中

| 缺口 | 补法 |
|---|---|
| 编辑在用群组时，看不到对上架弹窗与排程推送的影响 | 保存确认框并入 5.6 引用清单，列出上架和排程的引用方及改前改后人数 |
| 标签被引用时无停用保护 | 5.6 扩到标签：被群组引用的标签停用时拦截，并列出群组 |
| 新标签时间窗与刷新时刻矛盾 | 改为「截至前一自然日的近 14 天」，06:00 刷新 |
| 潜在流失的退出写不全 | 写明「近 7 天无登录时离开，转由流失／回流口径接管」 |
| 潜在付费与新增大量重叠，没写优先级 | 引用编排文档中的人群互斥顺序，或在 5.1 示例里补「潜在付费排除新增」 |
| 引用上限 5 个无依据 | 按已知交叉格的最大用量定，或者标为可配置 |
