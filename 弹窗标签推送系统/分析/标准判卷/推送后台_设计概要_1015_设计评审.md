# 推送统一后台 · 设计评审（10/15）：最重要的 4 个问题
1. 【乙，最先会被问】弹窗改规则保存即生效，没有测试账号预览、没有确认页：「不设审批、防错靠确认页＋测试发送＋可停止」在曝光量最大的弹窗页只剩「停用」；概要第 3 页「所有推送走同一套流程」与原型不符（原型页 #9、T10）。
2. 【甲，条件成立时】只能按「全部玩家／标签群组」选对象，没有按会员编号名单发送；短信现在就是营销侧按名单发，名单建群又在本需求范围外——若「会员标签设定」不能从名单建群，短信切换后中奖、补偿类名单发不出去（原型页 #3 发送对象、需求 2.2、3.5）。
3. 【乙】推送之间不能协同：排除只能选标签群组，不能排除「推送 N 的对象」；没有活动归组和跨推送排程视图。同一活动推播＋短信＋Facebook＋LINE 各自计上限，一人当天收 4 条；短信费也无法只花在推播不可达的人身上（原型页 #3、#6 同一群组推播可触达 4,310、短信可触达 6,690）。
4. 【乙】弹窗上限与互斥的规则在真实场景会出问题：大厅与破产合计 8 个、按时间先后用掉，破产储值弹窗会被当天多次回大厅的活动弹窗挤掉；活动类规则靠「排除群组名」互斥，下架回流规则后回流玩家一条活动类弹窗都命中不了（原型页 #8、#11）。

另有一项概念问题影响面广，列在第三节首条：「发送」既是动作、状态，又是指标（服务商受理数）；确认页漏斗与数据页漏斗的步骤不同，「预计发出 4,200」与「发送 3,617」不可比，运营做不了预计与实际的对照。

> 评审口径：只从运营每天使用的角度看页面、流程、规则；需求文档第 9 章已列事项不重复（与之相邻的会注明差别）；已定事项（统一入口、不设审批、两层、只写能力、不写排期）不讨论。位置写法：「原型页 #N」为原型第 N 页，行内引号为原文；「概要 pN」为设计概要第 N 页。

| 编号 | 位置 | 问题与反例场景 | 建议改法 | 严重度 |

| 2.10 | 原型页 #5「修改后须重新确认排程；未确认前仍按原设置发送」 | 运营改了内文（如修错字）后没点「重新确认排程」就离开，到点按旧内容发出，列表上看不出有未生效的修改 | 有未确认的修改时，列表状态旁标「有未确认修改」，离开页面时拦截提示；或改为保存即生效、只在人数变化超过阈值时要求确认 | 丙 |

## 三、概念不清

| 编号 | 位置 | 问题与反例场景 | 建议改法 | 严重度 |
|---|---|---|---|---|
| 3.1 | 术语「发送 游戏外推送被服务商受理的条数」（概要 p21、原型术语表）；同时有「发送对象」「发送时间」「发送方式」「发送中」「发送测试」「发送失败」；原型页 #10 快显状态有「发送中」，单条数据却写「发送 不适用」 | 「发送」同时是动作、状态和指标。读者会问：快显「发送中」但发送「不适用」？「发送失败」的推送发送数为 0？「预计发出」和「发送」是不是一回事（不是：前者是提交人数，后者是受理条数） | 指标改名「受理」（或「发出（服务商受理）」），动作与状态保留「发送」；表头悬停说明保留 | 乙 |
| 3.2 | 确认页漏斗「群组 → 排除后 → 可触达 → 勿扰时段顺延 → 频率上限拦下 → 预计发出」（原型页 #3）；单条数据漏斗「受众 → 发送 → 到达 → 曝光 → 点击」（原型页 #13）；快显单条数据却有「可触达」（原型页 #13 ID 32） | 预计与实际用两套步骤，对不上。反例：ID 42 确认时「可触达 4,310、预计发出 4,200」，发后数据页只有「受众、发送前拦下、未受理、发送」，运营无法回答「预计 4,200，实际发了多少、差在哪」；同是单条数据，快显有可触达、推播没有 | 单条数据页加「发送前的预计」一行，步骤与确认页一致：受众 → 可触达 → 勿扰 → 上限 → 提交 → 受理（发送）→ 到达；一次性推送保存确认时的预计值，便于对照 | 乙 |
| 3.3 | 概要 p20「受众 符合发送对象条件的玩家」；原型术语表「受众 符合发送对象条件、排除后的玩家」；原型页 #4「触发的玩家 1,250 人」与原型页 #13「受众 8,652 触发人次」 | 受众含不含排除两版写法；按行为同一量在确认页叫「人」、数据页叫「人次」；另外被提醒间隔挡掉的「不算受众」，受众又不等于触发次数 | 统一为「排除后」；按行为全部写「人次」；定义里写明「不含生效期间外、提醒次数与间隔不允许的」 | 丙 |
| 3.4 | 原型页 #11「今日被拦下 520 人」；原型页 #13「频率上限拦下 418」（近 7 天人次）；原型页 #8 弹窗「今日被拦下 1,240 人」，看板弹窗写「不适用」；T28 把 418 与 520 并列 | 同名「频率上限拦下」，单位（人／人次）与时间范围（今日／近 7 天）各页不同，T28 的对照会让人以为数字对不上 | 每处数字带单位与时间范围（「今日 520 人」「近 7 天 418 人次」）；看板弹窗与频率上限页用同一口径 | 丙 |
| 3.5 | 原型页 #12 字段表「曝光：推播 Android 显示通知时由客户端上报；Facebook 为已读；LINE 为官方统计」 | 游戏外「曝光」一列三种含义（显示在通知栏／已读／平台统计），放在同一列横向比较会误导；推播 Android 的「到达」（客户端回执）与「曝光」（显示通知）差别运营也说不清 | 曝光列表头按推送方式写明含义（如「曝光（Facebook＝已读）」）；或游戏外不跨推送方式比较曝光 | 丙 |
| 3.6 | 原型页 #12「人群」（固定五类，含「其余」）；原型页 #3「标签群组」；原型页 #14「标签名称」「所属群组」 | 「人群」「标签群组」「标签」三个词边界不清：看板的「潜在流失」与下拉里的「潜在流失（两档）」是否同一群组？「其余」是什么群组？玩家查询的「标签名称：潜在流失·实验组」与「所属群组」有何区别 | 术语表补「人群＝看板固定统计口径，对应哪些标签群组」；玩家查询把「标签名称」改为现有字段的原名并注明含义 | 丙 |
| 3.7 | 概要 p9「单条推送可不受上限」；原型页 #3「本条遵守频率上限」「不遵守上限」；需求「频率上限例外」；操作纪录「不遵守频率上限」 | 同一机制四种叫法；「不受勿扰」又是它的子选项，读者分不清是两个开关还是一个 | 统一叫「上限例外」，下设「计入方式」「是否同时不受勿扰」 | 丙 |
| 3.8 | 原型页 #4「每次触发最多 1 次，间隔至少 24 小时」；概要 p8「同一玩家两次至少隔 24 小时」 | 原型这句读起来是「同一次触发内两次提醒的间隔」，概要与需求的意思是「同一玩家任意两次提醒」，研发和运营会各按一种理解 | 原型拆成两行：「同一次触发最多提醒 N 次」「同一玩家任意两次提醒至少间隔 N 小时」 | 丙 |
| 3.9 | 原型页 #8 弹窗状态「上架中／启用／未到生效期间」；原型页 #10 快显状态「运行中／已暂停／已结束」；原型页 #1 总览弹窗行「按规则弹出 · 上架中 7 条规则」 | 同为游戏内推送，两套状态词；总览把两者放在同一张表的「已排程／发送中／运行中」列下，弹窗只能写成一句话 | 保留弹窗原状态，但在术语表写对应关系（上架且生效≈运行中，停用≈已暂停）；总览弹窗行单独说明 | 丙 |
