# 对标：推送统一后台「一个入口」（调研日 2026-10-19）

范围：十个设计点，每点 2–5 家，只写官方文档、官方博客、官方 API 参考里看得到的内容；看不到的写「未查到」。
核实方式两种：「已打开页面」＝用 WebFetch 打开了该页并读到相应内容；「仅搜索摘要」＝只看到搜索结果摘要，页面未能打开（Iterable 帮助中心对抓取返回 403）。
没有查到：国内头部游戏公司自有的运营后台（腾讯、网易等）没有公开官方文档；国内只查到推送云服务（阿里云、腾讯云）的单渠道接口说明，见第 8 节。

## 十点核心发现

1. 入口：所查多渠道平台都是「先选渠道再建」，侧栏按功能分组，没有按活动分组的。
2. 总览：跨渠道串联靠「标签＋日历」；只有游戏 LiveOps 产品（Satori、Balancy）把「活动」做成对象，消息挂在活动下。
3. 流程：各渠道骨架一致（3–5 步），渠道差异只出现在内容步和渠道前置项（订阅组、连接器、模板）。
4. 测试：测试名单挂在「人」上并跨渠道共用（Braze、OneSignal、Airship）；Airship 有独立 Tests 视图且不进报表。
5. 核对：确认页以「摘要＋人群规模＋预览／测试」为主；Braze 用「人群规模阈值」做二次确认，且要先开审批。
6. 改动：共同规则是「只对还没发出的生效，已排队的按旧版」，各家都建议重大改动「先停、复制、再改」。
7. 改期：所查文档均未写「活动改期时下游自动跟随或弹提示」；Satori 的「相对活动开始／结束 ± 偏移」是唯一从设计上支持跟随的模型。
8. 停止：已在途的消息停不住是共同事实，各家都在文档里写明；全局紧急暂停所查产品均未查到。
9. 接入：凭证一次性填、渠道变成表单里的一个选项；连接状态面板只有 Satori 有（错误诊断），凭证到期提示所查产品均未写。
10. 协作：复制、标签、按创建人筛选是标配；Braze 有变更日志和「Canvas 草稿同一时间只有一人可编辑」，其余编辑锁未查到。

## 1 入口与导航：所查平台都是「先选渠道再建」，用一张列表加渠道筛选，不按活动分层

| 产品 | 怎么做 | 出处链接 | 核实方式 |
|---|---|---|---|
| Braze | Messaging > Campaigns > Create campaign，创建时先选渠道；也可选 Multichannel，再在 Compose 步骤点 Add channel 逐个加渠道（应用内消息不能进 Multichannel）。侧栏按功能分组：messaging、audience、analytics、settings，不按活动。 | https://braze.com/docs/user_guide/engagement_tools/campaigns/building_campaigns/creating_campaign ；https://www.braze.com/docs/user_guide/administrative/access_braze/navigation/ | 已打开页面 |
| OneSignal | 点「Create...」后选择消息渠道；Messages 下的 All messages 把已发送和已排程合成一页，下拉切换 Sent／Scheduled。 | https://documentation.onesignal.com/docs/sending-notifications ；https://documentation.onesignal.com/release-notes/changelog | 已打开页面 |
| Firebase | DevOps & Engagement > Messaging，在 Campaigns 标签点 New campaign，再选 Notifications 或 In-App Messaging；两种走同一个入口路径。 | https://firebase.google.com/docs/cloud-messaging/android/first-message ；https://firebase.google.com/docs/in-app-messaging/get-started | 已打开页面 |
| Airship | Create 下拉 > Message；渠道不是第一步，而是在 Audience 步骤里勾选要触达的渠道（可多选），Content 步再按渠道分别填。Messages Overview 一张表列所有 composer 的消息，视图含 All／Ongoing／Scheduled／Drafts／History／Tests／Archive。 | https://www.airship.com/docs/guides/messaging/messages/create ；https://www.airship.com/docs/guides/messaging/manage-views/ | 已打开页面 |
| MoEngage | Engage > + New Campaign，弹窗里在 Outbound 下选 SMS 等，LINE 在 Connected Apps 下；All Campaigns 快速筛选栏含 Channel。 | https://moengage.com/docs/user-guide/campaigns-and-channels/sms-mms-and-rcs/sms/create-an-sms-campaign ；https://moengage.com/docs/user-guide/campaigns-and-channels/campaign-management-and-reports/all-campaigns-searchview-and-export-campaign-statistics | 已打开页面 |
| CleverTap | Campaigns > + Campaign，选渠道，渠道分四类：Mobile（Push、In-App、App Inbox、Native Display）、Web、Remarketing、Additional（Email、Webhooks、SMS）；列表可按渠道、类型、状态、创建人、标签、投放方式筛选。 | https://docs.clevertap.com/docs/intro-to-campaigns | 已打开页面 |

**共同做法**：新建的第一步（或 Airship 的第一屏表单）选渠道；列表页是一张跨渠道的表，用筛选区分渠道和状态。所查产品里没有以「营销活动」作侧栏第一层的。
**差异**：Airship 把渠道做成表单内的勾选项（一次消息可含多个渠道）；Braze 同时提供单渠道和 Multichannel 两条路；MoEngage、CleverTap、Firebase 的渠道在新建时就定死。

**对我们的启示**
1. 「侧栏按推送方式分页」比所查产品（一张列表加渠道筛选）分得更细，方向没有冲突；分页不改，但每页的「新建」按钮位置、名称、后续步骤要一致，并在顶部放一个跨渠道总表入口（参考 Airship Messages Overview），否则「为一次活动配齐六种」要在六页间来回找。
2. 第一次使用的运营：新建时的第一屏参考 Firebase／Braze，直接列出六种推送方式并一句话说明适用场景，而不是让运营先理解侧栏结构。
3. 「一条推送同时发多个渠道」保持可选：Braze 的 Multichannel 把「应用内」排除在外，说明游戏内弹窗不适合并进多渠道一条；与我们「游戏内、游戏外分两组」一致。

## 2 同一活动跨渠道串起来：靠标签加日历；只有游戏 LiveOps 产品把「活动」做成对象

| 产品 | 怎么做 | 出处链接 | 核实方式 |

| Braze Content Blocks | 中央库维护可复用内容，名称 100 字符内；Liquid 插入的块与源头关联，改源头会更新所有引用它的消息；文档用例全是邮件，未说明 push、SMS、LINE 是否可用。 | https://www.braze.com/docs/user_guide/messaging/design_and_edit/content_blocks | 已打开页面 |
| Airship | Messages Overview 日历：显示排程发送时间、有起止日期的消息的持续时间与重叠、发送历史；可按 Message Type、Status、月／周／日筛选；草稿和测试不上日历；点消息的 View message 回到原 composer 修改。Campaign categories 是另一回事，只用于汇总报告分组。 | https://www.airship.com/docs/guides/messaging/manage-views/ ；https://www.airship.com/docs/guides/messaging/features/campaigns | 已打开页面 |
| Satori | Live Event 是活动容器：可挂 feature flag 覆盖、玩家消息、监控指标；消息可在活动开始前／后、结束前／后触发；活动详情页的 Message Schedules 标签集中列出该活动下的全部消息；Live Events 页有最长四周的过去／现在／未来合并视图。 | https://heroiclabs.com/docs/satori/concepts/live-events ；https://heroiclabs.com/docs/satori/concepts/live-events/attach-player-messages/llm.md | 已打开页面 |
| Balancy | Game Event 是启动 Game Offer 的第一步（Attachment 选 Game Offer 或 Script）；日历（Calendar Dashboard）显示活动持续时间（2025-02 发布说明）；发布说明记载 2023-10「推送出现在日历里」「可从日历创建推送」；推送功能为封测，页面本身未写与日历的联动。 | https://en.docs.balancy.dev/liveops/game_events/ ；https://en.docs.balancy.dev/release_notes/ ；https://en.docs.balancy.dev/liveops/push_notifications/ | 已打开页面 |
| MoEngage | 每个活动最多 5 个标签；All Campaigns 的高级筛选可按标签「Any／All」；日历视图未查到。 | https://moengage.com/docs/user-guide/campaigns-and-channels/campaign-management-and-reports/all-campaigns-searchview-and-export-campaign-statistics | 已打开页面 |
| Iterable | 标签叫 labels；Campaigns、Journeys 列表用 Filters > Label 筛选。 | https://support.iterable.com/hc/en-us/articles/115004989743-Adding-Labels-to-Your-Campaigns- | 仅搜索摘要 |

**共同做法**：营销平台靠人工贴标签、列表筛选，再加一个日历；游戏 LiveOps 产品则有「活动」这个对象，消息挂在它下面。
**差异**：营销平台的日历都有缺口（Braze 不含 Canvas 和触发型；MoEngage、CleverTap 未查到日历）；Airship 的日历覆盖面最广，且能区分 composer 来源和状态（暂停显示斜线）。

**对我们的启示**
1. 分页不改的前提下，增加一个统一的「活动」字段（六页新建表单都有，选填但在首屏），所有列表可按它筛选，总览页以它分组；这比 Braze 的自由标签更稳（Braze 的标签可现场输入新建，同一活动容易出现多个写法）。
2. 日历要补齐 Braze 的缺口：持续生效的游戏内弹窗、快显、触发型推送都要以「持续条」画出，而不只画单次发送点；可参考 Airship 把有起止日期的消息画成条、把重叠显示出来。
3. 共用文案：Braze Content Blocks 是「改源头、全引用更新」，文档未写编辑锁或版本；我们第一版建议只做「复制文案到其他渠道」，不做引用，避免改一处误伤六处。

## 3 各渠道新建流程一致：骨架 3–5 步统一，渠道差异放在内容步和渠道前置项

| 产品 | 怎么做 | 出处链接 | 核实方式 |
|---|---|---|---|
| Braze 活动 | 五步：Compose messages → Schedule delivery → Target audiences → Assign conversion events → Review summary and launch；渠道特有内容在第 1 步。 | https://braze.com/docs/user_guide/engagement_tools/campaigns/building_campaigns/creating_campaign | 已打开页面 |
| Braze 短信 | 先选订阅组（决定发送号码和可用消息类型：SMS、MMS、RCS）；composer 上限 1,600 字符，边写边估算编码（GSM-7／UCS-2）、字符数和计费条数；但不计算 Liquid 与 Connected Content 展开后的长度。 | https://www.braze.com/docs/user_guide/message_building_by_channel/sms/campaign/create/ | 已打开页面 |
| Braze LINE | 先选订阅组（一个活动内所有变体须同组），Launch editor 拖入消息类型，一次最多 5 个气泡；类型与上限写在文档里（文本 5,000 字符；卡片消息最多 10 张，标题 40 字符等）；文档前置项要求先查阅渠道政策、额度与内容规则；发送消耗账号的 Message／Action Credits，未写月度条数额度。 | https://www.braze.com/docs/user_guide/channels/line/create_a_line_message | 已打开页面 |
| Braze WhatsApp | 分 Template message（企业发起，须 Meta 审核）和 Response message（须在用户来信开启的 24 小时窗口内）；可在 composer 内 Create new template 提交审核，最长 24 小时；通过审核的模板文字在 composer 里锁定；缺少 Liquid 默认值的消息不会发出。 | https://www.braze.com/docs/user_guide/channels/whatsapp/create_a_whatsapp_message | 已打开页面 |
| Braze Messenger | 没有原生 composer，用 webhook 模板：Content > Webhook 建模板，选 Facebook Messenger 模板，设置 message type 或 tag，请求体放用户的 PSID，Test 页签发预览；文档写明 Facebook 不允许经 Messenger 平台发营销消息；未写 24 小时窗口。 | https://www.braze.com/docs/partners/additional_channels_and_extensions/additional_channels/instant_chat/messenger | 已打开页面 |
| MoEngage | 三步：Target users → Content → Schedule and goals，SMS、LINE 都是同一骨架；SMS 内容步显示字符数和 SMS 条数，DLT 受管制的连接器须填 Template ID，链接自动缩短并追踪；LINE 内容步选 Connector、Connections，填 LINE ID 与 Message。 | https://moengage.com/docs/user-guide/campaigns-and-channels/sms-mms-and-rcs/sms/create-an-sms-campaign ；https://moengage.com/docs/partner-guide/messaging-channels/messaging-apps/line | 已打开页面 |
| Airship | 四步：Audience → Content → Delivery → Review；Content 步「按已启用渠道分别配置」；Review 步含设备预览和消息摘要。 | https://www.airship.com/docs/guides/messaging/messages/create | 已打开页面 |
| Firebase | 应用内消息四步：Style and content → Target → Scheduling → Conversion events；其中 Scheduling 多出触发事件和每设备频率（默认看过一次不再显示）。 | https://firebase.google.com/docs/in-app-messaging/compose-campaign | 已打开页面 |
| CleverTap | 区块为 Who／What／When，外加可选的转化目标和投放偏好；SMS 页未写字符上限或条数提示，只写每条缩短链接占 14–20 字符。 | https://docs.clevertap.com/docs/create-message-sms | 已打开页面 |
| 渠道方规则（背景） | LINE：每月有免费额度，按收件人数计，超额请求报错且不发送；官方提供查询本月上限与已发数量的接口。Messenger：24 小时内可发含促销的消息，窗口外只能用 message tag 发非促销的 1:1 更新，Human Agent tag 7 天。 | https://developers.line.biz/en/docs/messaging-api/pricing/ ；https://developers.facebook.com/documentation/business-messaging/messenger-platform/policy | 已打开页面 |

**共同做法**：骨架一致、顺序大同小异（内容或对象 → 时间 → 转化 → 确认）；渠道差异不改骨架，只体现为「先选订阅组／连接器／模板」的前置项和内容步的字段。
**差异**：渠道约束提示的深度不一——Braze 短信有计费条数估算，WhatsApp 有模板锁字段和默认值拦截；LINE 额度、Messenger 24 小时窗口在所查产品的表单里没见到现成提示（Braze Messenger 只让选 message type 或 tag）。

**对我们的启示**
1. 六种推送沿用「内容 → 对象 → 时间 → 频率上限 → 确认」与 Braze、MoEngage、Airship 的骨架同构，方向正确；渠道差异放在内容步，并把「渠道前置项」（短信=发送号和签名、LINE=官方账号、Messenger=主页）固定放在内容步顶部。
2. 渠道约束分三类提示：能实时算的就地显示（短信字符和条数，参照 Braze，但要把个性化展开后的长度也算进去，这是 Braze 没做的）；会导致发送失败的在确认页前拦截（LINE 超额请求直接失败、WhatsApp 缺默认值不发；确认页显示「本月 LINE 剩余额度」是所查产品没有的点，LINE 官方有查询接口）；政策类用一块固定的「本渠道须知」文字（Messenger 24 小时窗口与 tag）。
3. 差异说明放在表单里就地出现，不跳帮助中心；这与「六种新建流程一致、差异就地说明」的目标一致。

## 4 测试发送：测试名单挂在「人」上并跨渠道共用，测试入口在编辑页内

| 产品 | 怎么做 | 出处链接 | 核实方式 |
|---|---|---|---|
| Braze | Settings > Internal Groups 建 Content Test Group（每组最多 1,000 人，组数不限），用于 push、应用内、SMS、邮件、Content Cards 的测试发送；测试时可选个人或内部组，按各人属性做个性化，缺属性用默认值；SMS 只能发给库内有效号码；LINE 在 Preview & Test 页签同样可发给内容测试组或个人；Seed Group 只用于邮件投递监测，不是 QA 用。 | https://braze.com/docs/user_guide/administer/global/user_management/internal_groups/ ；https://www.braze.com/docs/user_guide/channels/line/create_a_line_message | 已打开页面 |
| OneSignal | 测试用户标记在 User 上，对其全部订阅（设备、邮箱、手机号）生效；composer 的 Test & Preview 勾选测试用户后点 Send Test Push；文档只写了 push 的测试按钮，没写邮件、SMS 的；SMS 设置页另有 Send Test SMS（用于验证接入）。 | https://documentation.onesignal.com/docs/en/test-users ；https://documentation.onesignal.com/docs/en/sms-setup | 已打开页面 |
| Airship | Preview and test groups 可开启「Test group」，最多 20 组，成员按渠道 ID、邮箱或手机号（MSISDN）加入，组名和 Test group 开关创建后不能改；Review 步点 Send Test 立即发送，收件人可选 named user 或测试组；测试出现在 Messages Overview 的 Tests 视图，不进报表；正在 Holdout 实验的用户收不到测试。 | https://www.airship.com/docs/guides/messaging/testing-tools/ ；https://www.airship.com/docs/guides/messaging/messages/create | 已打开页面 |
| Firebase | 通知：composer 右侧 Send test message，粘贴设备 FCM registration token 点 Test；应用内消息：Test on Device，填 installation ID 点 Test，立即发送，要关闭再打开 App 才能看到；测试对象是设备，不是人。 | https://firebase.google.com/docs/cloud-messaging/android/first-message ；https://firebase.google.com/docs/in-app-messaging/get-started | 已打开页面 |
| MoEngage | 内容步可「send a test campaign」，测试用户可用 unique ID、邮箱、手机号等标识；LINE 用 Test 检查连接器配置，测试用户收到即可发布。 | https://moengage.com/docs/user-guide/campaigns-and-channels/sms-mms-and-rcs/sms/create-an-sms-campaign ；https://moengage.com/docs/partner-guide/messaging-channels/messaging-apps/line | 已打开页面 |

**共同做法**：测试名单是「具名的人」，成员的多个渠道标识（设备、邮箱、手机号）归在一起；测试入口在编辑页内（Test 页签、Review 步、右侧栏）。
**差异**：全渠道共用程度不同——Braze 一个内容测试组覆盖五类渠道；OneSignal 的标记跨订阅但文档只写了 push 的按钮；Firebase 无名单，按设备。测试结果怎么看：只有 Airship 明确（Tests 视图，且不进报表）；其余未查到专门说明。

**对我们的启示**
1. 一份全渠道共用的测试名单：一个测试账号下挂 App 设备、手机号、LINE ID、Messenger ID（OneSignal 把标记挂在用户上、Airship 以 named user 聚合是现成参考）；六种推送的表单里都有同一个「发测试」入口。
2. 无审批的前提下，「测试账号＋发送前确认」要承担把关职责：测试记录单独查看且不计入正式数据（Airship 做法），确认页显示「本条是否已发过测试」。
3. 游戏内弹窗、快显的测试要写明触发条件：Firebase 应用内消息的测试需要重开 App 才显示，说明这类渠道的测试和「立即收到」的渠道不同，表单里要就地说明。

## 7 活动改期与生效期跟随：所查文档均未写「改期时下游自动跟随或提示」；只有 Satori 把时间建成对活动的引用

| Satori | Settings > Integrations > Message Integrations 填凭证；控制台对每个集成显示「最近一次错误、最近失败时间、累计错误数」，分集成级（凭证无效、供应商故障）和身份级（缺 token、邮箱无效）；最近错误列表存在内存里，服务重启即清空；「delivered」只表示供应商已接受，不代表到了设备。 | https://heroiclabs.com/docs/satori/concepts/player-messaging/message-integrations/ | 已打开页面 |

**共同做法**：接入是管理员一次性填凭证；之后渠道变成新建表单里的一个选项，受众沿用平台自己的人群，订阅状态由渠道侧同步回来（Braze LINE 的关注者、短信的订阅组）。运营不再接触凭证。
**差异**：连接状态与凭证到期提示：Braze、MoEngage 文档未写；只有 Satori 有最接近的错误诊断面板，且能区分「渠道坏了」和「某个玩家有问题」。部分渠道要先走较长的开通流程（Braze 短码 8–12 周）。

**对我们的启示**
1. 凭证由管理员在独立的「渠道连接」页维护，运营新建时只选渠道账号，不见凭证。
2. 连接页展示三项：最近一次成功和失败时间、失败类别（凭证／平台／对象）、累计失败数（照 Satori）；凭证到期提示所查产品都没写，是我们要补的，LINE、Messenger 的 token 到期会直接导致整批失败。
3. 搬进来后，运营少掉的步骤：到第三方平台导名单或圈人群（改用本后台的人群，Braze LINE 是关注者自动同步）、在第三方写文案（改在统一表单，文案可复制）、第三方单独测试（改用共用测试名单）、到第三方看数据（改看本后台报表；注意 LINE 侧只在当天触发人数超过 20 时才给打开和点击统计，见 Braze LINE 文档）。

**对我们的启示**
1. 不设审批的前提下，用「操作纪录」顶替：每条推送显示创建人、最后编辑人和时间，详情页有按字段的变更日志（参照 Braze 的变更记录项：名称、排程、标签、消息、受众）。
2. 全局搜索同时支持名称、ID、活动、标签（Braze 文档只写名称、MoEngage 支持 ID），并默认过滤掉已归档；这对「第一次用的运营找得到」最直接。
3. 编辑冲突：所查产品大多没有锁；可参照 Braze 的做法——已上线推送的修改走草稿，草稿同一时间只允许一人编辑；未上线的普通草稿不加锁，避免过重。
