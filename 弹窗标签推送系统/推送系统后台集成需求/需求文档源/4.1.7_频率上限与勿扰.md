#### 4.1.7 频率上限与勿扰

> 每种推送方式每人每天的上限、游戏外推送的勿扰时段与可选的同次弹窗间隔，都在「频率上限」页设置。
>
> 关键规则：游戏外、游戏内分开计，游戏外四种也各自计数；游戏外推送按服务商受理计 1 条，弹窗按弹出、快显按显示计；到上限当天不再发，不排队补发；立即、定时推送按开始发送时刻整条判断勿扰，自动重试沿用这次判断，不拆两批。（v0.9.41）游戏外营销名额的截断顺序：重要推送的预留在先，其余按每人受理先后；消息类别加「活动提醒」，服务通知只用于补偿、维护、账号安全与绑定结果；事前看名额占用见本节「名额占用」，各设计点的对标见本节末「对标与取舍」。（v0.9.42）活动提醒只给迁入的系统活动提醒与玩家自身事件（事件锚点、排名变化）触发的按行为推送，项目锚点与每日定点＋状态固定为营销；破产保护改为储值类破产位的项可勾「不受每人每天弹窗上限」（4.2.1）；同一时刻跨推送方式的不重复用合并组（4.1.4「合并组」）。

**弹窗的其他可选上限（10/16 夜补充）**

来源：同事草稿的全局规则（单次最多 3 个；弹出间隔 1800 秒，破产礼包、发财金除外；活动、普通礼包 24 小时各 ≤ 1 次）在原设计里只能人工凑或配不出，补为三项可选功能，都默认关闭、成本小改动。

| 项 | 规则 |
|---|---|
| 按弹窗类型每人每天上限 | • 活动类、储值类各一个值，1–99；只计大厅自动弹窗，破产弹窗不计（救急场景不受限）<br>• 计 1 的时点、日界、截断与大厅＋破产合计上限相同（弹出 1 个计 1，台湾时间 00:00 重置，按排序截断）；两者同时生效取最严<br>• 勾「不受每人每天弹窗上限」的项同样不受本项；「仍计入」的照常计入<br>• 被截掉的项记「频率上限拦下」，子原因「活动类当天已 1／1」<br>• 例：活动类 1、储值类 1；玩家 10:00 进大厅弹出活动类 1 个、储值类 1 个，14:00 再进大厅两类都不弹 |
| 每次进入大厅最多弹出数 | • 一次大厅请求活动类与储值类合计最多 N 个，1–8；只管大厅自动弹窗<br>• 按规则优先级（活动类与储值类共用的序列）、同一规则内按项排序截断，与判断顺序第 6 步一起截，取当天剩余名额与 N 的较小值；客服减量的单次弹出数照旧取更小值<br>• 例：N＝3，活动类规则（优先级 1）取到 2 项、储值类规则（优先级 2）取到 2 项，返回前 3 项，储值类第 2 项记「频率上限拦下 · 单次已 3／3」 |

**交互流程：修改上限与勿扰**

1. 页面上直接改数值；改过的格写出原值，页顶显示「修改中 · 尚未保存」。
2. 点「保存」弹出确认框：逐项列出改前 → 改后；按近 7 天估算影响，例：「推播每天约少拦下 430 人（上限 2 → 3 条）；按行为推送每天约多放弃 120 人次（ID 31）；23:00–24:00 开始的立即、定时推送改为顺延到 08:00；已排程的推送中落入新勿扰时段、将顺延到勿扰结束的：0 条」（有则逐条列出名称与原定时间；重复的定时按之后各次逐次判断，写受影响的次数）；写明「对之后的发送生效，已发出的不变」。（v0.9.41）改每人上限、每周上限、合计上限、活动提醒类别上限或最小间隔时，确认框另列今天与未来 7 天已排推送逐条的影响：推送 ID、名称、发送时刻、预计多收或少收人数（按下方「影响估算」与本节「名额占用」同一算法）；并固定写出中途修改的规则：「立即对尚未提交的人生效；当天已计数不清零；调低到低于已收的人当天不再发；已排推送的估算随之重算」。（v0.9.42）改弹窗每人每天上限（大厅＋破产合计，及弹窗按类型上限）时，确认框另列「名额截断影响」，算法与写法同弹窗规则保存前确认（4.2.1「保存前确认」、5.12 序号 69）：按近 7 天弹窗请求重放，用改后上限空跑，与改前对比，写每天多截掉（或少截掉）的项数、被截最多的 5 个项目及规则、首储礼包与破产礼包被截人数；勾了「不受每人每天弹窗上限」的项不被截，不进本项；未算完写「计算中」，不阻止保存。例：上限 8 → 7 个，每天约多截掉 975 项，首储礼包被截 +130 人、破产礼包 +45 人（原型页 #11 状态卡片 11，T577）。为什么：调游戏内上限时原先看不出会截掉哪些关键项（字段 5.10 序号 68）。
3. 点「确认保存」后：新值对之后的发送生效；新建表单的「频率上限」块随之更新，例「推播每人每天 3 条」；页面提示「已记入操作纪录」；操作纪录逐项写改前改后。
4. （10/15 夜补充）页顶「修改历史」按版本列出每次保存的改前改后；选一个旧版本可「恢复此版本」，走本流程第 2 步的保存确认框（改前改后、影响估算、将被顺延的推送），记操作纪录「恢复版本」；消息类别规则、每周上限、最小间隔、短信费用与阈值随本页整页恢复。

**影响估算（保存确认框）**

| 估算项 | 算法 |
|---|---|
| 按行为推送每天多（少）放弃的人次 | 对每条运行中的按行为推送，取过去 7 天的全部触发，按 4.1.4 判断顺序第 1–4 步筛过后，分别按改前、改后的勿扰时段统计落在时段内、处理方式为放弃的人次；差值按天求和后除以 7，逐条列推送 ID |
| 立即、定时改为顺延或不再顺延 | 已排程推送中，计划发送时刻由时段外变为时段内（或相反）的推送条数与可触达人数；重复的定时按之后各次计，写次数 |
| 改上限后每天多（少）拦下的人数 | 取过去 7 天该推送方式每人每天的实际受理条数（游戏内推送为显示次数），按改后上限算超出的人数，减去按改前上限算的人数；按天求和后除以 7<br>• （v0.9.41 改）需求量改用「受理＋频率上限拦下」（游戏内为显示＋被截断项目数），不只用受理：历史受理数已被旧上限截断，上限 2 时没有人受理到 3 条，只用受理时调高上限算出的差恒为 0。调高、调低都按需求量算超出人数后相减 |
| 已排推送逐条影响（v0.9.41） | 对今天与未来 7 天已排的立即、定时推送（重复的定时按各期），按「名额占用」的算法分别用改前、改后设置模拟一次，逐条给出预计发出人数之差（多收为正、少收为负）；按行为推送给近 7 天日均人次之差 |
| 范围 | 按台湾时间自然日；不含测试发送与「不计入」的推送 |

**异常与边界**

| 场景 | 处理 |
|---|---|
| 当天中途调低上限 | 已收数已达到或超过新上限的玩家，当天不再收到 |
| 当天中途调高上限 | 当天立即按新上限放行，被拦下的不补发 |
| 中途修改的统一说法（v0.9.41） | 改动立即对尚未提交的人生效，正在发送中的推送前后两段按提交时的值判断；当天已计数不清零；调低到低于已收的人当天不再发；已排推送的估算重算（本节「名额占用」），列表标「估算已更新」。这几句写在频率上限页保存确认框与改动格旁（原型页 #11），不只写在本文 |
| 已顺延、未发出的人次 | 按顺延时确定的时间发出，不随新时段改变 |
| 多条顺延推送在勿扰结束时同时释放（10/16 夜补充） | 按原计划时刻先后排队，同一时刻按推送 ID；先提交的先占每人每天上限；受服务商限速（4.1.1「八」8）；（v0.9.41）同一时刻的重要推送先，再按排程时刻、推送 ID；重要推送的预留名额照常保留（上方「截断先后」③） |
| 发送或重试跨过 00:00（10/16 夜补充） | 每人每天上限按受理时刻所在日计；数据按受理时刻所在日归属（4.1.8「日期归属」，v0.9.40 改，原写按开始发送日）；重复的定时某次延迟到与下一次同日时，当天只发一次，跳过的记「同日已发」（4.1.1「八」8） |
| 上限填 0、负数或非整数 | 校验不通过；上限为 1–99 的整数（5.10） |
| 两人同时修改 | 后保存的人在确认框看到「设置已被他人修改」，须刷新后重改 |
| 只读角色 | 只看，不显示「保存」 |
