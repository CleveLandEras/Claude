用户先后否定了两种汇报：
- 过程型验收包：「主要是记录」。
- 纯行动清单（N 件事 + 决策表 + 复制消息）：「看不懂，没有上下文，没有逻辑链……看不到当前我们的现状、问题诊断、支撑点、方案」。

**Why:** 用户要基于理解来判断。每个决定都得能追溯到它要解决的问题和证据，否则只能盲签。

**How to apply:**
- 结构：一句核心结论 → 一、现状（带分母的数据和图表）→ 二、问题诊断（每条是结论句 + 证据数字 + 待确认项）→ 三、方案（问题→方案→实现方式→评估指标的映射表）→ 四、进度与卡点 → 五、需要你决定。
- 每节标题写成一句结论。
- 决定只挑真正影响方案的关键几项，逐项讲清「为什么要决定」、推荐方案和备选方案的利弊，并标出对应哪条问题；其余照原设计的，一句话带过。
- 过程、日志、agent 往来不放进正文；要发出的消息放附录，默认收起。
- 数字核对出处，推断写成条件句，不能把话说过头。
- 与 [[conclusion-first-report-form]] 一致；呈现格式自己定（[[dont-ask-about-presentation-format]]）。

2026-10-28 补充（活动配置项目）：Dk 先嫌长版「字太多说明没抓住重点」，再看一屏短版说「完全看不懂……一个新的不了解情况的读者也应该能看懂」。短版的毛病是满篇项目内部叫法（必需档、尽量档、合并版、储值类、今早那页、第二批），没交代项目是什么。
- 写之前先假设读者从没听过这个项目：开头两句交代「现在的问题」和「这个项目做什么」，再给结论。
- 内部叫法一律换成大白话（「有时间再做」而不是「尽量档」）；每句主语、动作、对象写全。
- 结论只抓一个主要建议，下面两三条理由，每条配一个具体数字或例子；次要发现压成一两行放后面。
- 同日又一轮被否（「我快疯了，你怎么一直抓不住重点」），Dk 给出骨架：**问题是什么 → 原因是什么 → 怎么解决 → 结论是什么**。问题、原因、解决要一一对应（问题①→原因①→解决①），每格一句结论加一条证据；结论写本期做什么、效果、要他做什么。我自己检查方案时冒出来的旁支（规则细节等）不进这页。
