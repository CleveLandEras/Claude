## 〇、当前重点（Dk 10/18，优先于下面第三节的待办顺序）
Dk 10/18：「核心内容可以深入，但核心内容未完全深入完善之前不要思考外围的细节。先专注于核心内容」。起因：10/17 一轮大部分力气花在评审挑出的一致性、措辞、版面和参数示例（如短信预算示例）上，核心几乎没动。
- **核心五件，按此顺序逐件做透**：① 数据：每种推送的发送、到达、点击，弹窗、快显的曝光、点击，能按推送方式、人群、单条、时间看，口径与回传来源清楚；② 整体控制：每人每天上限（游戏外、游戏内两层）、弹窗的先后、互斥、频次与不重复打扰，多条同时竞争时谁让谁；③ 按人群发：标签且、或、排除、交集，五类人群都圈得出，人数可预览；④ 一个入口：推播、短信、Facebook、LINE、弹窗、快显都在一个后台配完，新建、测试、排程、停止走得通；⑤ 写死的迁进后台：客户端写死的弹窗、服务器写死的推送与快显，迁入后改内容不发版、不重弹不漏弹。
- **做透的方法**：每件先列运营要靠它完成的真实任务（出处用现有后台截图与盘点、同事草稿、Jira、Dk 原话、产品计划；见 `分析/应有内容参照.md`）；每个任务在原型上从头走到尾，逐层查：页面 → 字段与规则 → 异常；再对标至少两家做得好的产品在这件事上的做法（带出处）；走不通、浅、缺的就设计补上，落进原型与需求文档。评审只问「这件核心能不能支撑这些任务、和做得好的产品比还缺什么关键的」，评审人扮演做过推送或游戏运营后台的资深同行，只给作品与任务。
- **Dk 10/18 再提醒**：「只专注于核心」「一定要参考顶尖优秀的做法」「整个全部做完之后，要向我汇报的点只有做了什么以及为什么做。其他的不用汇报」。每件核心的设计都先查顶尖产品的官方文档与公开做法（如 Braze、OneSignal、CleverTap、MoEngage、Airship、Firebase，以及头部游戏的运营后台公开资料），写清「它们怎么做——我们怎么做——为什么相同或不同」，再落进原型与需求文档；凭空设计的不算做透。五件全部做完前不向 Dk 汇报。
- **顶尖做法参考库**（Dk 10/19：「那些业界顶尖产品怎么做的资料我希望能收录起来，因为那些都是很重要的参考标准」）：每个设计点先查 `规则与交接/顶尖做法参考库/`；库里没有的再查官方文档，查到后按库的格式补进对应文件（做法、哪些产品、出处链接、核对日期、我们的取舍、落在哪）。
- **交付前必查**：每份交付物的任务说明都附上 `规则与交接/交付前必查.md`，交付前逐条检查并在回报里写明过／不过（10/19 起，起因：需求评审版结构不清，结构原则未被执行）。
- **不做**：核心五件没做透之前，不改参数示例、默认值微调、配色、措辞、版面、页面标注这类外围细节；评审意见里属于外围的，记进细节表，不改。不加候选块。
- **每做完一件**：写一份短结果 `分析/核心_<名称>_结果.md`：这件核心原来能做到什么、现在能做到什么、改了哪些（每条一句「改了什么——为什么」）、还缺什么；截图交子任务，只截改动区域。

## 〇·一、省 token 的做法（10/19 起，Dk：「token消耗能降低吗？这看起来浪费了很多呢」）
起因：10/18–10/19 的 70 个子任务用了约 13 亿 token，65 个子任务每一步都背着 15 万以上的上下文（最费的平均 24 万–40 万、走 130–200 步）；原型 141 万字、需求文档 74 万字，读进一段就一直背着。
- 不把原型、需求文档的大段读进上下文：用 grep 或 python 按关键词取相关的 20–60 行。
- 改稿子任务一个只管一页原型或一节需求文档，最多约 40 步就收尾，下一批另派新的子任务。
- 多处改动先写成改动清单，用 python 脚本一次替换，不逐处 Edit。
- 验收用例、追溯表、附录的同步等本期范围定了统一做一次，不在每件核心里做。
- 评审每件只派 1 位、只看任务表与改动页；截图、机械核对、文档同步用 model: "sonnet"。
- 主线自己（编排者）不读大文件，只读子任务的短回报和结果文件。

## 〇·二、改原型、需求文档＝改源文件，再运行拼装脚本（10/19 瘦身后）
- 原型按页拆在 `推送系统后台集成需求/原型源/`（每页一个文件，如 `p3.html`；页首、页尾各一个；顺序见 `_顺序.txt`）；需求文档按章拆在 `推送系统后台集成需求/需求文档源/`（第 4 章拆到 4.x.y 小节、第 5 章拆到 5.x 小节，如 `5.4_推播新建与编辑表单.md`）。
- 改完运行 `python3 _scripts/an_原型拼装.py`、`python3 _scripts/an_需求文档拼装.py`，生成 `3_原型.html`、`4_需求文档.md`。不要直接改这两份：拼装脚本发现它们被直接改过会停下。找某段文字在哪个源文件：`python3 _scripts/an_原型拼装.py 找 <文字>`（需求文档同）；只核对不写：加参数「比对」。`_scripts/pl_原型替换.py` 已改为替换源文件后自动拼装。
- 加锁对源文件加：`python3 _scripts/pl_锁.py 加 <源文件名> 设计主线`（如 `p3.html`、`5.4_推播新建与编辑表单.md`）；一次改多页、重排或改 `_顺序.txt` 时另加 `3_原型.html`／`4_需求文档.md` 的锁。拼装前确认没有别人持着同一份交付物的锁。
- 其余位置：样式只在 `推送系统后台集成需求/原型样式.css`（原型与验收用例共用）；验收用例在 `推送系统后台集成需求/验收用例.html`（不拆，直接改）；修改记录只在 `推送系统后台集成需求/需求文档_修改记录.md` 表末加一行，需求文档第 1 章由拼装脚本自动取最后 3 行。
