一

系统机制

弹窗

  • 排序列表是优先级链。第 1 位该玩家当前不可购买（已购买、不在开放期）时，系统跳过往下取，直到取满「弹出数量」。
  • 多条规则命中时叠加触发。做定向不必重配全量内容，在现有规则之外增加定向规则即可。
  • 两层结构：规则层定「对象 + 位置 + 弹出数量」，排序列表里每一项自带「时机 / 形式 / 每日次数 / 冷却」。
  • 有效时机 4 个：活动开启 / 首次登入 / 大厅 / 破产。后台的「进入大厅」与「返回大厅」不做区分。金币水位、连败次数、当日下注量这类状态不能作为时机，只能作为人群圈选条件。
  • 频次与限制：可限单个弹窗每日次数上限与冷却时间；不支持负反馈降权（无法做到连续关闭 N 次后自动静默）；实验分流支持，开发成本未评估。

标签

  • 每个标签是独立的 BigQuery 脚本，不是统一刷新的系统。新建标签时排程频率可自行指定，最快 25 分钟一次。
  • 组合能力：支持 And、排除、or，计划增加交集。群组标签可任选、不受限。
  • 规模：约 100 个，分十个大类——历史最高卡别 / 身份状态 / 游戏偏好 / 广告 / 当前卡别 / 支付平台 / 当月存款金额 / 指定活动 / 存储价值条件 / 赌注条件。
  • 在弹窗里的用法：对象列填「标签名称 + 群组ID」，带「标签状态」启用字段。
  • 五类人群都有现成标签：新增 →「新增」；回流 →「回流」「7–30 天内回流」「30 天未登入」；破产 → 走破产位；潜在流失 → 衰减型「当月储值额小于上月 70% / 50% / 25%」；潜在付费 → 阈值型「该月储值 ≥ 1 元 / ≥ 200 / ≥ 1000」配合未首储。

三

用户结构

近一个月活跃口径：按最后登录时间取 2026-08-16 至 09-16，剔除机器人 599 与测试账号 141，有效 62,292 人。

卡别分布

付费分布：新用户与活跃全量是两个分布

储值类弹窗每次只弹 1 个，排序第 1 位基本决定结果。同一条排序给全部玩家，对新用户偏贵、对高卡用户偏便宜。

身份、押注与 RTP

  • 身份分布（分母 62,292）：持续 34,856（55.96%）、回流 16,564（26.59%）、新增 10,749（17.26%）、VIP 108（0.17%）、黑名单 15（0.02%）。口径：新增＝注册 30 天以内，持续＝注册超过 30 天，两者与回流互斥。
  • 回流是第二大人群，目前没有任何一条针对它的规则，只有 ID 5 排序第 7 位的「回流任务」对全部玩家生效。
  • 押注分布（分母 62,292）：0 占 8.56%、1–10,000 占 20.85%、10,001–100,000 占 25.04%、100,001–1,000,000 占 25.27%、1,000,001 以上占 20.22%。累计押注 ≥ 10,000 的有 43,944 人（70.55%），同口径下新用户只有约 48.6%。
  • RTP 分布（分母 62,292，中位数 87.21%）：大于 100% 占 8.58%、100–96.5% 占 9.65%、96.5–80% 占 45.3%、80% 及以下占 27.41%、等于 0 占 9.06%。
  • 注册时长与卡别：近三个月注册的 16,031 人中 95.8% 是普卡、储值率 16.5%；三个月以前注册的 46,226 人储值率 33.78%，卡别分散。卡别这一维度只在存量用户里可用。
四

礼包与限时加码礼包

价格带

  • 上架中的礼包共几十个：最低是首储礼包 NT$50，最高 NT$30,000，大多数集中在几百到三千。
  • 弹窗排序中出现的七个礼包（独享礼包、惊喜三选一、限时加码礼包、生涯限购、每日礼包、平台限量/专属礼包、破产礼包）各自售价未取得，是排储值类顺序的直接输入。

限时加码礼包

该礼包同时出现在弹窗后台 ID 6、ID 7 排序的第 4 位，以及推荐礼包管理后台的一整套独立机制中。推荐礼包后台界面无弹窗位置、时机、弹出数量字段，决定的是资格与加码幅度；弹出由弹窗后台负责，推播则是它自身独立的一条通路。

  • 准入门槛为累计押注 10,000 以上，近一月活跃用户中 70.55% 达标，新用户约 48.6% 达标。
  • 每月 1–7 日不出现：出现时间设定为每月 8–31 日，这 7 天排序会跳过它取下一位。
  • 排除名单中的「VIP 名单」是身份字段的一个值，共 108 人（0.17%），不是按卡别自动判定，不影响中高卡用户的排序。
  • 加码是普惠的：按个人 RTP 分五档给 2%–12%，72.71% 的活跃用户落在 6% 以上的档位。
五

推送现状

  • 已有推送能力，但每个功能各一套，没有统一入口。
  • 实例一：限时加码礼包——用户触发后在设定时间内未购买，剩 2 小时时发推播，标题「最後提醒⚠️幸運加碼禮包」。
  • 实例二：新手通行证——前几级升级时有推送条，内容只说明升级，不说明有奖可领，点击不跳转。
  • 其他触达通路：游戏内侧边栏常驻入口、红点、大厅活动中心二级入口。
  • 发送量与到达率无数据。

推送现状 · 分三步追问
建议
第一步 · 研发或通行证对接人新手通行证升级时会给用户发一条推送，内容是「通行证升级了」。这条推送是哪个系统发出去的？配置在哪个后台？
第二步 · 该系统的维护人除了通行证，还有哪些功能在用这套推送？平台上是不是所有推送都走这一套，还是各功能有各自的？

补齐后推送形成可操作的现状底稿。直接询问系统总数通常无人能答，从一个已知实例往回追更可行。这一项与弹窗并行，不构成弹窗方案的前置。

P1
弹窗埋点现状与补埋点工作量
建议
可照发弹窗埋点现在有的有、有的没有。想确认两件事：一是已经有埋点的部分，数据在哪里看，能不能按弹窗项查到曝光人数和点击率；二是给还没埋点的弹窗补上曝光、点击、关闭三个事件，大概是什么量级的工作量。

补齐后方案上线后可衡量效果；总控弹窗数量也需要人均曝光数。第一版的人群与内容来自标签清单与现有活动，不依赖历史效果数据。

P2
最轻一档负反馈与实验分流成本
建议
可照发 · 负反馈能不能做到：用户点 X 关掉某个弹窗之后，这个弹窗当天就不再出现？不需要连续关几次自动静默那种逻辑，就最简单的当日不再弹。
可照发 · 实验分流如果要把同一个人群随机切成两组、分别看到不同的弹窗内容，现在配置上能做吗？如果要开发，大概是什么量级的工作量？

补齐后负反馈能做则可降低弹窗疲劳；分流做不了则效果判断只能用前后对比，需在方案中说明归因限制。

共同的口径限制

两份的「总储值金额」均为账号累计值，时间窗口不同——新用户那份最长 3 个月，活跃全量那份可跨多年。两者的付费分布对比方向可信，幅度不可直接引用。两份均无「是否购买过首储礼包」字段，亦无法按月拆分，衰减型人群规模无法从中计算。

限时加码礼包的触发名单，按周取、每周四切：

WITH active_activity AS (
  SELECT store_activity_id, condition
  FROM `prod-439407.o8richonline_cdc.store_activity`
  WHERE category = "premium_bag" AND status = "active"
  LIMIT 1
)
SELECT DISTINCT elem.user_id
FROM active_activity, UNNEST(condition.buy_count_users) AS elem
UNION DISTINCT
SELECT DISTINCT b.user_id
FROM `prod-439407.o8richonline_cdc.user_premium_bag` b
JOIN active_activity a ON b.store_activity_id = a.store_activity_id
WHERE b.date = DATE_TRUNC(CURRENT_DATE('Asia/Taipei'), WEEK(THURSDAY));
