## 3. 病根（为什么不能直接按版本数单）

1. **一张单挂多个版本是设计内的。** 直接按 `fixVersion` 计数，同一张单会在 V50、V51 各算一次，用发版日去比截止日还会误判逾期。（事实：两版重叠的子单 18 张、长篇故事 3 张。）
2. **立项就是改类型，不留关联。** 「上周新建的营运需求单」如果只查 Requirement 类型，会漏掉他已经转走的单；如果按 form-37 标签查，又会混进子单和克隆单。（事实：见 2.1 末尾。）
3. **一半截止日没填。** 逾期只能判填了的单，没填的只能照实计数。（事实：V50 44%、V51 59%。）

## 4. 做法对比

**4.1 查询方式**
- A：MCP 只读查询，把返回的 JSON 存下来，再用 Python 离线计算和生成 HTML（同 `查去向.py` 的做法）。现在就能跑；每个单号都在存下的原始 JSON 里，完成标准 2 能用程序核对；重跑就是照 README 再查一遍、再运行脚本（完成标准 8）。缺点：每周一要手动发约 10—15 次查询，翻页也要手动。
- B：写一个 Python 脚本直接调 Jira REST。一条命令就能跑完。但要 Dk 生成 API token，AI 不能代填；token 落在本机也多一个泄露面。
- **推荐 A。** 能当天开工，也不涉及凭据。

**4.2 「上一周新建的营运需求单」怎么圈**
- A：只查 `issuetype in (Requirement, ACC)`。会漏掉已转走的 3 张，违反必答 ②-4。
- B：查 Requirement、ACC，再加上带 form-37 的长篇故事（都按建单日期），带 form-37 的长篇故事逐张查变更记录确认。能剔掉 RICH-25951 这类克隆单。
- C：同 B，但不查变更记录。RICH-25951 会被误算成需求单。
- **推荐 B。**（变更记录保留建单日期：改了类型以后，`created` 还是原需求单的日期，RICH-25827 就是这样。）

**4.3 「已转长篇故事、没挂版本」**
- A：标签 JQL 查到的直接用（16 张），里面可能有克隆单。
- B：标签 JQL 加变更记录确认，结果存进 `来源核对.json` 缓存，以后每周只查新出现的单。第一周要查 16 张，可以并行发。
- **推荐 B。**

**4.4 逾期第二条「截止日晚于发版日」，碰到挂多个版本的单怎么比**
- A：跟它挂的最早一个未发布版本比。两版重叠的 18 张子单很可能都被判成风险，违反完成标准 6。
- B：跟它所挂版本里最晚的那个 `releaseDate` 比。
- **推荐 B。**

**4.5 子单怎么取**
- A：取 `fixVersion = 本版` 的非长篇故事。没法按长篇故事分组，也会漏掉没继承到版本的子单。
- B：取本版长篇故事的全部子单（`parent in (…)`，不限状态，顺便算出「已完成 x/y」），再补上挂了本版、但没有父单或父单不在本版的单。
- **推荐 B。**

**4.6 HTML 怎么排，才能 30 秒看到要紧的事**
- A：按必答的顺序排：需求明细 → 风险 → 未挂版本。风险在第二屏。
- B：最上面一个「先看这里」框（≤5 行：风险计数加最急的 ≤3 个单号；要他定的单号），下面依次是风险表、要他排或要他回的单、明细，最后一行写口径。
- **推荐 B。** 完成标准 1 要的就是这个。

**4.7 需求单的建议怎么出**
- A：全靠脚本规则（比如标题关键词撞上就算重复）。会误判，理由也写不出来。
- B：脚本负责拉事实、列出可能重复的单；AI 读正文和评论，写进 `建议.json`；脚本校验证据之后合成 HTML。
- **推荐 B。** 完成标准 5 能用程序核对。
